1. EXECUTIVE SUMMARY
================================================================================

This plan ports Hermes's multi-pass context compaction system into OpenClaw.
The core idea: instead of a single compaction pass with a rigid 180s timeout,
wrap compaction in an iterative loop that:

  (a) runs up to MAX_COMPACTION_PASSES (3) sequential compaction passes,
  (b) measures progress after each pass (>5% token reduction or message
      count reduction),
  (c) stops early when context fits within the token budget OR progress
      stalls,
  (d) guards against thrashing via consecutive ineffective-compression
      tracking.

The plan also ports three complementary subsystems that make multi-pass
effective:

  - Pre-compaction tool result pruning with informative 1-line summaries
    (cheap LLM-free pass that shrinks context before expensive summarization)
  - Message anchoring in the tail (ensure last user/assistant messages
    survive compaction, preventing active-task loss)
  - Summary prefix disambiguation (prevent the model from treating
    compacted summaries as active instructions)

DESIGN PRINCIPLE: Extend, don't replace. OpenClaw's existing compaction
safeguard hook, quality guard, staged summarization, context pruning, and
session tree model are PRESERVED. The new multi-pass logic wraps AROUND
the existing single-pass infrastructure.

LAYER ASSIGNMENT:

  The multi-pass loop lives in the GATEWAY LAYER (src/agents/), NOT in
  agent-core. Rationale:

  1. agent-core's compact() is a stateless, single-pass primitive designed
     for portability across hosts (CLI, Copilot, Codex). Making it multi-pass
     would break that contract.

  2. The gateway layer (embedded-agent-runner) already manages retry loops,
     timeout accounting, and session state — multi-pass is a natural extension.

  3. The compaction-safeguard hook already overrides compact() behavior from
     the gateway layer — multi-pass wraps that same hook path.

  4. OpenClaw's architecture convention: agent-core provides primitives,
     gateway provides orchestration policies.

3. PORTING STRATEGY & PRINCIPLES
================================================================================

  P1  EXTEND, DON'T REPLACE
      - Existing compaction-safeguard hook, quality guard, staged
        summarization, context pruning, and session tree model are
        PRESERVED unchanged.
      - Multi-pass wraps around existing infrastructure.

  P2  IDIOMATIC TYPESCRIPT
      - Python classes -> TypeScript classes/interfaces
      - Python dicts -> TypeScript Record<string, unknown> or typed interfaces
      - Python Optional -> TypeScript `| undefined`
      - Python tuples -> TypeScript named return types or objects
      - Python f-strings -> TypeScript template literals
      - Python `for _pass in range(3)` -> TypeScript `for (let pass = 0; ...)`
      - Python `re.search` -> TypeScript `RegExp.exec()` or `.match()`
      - Python `json.loads/dumps` -> TypeScript `JSON.parse/stringify`
      - Python `hashlib.md5` -> Node.js `crypto.createHash('md5')`

  P3  FOLLOW OPENCLAW CONVENTIONS
      - Result<T, E> pattern for fallible operations
      - Structured logging via subsystem loggers
      - AbortSignal threading for cancellation
      - Worker threads for CPU-heavy planning
      - Hook-based extension points
      - Constants at module top, exported when cross-module

  P4  INCREMENTAL BUILDABILITY
      - Each step produces a compilable, testable increment
      - Steps 1-5 are independent leaf modules
      - Steps 6-7 integrate them into the run loop
      - Step 8 adds configuration
      - Step 9 adds tests

  P5  PRESERVE TIMEOUT SAFETY
      - The existing 180s safety timeout must encompass ALL passes, not
        reset per pass. Multi-pass shares one AbortSignal + one timeout
        window.

  P6  SESSION TREE COMPATIBILITY
      - Each compaction pass appends a CompactionEntry to the session tree
        (existing behavior via harness.compact() or the hook). Multi-pass
        means multiple CompactionEntry appends per invocation — this is
        safe because prepareCompaction() always finds the LAST compaction
        entry and builds from there.

STEP 2: Progress Detection & Anti-Thrashing Module
────────────────────────────────────────────────────────────────────────────────

PURPOSE: Port Hermes's _compression_made_progress() and anti-thrashing

─── FILE: packages/agent-core/src/harness/compaction/compaction-progress.ts (EXTEND)

  Add to the module created in Step 1:

  1. FUNCTION: compactionMadeProgress()

     Ported from: agent/turn_context.py lines 41-61

     /**
      * Determine whether a compaction pass materially reduced the context.
      *
      * Progress is detected when EITHER:
      *   - Message count decreased (any reduction counts), OR
      *   - Token count decreased by more than the progress threshold
      *     (default 5%), even if message count is unchanged.
      *
      * The token-only path handles "size-only" compression where tool
      * outputs are summarized without removing message rows.
      *
      * @see Hermes issue #39548 — size-only wins were false-negatives
      */
     export function compactionMadeProgress(
       origMessageCount: number,
       newMessageCount: number,
       origTokens: number,
       newTokens: number,
       progressThreshold: number = PROGRESS_THRESHOLD,
     ): boolean {
       if (newMessageCount < origMessageCount) return true;
       if (origTokens <= 0) return false;
       return newTokens < origTokens * (1 - progressThreshold);
     }

     TypeScript note: Direct translation — Hermes uses `new_tokens <
     orig_tokens * 0.95`, we use `(1 - progressThreshold)` for
     configurability.

  2. CLASS: CompactionProgressTracker

     Ported from: ContextCompressor._ineffective_compression_count and
     related tracking in agent/context_compressor.py lines 964-984,
     2665-2671.

     /**
      * Tracks compaction effectiveness across passes within a session.
      * Implements anti-thrashing: after MAX_INEFFECTIVE_COMPRESSIONS
      * consecutive passes that each save < INEFFECTIVE_SAVINGS_THRESHOLD,
      * shouldCompact() returns false to prevent infinite loops.
      *
      * Lifecycle: one instance per embedded-agent-runner session.
      * Reset on session clear/new session.
      */
     export class CompactionProgressTracker {
       private _ineffectiveCount = 0;
       private _lastSavingsPct = 0;
       private _compressionCount = 0;

       /** Record the outcome of a compaction pass. */
       recordCompaction(tokensBefore: number, tokensAfter: number): void {
         this._compressionCount++;
         const savingsPct =
           tokensBefore > 0
             ? ((tokensBefore - tokensAfter) / tokensBefore)
             : 0;
         this._lastSavingsPct = savingsPct;
         if (savingsPct < INEFFECTIVE_SAVINGS_THRESHOLD) {
           this._ineffectiveCount++;
         } else {
           this._ineffectiveCount = 0;  // Reset on effective compression
         }
       }

       /** Anti-thrashing check: should we attempt compaction? */
       shouldAttemptCompaction(): boolean {
         return this._ineffectiveCount < MAX_INEFFECTIVE_COMPRESSIONS;
       }

       /** Reset tracker (session clear / new session). */
       reset(): void {
         this._ineffectiveCount = 0;
         this._lastSavingsPct = 0;
         this._compressionCount = 0;
       }

       /** Current state snapshot (for diagnostics/logging). */
       getState(): CompactionProgressTrackerState {
         return {
           ineffectiveCompressionCount: this._ineffectiveCount,
           lastCompressionSavingsPct: this._lastSavingsPct,
           compressionCount: this._compressionCount,
         };
       }
     }

  2. FUNCTION: pruneOldToolResults()

     Ported from: _prune_old_tool_results()

     /**
      * Cheap LLM-free pre-pass that reduces context before summarization.
      *
      * Three sub-passes:
      *   1. Deduplicate identical tool results (MD5 hash, keep newest)
      *   2. Replace old tool results with 1-line summaries
      *   3. Truncate large tool call arguments in assistant messages
      *
      * "Old" = before the tail protection boundary.
      *
      * @param messages     Session messages to prune
      * @param tailTokenBudget  Token budget for the protected tail
      * @param minProtectedCount  Minimum messages to protect in tail
      * @returns { messages: pruned list, prunedCount: number }
      */
     export function pruneOldToolResults(
       messages: AgentMessage[],
       tailTokenBudget: number,
       minProtectedCount: number,
     ): { messages: AgentMessage[]; prunedCount: number }

     SUB-PASS 1: Deduplication
       - Walk backward through messages
       - For each toolResult message with content > 200 chars:
         - Compute MD5 hash of content (first 12 hex chars)
         - If hash already seen (newer copy exists), replace content with:
           "[Duplicate tool output — same content as a more recent call]"
       - Uses: import { createHash } from "node:crypto";

     SUB-PASS 2: Old Tool Result Replacement
       - Determine prune boundary: walk backward accumulating tokens,
         stop when accumulated > tailTokenBudget AND at least
         minProtectedCount messages are protected
       - For messages BEFORE boundary with role "toolResult":
         - Look up the parent tool call (by tool_use_id) to get tool name + input
         - Replace content with summarizeToolResult(toolName, input, content)
         - Only replace when original content > 200 chars

     SUB-PASS 3: Tool Call Argument Truncation
       - For assistant messages BEFORE boundary with tool_use blocks:
         - If tool input JSON string > 500 chars:
           - Parse as JSON
           - Truncate string values > 200 chars (keep head + "...[truncated]")
           - Re-serialize
       - Use JSON.parse/stringify with a truncation replacer

     /**
      * JSON-aware truncation of tool call arguments.
      * Preserves JSON validity (critical for API wire format).
      */

       inputJson: string,
       maxTotalChars: number = 500,
       maxStringValueChars: number = 200,
     ): string

STEP 4: Cut Point Enhancement (Message Anchoring)
────────────────────────────────────────────────────────────────────────────────

PURPOSE: Port Hermes's _ensure_last_user_message_in_tail() and
_ensure_last_assistant_message_in_tail() into OpenClaw's findCutPoint()

─── FILE: packages/agent-core/src/harness/compaction/compaction.ts (MODIFY)

  Ported from: agent/context_compressor.py lines 442-459
  (_ensure_last_user_message_in_tail, _ensure_last_assistant_message_in_tail)

  1. MODIFY findCutPoint():

     After the existing cut point calculation (walk backward accumulating
     tokens to keepRecentTokens), add two anchoring passes:

     a. LAST USER MESSAGE ANCHOR:
        - Find the last entry with role "user" at or after startIndex
        - If it falls BEFORE the computed firstKeptEntryIndex:
          - Pull firstKeptEntryIndex back to include this message
        - This prevents the active user task from being compacted away
        - Ported from Hermes issue #10896 fix

     b. LAST ASSISTANT MESSAGE ANCHOR:
        - Find the last entry with role "assistant" that has visible text
          content (not just tool_calls)
        - If it falls BEFORE firstKeptEntryIndex:
          - Pull firstKeptEntryIndex back to include this message
        - This prevents "can't see the output" bugs
        - Ported from Hermes issue #29824 fix

     c. RE-ALIGNMENT:
        - After both anchors, re-check that the cut point doesn't land
          inside a tool_call/toolResult pair
        - Walk backward past consecutive toolResult entries
        - If landed on a parent assistant with tool_calls, pull before it

     d. MONOTONICITY INVARIANT:
        - Both anchors can only GROW the tail (pull firstKeptEntryIndex
          earlier), never shrink it
        - Final safety: max(firstKeptEntryIndex, startIndex + 1)

  2. MODIFY CutPointResult type (in types.ts):

     Add optional diagnostic fields:
       /** Whether the user message anchor activated */
       userMessageAnchored?: boolean;
       /** Whether the assistant message anchor activated */
       assistantMessageAnchored?: boolean;

  CRITICAL: The anchoring logic uses OpenClaw's SessionTreeEntry types
  (message entries with roles), NOT Hermes's flat dict format. The
  translation maps:
    - Hermes: msg["role"] == "user" -> OpenClaw: entry.type === "message"
      && entry.message.role === "user"
    - Hermes: msg["role"] == "assistant" -> OpenClaw: entry.type === "message"
      && entry.message.role === "assistant"
    - Hermes: assistant with visible content -> check for text content
      in entry.message.content, not just tool_calls

─── REUSE: Fully within existing findCutPoint() function. No new files
    needed. Uses existing SessionTreeEntry types.

  1. FUNCTION: multiPassCompact()

     /**
      * Run up to maxPasses sequential compaction passes, checking for
      * material progress after each. Stops when:
      *   - Token count is below the compaction threshold, OR
      *   - Progress stalls (<5% token reduction AND no message count
      *     reduction), OR
      *   - maxPasses exhausted, OR
      *   - Safety timeout fires, OR
      *   - AbortSignal is triggered.
      *
      * This wraps the existing single-pass compaction infrastructure
      * (contextEngine.compact via compactContextEngineWithSafetyTimeout).
      * The compaction-safeguard hook, quality guard, staged summarization,
      * and all existing OpenClaw features are preserved per-pass.
      *
      * @param contextEngine    The context engine to compact against
      * @param params           Base compaction params (sessionId, runtimeContext, etc.)
      * @param settings         Compaction settings (reserveTokens, keepRecentTokens, maxPasses)
      * @param contextWindow    Total context window tokens for threshold check
      * @param estimateTokensFn Function to estimate current context tokens
      * @param tracker          Progress tracker for anti-thrashing
      * @param timeoutMs        Total timeout budget for ALL passes (default 180s)
      * @param abortSignal      External abort signal
      * @param logger           Subsystem logger
      * @returns MultiPassCompactionResult with per-pass details
      */
     export async function multiPassCompact(params: {

       compactParams: ContextEngineCompactParams;

     async function multiPassCompact(params): Promise<MultiPassCompactionResult> {
       const {
         contextEngine, compactParams, settings, contextWindow,
         estimateTokensFn, tracker, abortSignal, logger,
       } = params;

       const maxPasses = settings.maxPasses ?? MAX_COMPACTION_PASSES;
       const progressThreshold = settings.progressThreshold ?? PROGRESS_THRESHOLD;
       const timeoutMs = params.timeoutMs ?? EMBEDDED_COMPACTION_TIMEOUT_MS;

       const passes: MultiPassCompactionState[] = [];
       const startTime = Date.now();
       let finalTokens = await estimateTokensFn();

       // Anti-thrashing gate
       if (!tracker.shouldAttemptCompaction()) {
         logger?.warn("Compaction skipped — last %d compressions saved <10%% each",
           tracker.getState().ineffectiveCompressionCount);
         return {
           passes: [],
           totalPasses: 0,
           finalTokens,
           metThreshold: !shouldCompact(finalTokens, contextWindow, settings),
           stopReason: "no_progress",
           totalElapsedMs: 0,
         };
       }

       for (let pass = 0; pass < maxPasses; pass++) {
         // Check timeout budget
         const elapsed = Date.now() - startTime;
         const remainingMs = timeoutMs - elapsed;
         if (remainingMs < 10_000) {  // Need at least 10s for a pass
           return buildResult(passes, finalTokens, "timeout", ...);
         }

         // Check abort signal
         if (abortSignal?.aborted) {
           return buildResult(passes, finalTokens, "aborted", ...);
         }

         const origTokens = finalTokens;
         const origMessageCount = /* get from session context */;
         const passStart = Date.now();

         // Run one compaction pass with remaining timeout budget
         const compactResult = await compactWithSafetyTimeout(
           (signal) => contextEngine.compact({ ...compactParams, abortSignal: signal }),
           remainingMs,
           abortSignal ? { abortSignal } : undefined,
         );

         const passElapsed = Date.now() - passStart;

         if (!compactResult.ok || !compactResult.compacted) {
           // Pass failed or nothing to compact
           passes.push({
             pass,
             tokensBefore: origTokens,
             tokensAfter: origTokens,
             messageCountBefore: origMessageCount,
             messageCountAfter: origMessageCount,
             madeProgress: false,
             elapsedMs: passElapsed,
           });
           return buildResult(passes, finalTokens, "no_progress", ...);
         }

         // Re-estimate tokens after compaction
         finalTokens = compactResult.result?.tokensAfter
           ?? await estimateTokensFn();
         const newMessageCount = /* get from session context */;

         // Track effectiveness
         tracker.recordCompaction(origTokens, finalTokens);

         const madeProgress = compactionMadeProgress(
           origMessageCount, newMessageCount,
           origTokens, finalTokens,
           progressThreshold,
         );

         passes.push({
           pass,
           tokensBefore: origTokens,
           tokensAfter: finalTokens,
           messageCountBefore: origMessageCount,
           messageCountAfter: newMessageCount,
           madeProgress,
           elapsedMs: passElapsed,
         });

         logger?.info(
           "Compaction pass %d: %d -> %d tokens (%.1f%% reduction), %d -> %d messages",
           pass + 1, origTokens, finalTokens,
           ((origTokens - finalTokens) / origTokens) * 100,
           origMessageCount, newMessageCount,
         );

         // Check if we're below threshold now
         if (!shouldCompact(finalTokens, contextWindow, settings)) {
           return buildResult(passes, finalTokens, "threshold_met", ...);
         }

         // Check if progress stalled
         if (!madeProgress) {
           return buildResult(passes, finalTokens, "no_progress", ...);
         }

         // Anti-thrashing check for next pass
         if (!tracker.shouldAttemptCompaction()) {
           return buildResult(passes, finalTokens, "no_progress", ...);
         }
       }

       return buildResult(passes, finalTokens, "max_passes", ...);
     }

  3. HELPER: buildResult()

     function buildResult(
       passes, finalTokens, stopReason, contextWindow, settings, startTime,
     ): MultiPassCompactionResult {
       return {
         passes,
         totalPasses: passes.length,
         finalTokens,
         metThreshold: !shouldCompact(finalTokens, contextWindow, settings),
         stopReason,
         totalElapsedMs: Date.now() - startTime,
       };
     }

─── KEY DESIGN DECISIONS:

  D1. TIMEOUT SHARING: The total timeout budget (180s by default) is
      SHARED across all passes. Each pass gets `remainingMs`, not a
      fresh timeout. This prevents multi-pass from exceeding the safety
      timeout.

  D2. ABORT PROPAGATION: The external AbortSignal is threaded into each
      pass. If the user cancels mid-loop, the current pass aborts and
      the loop exits cleanly.

  D3. TOKEN ESTIMATION: After each pass, tokens are re-estimated using
      either the compactResult.result.tokensAfter (preferred, from the
      compaction-safeguard hook) or the estimateTokensFn callback (fallback,
      calls estimateContextTokens on the rebuilt session context).

  D4. SESSION CONSISTENCY: Each pass appends a CompactionEntry to the
      session tree. On the next pass, prepareCompaction() finds this
      entry and builds from it. This is the correct behavior — each pass
      starts from where the previous one left off.

  D5. PRE-PRUNING INTEGRATION: The pruneOldToolResults() function from
      Step 3 is called ONCE before the first pass (not per-pass), because
      subsequent passes operate on already-pruned content. This is wired
      in Step 7 when integrating with the run loop.

7. RISK ANALYSIS & MITIGATION
================================================================================

─── RISK 1: Timeout Exhaustion ────────────────────────────────────────────────

  RISK: Multi-pass consumes the entire 180s timeout budget, causing
  compaction to time out when it wouldn't have with single-pass.

  PROBABILITY: MEDIUM
  IMPACT: MEDIUM (compaction fails, context continues to grow)

  MITIGATION:
  a. Reserve minimum 10s per remaining pass before starting
  b. Log per-pass timing in MultiPassCompactionResult
  c. Default maxPasses=3 with typical 20-40s per pass = 60-120s total,
     well within the 180s budget
  d. Configurable timeoutMs per deployment

─── RISK 2: Session Tree Bloat ────────────────────────────────────────────────

  RISK: Each pass appends a CompactionEntry to the session tree.
  3 passes = 3 entries per compaction invocation. Over many invocations,
  the session file grows.

  PROBABILITY: LOW
  IMPACT: LOW (entries are small, and buildSessionContext only uses the
  LAST compaction entry)

  MITIGATION:
  a. prepareCompaction() already skips entries before the last compaction.
     Multiple entries are harmless — only the last one matters at runtime.
  b. Monitor session file growth in production telemetry.

─── RISK 3: Pre-Pruning Side Effects ─────────────────────────────────────────

  RISK: Tool result pruning replaces content that the summarizer or
  quality guard relies on.

  PROBABILITY: LOW
  IMPACT: MEDIUM (degraded summary quality)

  MITIGATION:
  a. Pre-pruning only modifies the ASSEMBLED context, not the persisted
     session tree. Original content is always recoverable.
  b. The tail protection boundary ensures recent tool results are never
     pruned — only old, out-of-cache results are affected.
  c. 1-line summaries preserve the KEY information (tool name, arguments,
     exit code, output size) that the summarizer needs.
  d. Pre-pruning can be disabled via config: prePruning.enabled = false.

─── RISK 4: Message Anchoring Over-Protection ────────────────────────────────

  RISK: Message anchoring pulls too many messages into the tail, leaving
  insufficient content for the summarizer (nothing to summarize).

  PROBABILITY: LOW
  IMPACT: MEDIUM (compaction becomes a no-op)

  MITIGATION:
  a. Anchoring only activates when the target message is NOT already in
     the tail — most conversations won't trigger it.
  b. The minimum-for-compression check (existing) catches the case where
     anchoring leaves nothing to summarize.
  c. Both anchors are MONOTONIC — they can only grow the tail, and the
     tail growth is bounded by message positions.

─── RISK 5: Anti-Thrashing False Positives ────────────────────────────────────

  RISK: The anti-thrashing guard blocks compaction prematurely, causing
  the context to exceed the window and trigger overflow errors.

  PROBABILITY: LOW
  IMPACT: HIGH (context overflow, potential data loss)

  MITIGATION:
  a. Anti-thrashing only blocks via should_compress() / shouldAttemptCompaction().
     Overflow recovery (Path B) uses force=true which bypasses the guard.
  b. The tracker resets on session switch/clear.
  c. Anti-thrashing is configurable: antiThrashingEnabled = false.
  d. The threshold (2 consecutive ineffective) matches Hermes's proven value.

─── RISK 6: Breaking Existing Hook Consumers ──────────────────────────────────

  RISK: The compaction-safeguard hook expects to be called once per
  compaction event. Multi-pass calls it multiple times.

  PROBABILITY: LOW
  IMPACT: LOW (hook is idempotent — each call produces a fresh summary)

  MITIGATION:
  a. The hook receives independent CompactionPreparation per call.
  b. The hook's quality guard runs per-pass (desirable — each summary
     is quality-checked).
  c. The session_compact notification hook fires per-pass — extension
     consumers get per-pass notifications (more data, not less).

─── RISK 7: Summary Prefix Regression ────────────────────────────────────────

  RISK: The enhanced disambiguation prefix is significantly longer than
  the current prefix. This consumes more of the context window and
  may affect summarization behavior for models that weight prefix
  instructions heavily.

  PROBABILITY: LOW
  IMPACT: LOW (prefix adds ~300 tokens, negligible vs 200K context)

  MITIGATION:
  a. The prefix is still much smaller than the summary body.
  b. Configurable: disambiguationPrefix = false reverts to the minimal prefix.
  c. The end marker (separate) can be independently disabled.
