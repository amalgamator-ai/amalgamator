ISSUE 1 — CRITICAL: Silent test no-op (double-wrapped async function)

  AFFECTED CODE:
    src/agents/multi-pass-compaction.test.ts, line 88
    it("returns after one pass when compact succeeds...", () => async () => {

  WHAT IS WRONG:
    The test callback is `() => async () => {` — a synchronous function that
    returns an async function. Vitest calls the outer function, gets back an
    async function (truthy), and marks the test as passed without executing
    the inner function body. All assertions inside (expect(result.totalPasses),
    expect(result.stopReason), expect(mockEngine.compact)) never run.

  WHY IT MATTERS:
    This is a false-positive test. The first test in Suite E's "single-pass
    behavior" group passes vacuously, providing zero coverage for the
    threshold_met stop condition on a below-budget single-pass. A regression
    in that code path would go undetected.

  FIX APPLIED:
    Changed `() => async () => {` to `async () => {` — the standard vitest
    async test pattern.

ISSUE 2 — MEDIUM: `any` type cast in hasVisibleContent helper

  AFFECTED CODE:
    packages/agent-core/src/harness/compaction/compaction.ts, line 420
    const content = (msg as any).content;

  WHAT IS WRONG:
    The `as any` cast bypasses TypeScript's type system entirely. The existing
    codebase's established pattern for accessing content on HarnessMessage
    variants uses structural type casts like:
      (harnessMessage as { content: string | Array<{ type: string; text?: string }> }).content
    (See estimateTokens() in the same file.)

  WHY IT MATTERS:
    Using `as any` means typos in property access (e.g., `msg.contnt`) would
    not be caught at compile time. A structural cast preserves type checking
    for the accessed property. Also `(c: any)` in the `.some()` callback
    loses type info for the block shape.

  FIX APPLIED:
    Changed to:
      (msg as { content?: string | Array<{ type: string; text?: string }> }).content
    And removed `c: any` from the `.some()` callback since the array type
    now properly narrows the element type.

ISSUE 3 — MEDIUM: Excessive `as any` casts in pre-compaction-pruning.ts

  AFFECTED CODE:
    src/agents/agent-hooks/pre-compaction-pruning.ts, lines 36, 46, 63, 75
    const msg = result[i] as any;
    Also: function signatures extractToolResultText(msg: any) and
    cloneToolResultWithText(msg: any, ...)

  WHAT IS WRONG:
    Four loop bodies and two helper functions use `any` for message access.
    While the role checks that follow (e.g., `if (msg.role !== "toolResult")`)
    provide runtime safety, the `any` type undermines compile-time checking.
    After the role narrowing, accessing `msg.toolName`, `msg.content`, etc.
    would ideally be type-safe.

  WHY IT MATTERS:
    Any property misspelling (e.g., `msg.toolname` instead of `msg.toolName`)
    would compile silently and fail only at runtime. A typed intermediate
    narrows the error surface.

  FIX APPLIED:
    Added a typed alias:
      type NarrowedMessage = AgentMessage & { role: string; [key: string]: unknown };
    Replaced all 4 `as any` casts with `as NarrowedMessage`.
    Updated `extractToolResultText` and `cloneToolResultWithText` signatures
    from `msg: any` to `msg: NarrowedMessage`.

2. ISSUES REVIEWED BUT NOT REQUIRING FIXES

REVIEW ITEM A: Import path pattern (../../packages/agent-core/src/...)

  The multi-pass-compaction.ts and its test use relative paths like
  `../../packages/agent-core/src/harness/compaction/compaction.js`
  rather than the `@openclaw/agent-core` package alias.

  VERDICT: ACCEPTABLE — This pattern is widely used throughout the
  codebase (37+ files in src/ import from ../../packages/). The
  @openclaw/agent-core alias is defined in tsconfig.json but not used
  by any src/agents/ files. The vitest runtime resolves relative paths
  correctly, as confirmed by test execution. No change needed.

REVIEW ITEM B: Hermes progress detection includes message count check

  Hermes's _compression_made_progress() returns True if EITHER:
    - new_len < orig_len (message count decreased), OR
    - new_tokens < orig_tokens * 0.95 (token reduction >= 5%)

  The OpenClaw port only checks token reduction, not message count.

  VERDICT: ACCEPTABLE — This is a deliberate design decision documented
  in the porting plan (Step 2). The multi-pass loop does not have direct
  access to message counts (it calls contextEngine.compact() which
  returns token counts). Token-only progress detection is sufficient
  because any meaningful compaction that reduces message count also
  reduces token count. The plan explicitly notes this simplification.

REVIEW ITEM C: findCutPoint anchoring guard threshold

  The anchoring in findCutPoint requires `lastUserIdx - startIndex >= 3`
  and `lastAssistantIdx - startIndex >= 3` before applying. This was
  added to prevent regression of the existing compaction-trailing-
  toolresult test.

  VERDICT: ACCEPTABLE — The guard ensures at least 3 entries remain for
  summarization, preventing degenerate cases where anchoring would make
  compaction unable to summarize anything. The existing test confirms
  the guard works correctly.

REVIEW ITEM D: pre-compaction-pruning.ts remaining (block: any) cast

  Line 82: `msg.content.map((block: any) => {` uses `any` for content
  block iteration inside an assistant message.

  VERDICT: ACCEPTABLE — After the role check `msg.role !== "assistant"`,
  the content is known to be an array of content blocks (text, toolCall,
  thinking). The `any` here is pragmatic since the map handles multiple
  block types with type-guarded property access (`block.type !== "toolCall"`).
  The existing codebase uses similar patterns in estimateTokens().

REVIEW ITEM E: Correctness of multiPassCompact loop logic

  Verified against Hermes source:
  - 3 max passes (matches Hermes `range(3)`)
  - 5% progress threshold (matches Hermes `0.95` multiplier)
  - Anti-thrash: 2 consecutive < 10% savings (matches Hermes counter)
  - Per-pass lifecycle with adoptTranscript (matches Hermes state resets)
  - Timeout via single AbortSignal budget (correct adaptation of
    OpenClaw's safety timeout pattern)
  - Token re-estimation via CompactResult.result.tokensAfter (matches
    Hermes's estimate_request_tokens_rough after each pass)

  VERDICT: CORRECT — The multi-pass loop faithfully ports Hermes behavior.

REVIEW ITEM F: Summary prefix / end marker changes

  The enhanced COMPACTION_SUMMARY_PREFIX includes:
  - "[COMPACTION — REFERENCE ONLY]" (matches Hermes prefix concept)
  - "Do NOT answer questions or fulfill requests" (matches Hermes)
  - "Respond ONLY to the latest user message" (matches Hermes)
  - COMPACTION_SUMMARY_END_MARKER appended after </summary> tag

  VERDICT: CORRECT — The prefix is a condensed version of Hermes's
  more verbose prefix. It captures the core disambiguation directives
  without the Hermes-specific headings (Historical Task Snapshot, etc.)
  that don't apply to OpenClaw's structured summary format.
