              compaction providers no longer receive all messages.
  Action:     FIXED. Moved preCompactionPrune call from before the provider
              path to after it, so it only applies to the LLM safeguard path.

              baseMessagesToSummarize, preserving its existing all-message

              built-in LLM summarization path.

COMMENT 2: [P1] Wire the multi-pass loop into real callers
  Location:   src/agents/multi-pass-compaction.ts:119-121
  Category:   Design concern
  Priority:   Must-fix (addressed by scope reduction)
  Reviewer:   multiPassCompact is standalone and not wired into production
              compaction entry points. Users setting maxPasses would get
              the old single-call path.
  Action:     ADDRESSED VIA SCOPE REDUCTION. Instead of wiring into production
              callers (which requires changes to the embedded-agent-runner's
              compaction orchestration — a significant architectural change
              outside this PR's scope), we:
              (a) Removed public exports of all multi-pass internals from
                  packages/agent-core/src/index.ts
              (b) Removed user-facing config knobs (maxPasses, progressThreshold)
                  from the Zod schema, type definitions, and defaults
              (c) Kept multiPassCompact as an internal, well-tested module
                  ready for integration in a follow-up PR
              This ensures production behavior matches PR claims: no user-visible
              knobs that don't work, no unapproved public API surface.
  Why:        The reviewer's core concern was that users could set config
              values that would be no-ops. By removing the public config
              surface while keeping the internal implementation intact and
              tested, we eliminate that risk without a large refactor.
