2. PLAN SUMMARY
================================================================================

The V2 plan ports Hermes's multi-pass context compaction into OpenClaw
through 9 incremental steps:

  Step 1: Types, Interfaces & Constants
    - Define MultiPassCompactionState, MultiPassCompactionResult,
      CompactionProgressTrackerState in new compaction-progress.ts
    - Add maxPasses, progressThreshold to CompactionSettings
    - Export new types from agent-core index

  Step 2: Progress Detection & Anti-Thrashing
    - compactionMadeProgress(): token-only progress check (>5%)
    - CompactionProgressTracker class with anti-thrashing (2x <10% → block)

  Step 3: Tool Result Pre-Pruning
    - NEW pre-compaction-pruning.ts with summarizeToolResult() and
      pruneMessagesForCompaction()
    - Injected into compaction-safeguard.ts AFTER stripRuntimeContextCustomMessages
      (line 884), BEFORE buildHistoryPrunePlanWithWorker (line 1077)
    - 3 sub-passes: MD5 dedup, 1-line summaries, arg truncation

  Step 4: Cut Point Enhancement (Message Anchoring)
    - Add last-user-message anchor to findCutPoint()
    - Add last-assistant-message anchor (text content only)
    - Re-alignment to prevent tool pair splitting
    - Monotonicity invariant (tail only grows)

  Step 5: Summary Prefix Disambiguation
    - Enhanced prefix with REFERENCE ONLY directives
    - End marker after summary suffix
    - Backward-compatible (both minimal and enhanced available)

  Step 6: Multi-Pass Compaction Loop (CENTRAL STEP)
    - NEW multi-pass-compaction.ts in gateway layer
    - multiPassCompact() wraps existing single-pass infrastructure
    - Per-pass lifecycle: adopt → maintenance → record → check
    - Timeout sharing, abort propagation, session consistency

  Step 7: Embedded Runner Integration
    - Replace 2 compactContextEngineWithSafetyTimeout calls in run.ts
    - Lifecycle callbacks for per-pass adopt/maintenance
    - Conditional multi-pass/single-pass selection
    - Result mapping to CompactResult for existing code compatibility

  Step 8: Configuration
    - multiPass section in config (enabled, maxPasses, progressThreshold)
    - prePruning section (enabled, minContentLength, deduplication)
    - All optional with sane defaults

  Step 9: Tests
    - 5 test files (2 new in agent-core, 3 new/modified in gateway)
    - Coverage: progress detection, tracker, pre-pruning, anchoring,
      multi-pass loop, prefix/end marker, integration

FILE COUNTS:
  New files: 6 (3 modules + 3 test files)
  Modified files: 9

DEPENDENCIES:
  New: node:crypto (built-in)
  External npm: none

3. ITERATION EVOLUTION
================================================================================

─── ITERATION 1: V1 (Initial Plan) ───────────────────────────────────────────

  The V1 plan was generated from code trace analysis and partial source
  verification. It established the 9-step structure and identified the
  core porting targets. However, it had 15 issues across critical,
  significant, and minor severity levels.

  Key errors in V1:
    - Pre-pruning injection point in run.ts (dead code location)
    - Per-pass lifecycle not recognized (adopt + maintenance)
    - Wrong file locations for types (CompactionSettings, CutPointResult)
    - Wrong package name (@anthropic/ instead of @openclaw/)
    - Message count estimation hand-waved (impossible in session tree)
    - estimateTokensFn unnecessary (tokensAfter is reliable)
    - 3 call sites assumed (actually 2)

─── ITERATION 1.5: Review V1 (Corrected Plan) ────────────────────────────────

  The Review V1 phase performed deep code-level verification against
  the actual OpenClaw source. It found and fixed all 15 issues, with
  the most important fixes being:

    - Pre-pruning moved to compaction-safeguard hook (correct pipeline)
    - Per-pass lifecycle callbacks added (adoptTranscript + runMaintenance)
    - All file locations and package names corrected
    - Progress detection simplified to token-only
    - Call site count corrected to 2

  The Review V1 was a CORRECTED plan, not a from-scratch rebuild. It
  maintained the same structure as V1 but with fixes applied in-place.

─── ITERATION 2: V2 (Current — From Scratch) ─────────────────────────────────

  V2 was built from scratch with all Review V1 learnings pre-incorporated.
  Additionally, 6 new issues were discovered through even deeper source
  verification:

    L16: EMBEDDED_COMPACTION_TIMEOUT_MS is a private constant, not exported.
         V2 defines DEFAULT_COMPACTION_TIMEOUT_MS as a public alternative
         and passes resolved timeout from the caller.

    L17: Third adoptCompactionTranscript call site at run.ts:2768 was not
         documented. This is a safety fallback for partial-ok compaction
         results. V2 accounts for all 3 call sites and subsumes them
         via per-pass adoption.

    L18: The overflow recovery has a two-branch adoption pattern:
         (ok && compacted) at line 2725 triggers adopt + maintenance,
         while (compacted only) at line 2767 is a fallback. V2's
         per-pass adoption handles both branches correctly.

    L19: runOwnsCompactionBeforeHook and runOwnsCompactionAfterHook must
         fire once per invocation (not per pass). V2 adds Principle P8
         and preserves hooks at the caller level.

    L20: buildEmbeddedContextEngineRuntimeSettings is a locally-scoped
         closure, not an exported function. V2 notes that callbacks
         defined in run()'s scope have access to it.

    L21: shouldCompact has two identities: the agent-core function
         (simple threshold check, correct for post-pass use) and the
         preemptive decision function (complex, not used in multi-pass).
         V2 clarifies which is used where.

  V2 STRUCTURAL IMPROVEMENTS over Review V1:

    1. Conditional multi-pass/single-pass selection via isMultiPassEnabled()
       provides a safe rollback mechanism at each call site.

    2. runMaintenance callback is OPTIONAL in multiPassCompact — the timeout
       path doesn't call runContextEngineMaintenance (verified), so the
       callback is omitted for site 1.

    3. Result mapping from MultiPassCompactionResult to CompactResult is
       explicitly documented, ensuring compatibility with existing
       post-compaction code (hooks, token tracking, truncation).

    4. Anti-thrashing stopReason is "anti_thrash" (distinct from
       "no_progress") for clearer diagnostics.

    5. 8 risks analyzed (vs 7 in Review V1), including a new risk for
       result mapping correctness.

    6. shouldCompact import in multiPassCompact uses dynamic import
       with documented rationale (D8) to avoid confusion with the
       preemptive decision function.

    7. Full traceability section (Section 9) maps all 21 issues from
       V1 through V2 with exact locations of each fix.

  V2 UNCHANGED from Review V1:

    - 9-step structure (types → progress → pruning → anchoring →
      prefix → loop → integration → config → tests)
    - 6 new files, 9 modified files
    - Gateway layer placement for multi-pass loop
    - Agent-core placement for types and tracker
    - Pre-pruning inside compaction-safeguard hook
    - Per-pass lifecycle via callbacks
    - Token-only progress detection
    - No new npm dependencies (node:crypto is built-in)
