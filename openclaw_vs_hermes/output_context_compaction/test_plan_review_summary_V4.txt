  ── FIX-RV4: TESTS 8.8 AND 8.19 ANTI-THRASH AMBIGUITY ──────────────────────

    SEVERITY: Medium (tests pass for the wrong reason)

    V4 STATED (for both tests):
      mockEngine.compact always resolves to
      makeCompactSuccess({ tokensAfter: 150000 })

    PROBLEM: The multi-pass loop tracks inter-pass progress. With a
    constant mock (every call returns tokensAfter=150000):

      Pass 1: result.tokensBefore=200000 (makeCompactSuccess default),
              tokensAfter=150000. Progress: 25% (200000→150000). OK.
      Pass 2: prevTokens=150000 (from pass 1), newTokens=150000 (same mock).
              Progress: 0%. consecutiveNoProgress=1.
      Pass 3: prevTokens=150000, newTokens=150000.
              Progress: 0%. consecutiveNoProgress=2. ANTI-THRASH FIRES.

    Result: the loop stops at 3 passes because anti-thrash fires at
    counter=2, which COINCIDENTALLY equals maxPasses=3.

    Test 8.8 says it verifies "stops at maxPasses even if still above
    budget" — but it actually stops due to anti-thrash.
    Test 8.19 says it verifies "defaults maxPasses to 3" — but it
    actually stops due to anti-thrash.

    If the default maxPasses were changed to 10, BOTH tests would still
    pass (anti-thrash stops at pass 3 regardless). So they don't detect
    regressions in the maxPasses logic.

    NOTE: This analysis assumes the loop uses "inter-pass tracking"
    (previous tokensAfter vs current tokensAfter) for progress detection.
    If the implementation uses "per-pass tracking" (result.tokensBefore vs
    result.tokensAfter), every pass shows 25% progress and only maxPasses
    limits the loop. Since the implementation design isn't locked, the test
    should be robust to EITHER approach.

    CORRECTED: Both tests now use .mockResolvedValueOnce() with DECREASING
    tokensAfter values, each showing >5% relative reduction from the
    previous pass. This ensures progress is always detected and ONLY
    maxPasses limits the loop — regardless of which progress tracking
    method the implementation uses.

    VERIFICATION:
      Test 8.8 (corrected):
        Pass 1: 200000→170000. 15% reduction > 5%. Progress. ✓
        Pass 2: 170000→145000. 14.7% reduction > 5%. Progress. ✓
        Pass 3: 145000→125000. 13.8% reduction > 5%. Progress. ✓
        Budget: 125000 > 100000. Still above. ✓
        Only maxPasses=3 stops the loop.

      Test 8.19 (corrected):
        Same decreasing pattern. Only maxPasses=3 (default) stops the loop.

  ── FIX-RV5: TEST 8.21 TWO CASES IN ONE it() BLOCK ──────────────────────────

    SEVERITY: Low-Medium (test would fail due to accumulated mock calls)

    V4 STATED:
      8.21 it("clamps maxPasses to [1, 10] at runtime")
           CALL 1: multiPassCompact(..., { maxPasses: 50 })
           EXPECT: called at most 10 times

           CALL 2: multiPassCompact(..., { maxPasses: 0 })
           EXPECT: called exactly 1 time

    PROBLEMS:
      1. Mock not reset between calls. After call 1 (3 compact calls due
         to anti-thrash, see FIX-RV4), total call count = 3. After call 2
         (1 more call), total = 4. Assertion "called exactly 1 time" fails
         because the mock shows 4 accumulated calls.

      2. With the original constant mock, call 1 results in only 3 calls
         (anti-thrash), not 10. The assertion "at most 10 times" passes
         trivially (3 <= 10) but doesn't verify clamping from 50 to 10.

      3. Violates principle P1 (one assertion focus per test).

    CORRECTED: Split into two it() blocks:
      8.21a: "clamps maxPasses to 10 at maximum" — uses decreasing
             tokensAfter mock, expects exactly 10 compact calls.
      8.21b: "clamps maxPasses to 1 at minimum" — expects exactly 1 call.

    Test count: 22 → 23 (Suite E only; total 112 → 113).

  ── FIX-RV6: SUITE F IMPORT PATTERN WRONG ───────────────────────────────────

    SEVERITY: Low (would work but inconsistent with existing convention)

    V4 STATED:
      let harness: Awaited<ReturnType<
        typeof import("../run.overflow-compaction.harness.js")
      >>;
      beforeAll(async () => {
        const mod = await import("../run.overflow-compaction.harness.js");
        harness = await mod.loadRunOverflowCompactionHarness();
      });

    PROBLEMS:
      1. Type annotation invalid: typeof import(...) yields a Promise,
         not a function. ReturnType<Promise<T>> is not valid TypeScript.

      2. Uses dynamic import for the harness module. The EXISTING test
         (run.overflow-compaction.test.ts) uses STATIC imports:
           import { loadRunOverflowCompactionHarness, mockedContextEngine, ... }
           from "./run.overflow-compaction.harness.js";

      3. The test references `mockedMultiPassCompact` directly in EXPECT
         clauses, but with the V4 pattern, this variable would only be
         available as `mod.mockedMultiPassCompact`, not in the test scope.

    VERIFICATION: Direct read of run.overflow-compaction.test.ts confirmed
    static import pattern at lines 25-53.

    CORRECTED: Changed to static imports matching the existing convention.
    The mock variables are imported directly as named exports from the
    harness module. loadRunOverflowCompactionHarness() is called in
    beforeAll to get runEmbeddedAgent.
