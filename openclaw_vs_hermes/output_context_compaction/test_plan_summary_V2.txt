1. EXPLANATION OF THE V2 TEST PLAN
================================================================================

  The V2 test plan is a from-scratch rewrite that incorporates ALL 15
  corrections from the V1 Review iteration. Rather than patching the
  V1 plan, V2 was rebuilt from first principles with every pattern,
  type definition, mock strategy, and shard assignment verified directly
  against the actual OpenClaw codebase via file reads and exploration.

  1.1 SCOPE AND STRUCTURE

    The plan covers 9 test suites (A through I) totaling 106 tests across
    6 new test files, 2 modified test files, and 1 modified harness file.
    Tests are organized to match the 9-step implementation plan from
    code_port_plan_review_V4.txt:

      Suite A: Progress Detection & Anti-Thrashing (18 tests)
        -> Validates Step 2: compressionMadeProgress and shouldContinueMultiPass
        -> Pure functions, zero mocks needed

      Suite B: Pre-Compaction Pruning (22 tests)
        -> Validates Step 3: preCompactionPrune with 3 sub-passes
        -> Pure function, uses shared fixture factories

      Suite C: Cut Point Anchoring (12 tests)
        -> Validates Step 4: findCutPoint user/assistant message anchoring
        -> Uses REAL estimateTokens (char/4), inline helpers matching
           existing compaction test convention

      Suite D: Summary Prefix Disambiguation (6 tests)
        -> Validates Step 5: buildMultiPassSummaryPrefix, buildCompactionEndMarker
        -> Added to existing compaction-safeguard.test.ts via testing export

      Suite E: Multi-Pass Compaction Loop (20 tests)

        -> Mock contextEngine injected as parameter (not vi.mock)

      Suite F: Embedded Runner Integration (7 tests)
        -> Validates Step 7: integration with overflow/preemptive compaction
        -> Extends existing run.overflow-compaction.harness.ts

      Suite G: Configuration Schema Extension (13 tests)
        -> Validates Step 8: Zod schema + applyCompactionDefaults changes
        -> Explicitly tests .strict() constraint and backward compatibility

      Suite H: Compaction-Safeguard Integration (4 tests)
        -> Validates Steps 3+5 integration in compaction-safeguard.ts
        -> Uses existing createCompactionHandler and setSummarizeInStagesForTest

      Suite I: Vertical Integration (4 tests)
        -> Validates full feature interaction across components
        -> Uses same mock infrastructure as Suite E

  1.2 KEY V2 IMPROVEMENTS OVER V1 REVIEW

    IMP-1: ZOD STRICT SCHEMA HANDLING
      The compaction Zod schema uses .strict() which rejects unknown keys.
      Suite G now includes explicit tests for:
        - New fields being accepted (10.9)
        - Invalid types being rejected (10.10, 10.11)
        - Backward compatibility (old configs without new fields: 10.12)
        - Strictness regression (unknown keys still rejected: 10.13)
      V1 Review did not account for the .strict() constraint.

    IMP-2: PRECISE TOKEN ESTIMATION IN SUITE C
      Tests now specify exact character counts mapped to expected token
      values via the char/4 heuristic:
        "x".repeat(80000) = 20000 tokens
        "x".repeat(4000)  = 1000 tokens
        "x".repeat(400)   = 100 tokens
      This ensures deterministic cut point positioning. V1 Review described
      this approach but V2 provides specific character/token mappings.

    IMP-3: VERIFIED TESTING EXPORT CONTENTS
      The compaction-safeguard.ts testing export was verified to contain
      30+ entries (lines 1318-1351). V2 specifies exactly where
      buildMultiPassSummaryPrefix and buildCompactionEndMarker fit within
      the existing export structure.

    IMP-4: VERIFIED compactionSafeguardDeps INJECTION PATTERN
      The summarizeInStages mock uses a module-level deps object
      (compactionSafeguardDeps), not constructor injection. Suite H tests
      follow this exact pattern via testing.setSummarizeInStagesForTest().

    IMP-5: VERIFIED applyCompactionDefaults IMPLEMENTATION
      The current function (defaults.ts:529-552) only sets mode:"safeguard".
      Suite G tests explicitly verify that the function is extended to
      handle maxPasses and minProgressThreshold defaults.

    IMP-6: ALL THREE CompactResult VARIANTS
      Suite E now provides factory functions for all three discriminated
      union variants of CompactResult, and tests each code path:
        makeCompactSuccess: { ok: true, compacted: true, result: {...} }
        makeCompactNotCompacted: { ok: true, compacted: false, reason }
        makeCompactFailure: { ok: false, compacted: false, reason }

    IMP-7: REFINED INLINE HELPERS FOR SUITE C
      The inline helper functions match the exact pattern from
      compaction-trailing-toolresult.test.ts, including ISO timestamp
      conversion, null parentId for first entry, and the HarnessMessage
      type system.

    IMP-8: EXISTING SUMMARY PREFIX PATTERNS REFERENCED
      Suite D references PREVIOUS_SUMMARY_REDISTILL_PREFIX and
      SUMMARY_TRUNCATED_MARKER as design anchors for the new multi-pass
      prefix functions.

  1.3 DESIGN DECISIONS

    D1: PURE FUNCTION TESTING (Suites A, B, C, G)
      Functions with no side effects are tested with real inputs and
      real return values. No mocks. This gives highest confidence and
      simplest test maintenance.

    D2: DEPENDENCY INJECTION TESTING (Suites E, I)
      multiPassCompact receives contextEngine as a parameter. Tests
      inject a mock object directly, matching the run.overflow-compaction
      harness pattern. No vi.mock() needed.

    D3: TESTING EXPORT PATTERN (Suites D, H)
      New internal functions are exposed via the existing testing export
      on compaction-safeguard.ts. Tests import them via
      `import { testing } from "./compaction-safeguard.js"`.

    D4: HARNESS EXTENSION (Suite F)
      New mock (mockedMultiPassCompact) is added to the existing overflow
      compaction harness rather than creating a parallel harness. This
      keeps all overflow-related mocking centralized.

    D5: FIXTURE REUSE OVER CREATION
      New fixture factories (compaction-fixtures.ts) only add genuinely
      new helpers. makeToolResultMessage, makeAssistantWithToolCalls,
      makeAlternatingConversation, and makeConversationWithToolCalls
      have no existing equivalents. All other message construction
      reuses existing factories.

    - Suite F (runner integration): Depends on harness extension that hasn't
      been attempted yet. The harness has 40+ mock exports and a complex
      loading sequence. The extension strategy is sound but implementation
      may reveal additional mocks needed.
    - Suite H (safeguard integration): The pre-pruning injection point
      (line ~965 of compaction-safeguard.ts) is in a complex code path
      with multiple branches. The exact test setup may need adjustment
      based on which branch path is exercised.

  LOWER CONFIDENCE:
    - Specific test values in Suite C (anchoring): The keepRecentTokens
      values needed to produce specific cut points depend on the exact
      token estimation for each message type. While the char/4 formula
      is known, the overhead per message/content block may shift the
      cut point by 1-2 positions. Tests should use assertions like
      `<= expectedIndex` rather than `=== exactIndex`.
