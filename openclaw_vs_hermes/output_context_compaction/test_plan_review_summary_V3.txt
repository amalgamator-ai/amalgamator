  ── FIX-R1: SUITE G MISSING TEST FOR "mode set, maxPasses absent" ──────────

    SEVERITY: Medium (gap in defaults regression coverage)

    V3 TESTED:
      10.1: materializeCompactionConfig({}) → maxPasses=3
      10.3: materializeCompactionConfig({maxPasses:5}) → preserved
      10.5: materializeCompactionConfig({mode:"safeguard",...,maxPasses:2}) → all preserved

    MISSING SCENARIO:
      materializeCompactionConfig({mode:"safeguard"}) → should get maxPasses=3

    WHY THIS MATTERS:
      The CURRENT applyCompactionDefaults (defaults.ts:529-552) has:
        `if (compaction?.mode) return cfg;`
      This early-exits when mode is set, returning the config UNCHANGED.
      The port plan must modify this to per-field defaulting, following the
      pattern used by applyAgentDefaults (defaults.ts:404-450), which checks
      EACH field independently:
        `const hasMax = typeof defaults?.maxConcurrent === "number"...`
        `if (hasMax && hasSubMax && hasSubArchive) return cfg;`

      Without test 10.5a, a regression where the mode-set guard blocks the
      new maxPasses/minProgressThreshold defaults would go undetected.
      This is especially likely because the implementor might only modify
      the block under the `if (!compaction?.mode)` branch, leaving the
      early-exit intact.

    VERIFICATION:
      Direct read of applyCompactionDefaults (defaults.ts:529-552).
      Direct read of applyAgentDefaults (defaults.ts:404-450) for pattern.
      Direct read of config.compaction-settings.test.ts for existing test
      conventions — existing tests cover mode defaulting and field preservation,
      but NOT the interaction between mode-set and new-field defaults.

    CORRECTED: Added test 10.5a. Renumbered 10.5→10.5b.
    Suite G test count: 15 → 16.

  ── FIX-R2: SUITE E baseCompactParams MISSING runtimeContext/runtimeSettings ──

    SEVERITY: Low (optional fields, but real code always passes them)

    V3 STATED:
      const baseCompactParams = {
        sessionId: "test-session",
        sessionKey: "test-key",
        sessionFile: "/tmp/session.jsonl",
        tokenBudget: 100000,
        force: true,
        compactionTarget: "budget" as const,
      };

    ACTUAL compact() CALLS (run.ts lines 2503-2519, 2707-2724):
      All real call sites include runtimeContext and runtimeSettings:
        - Timeout path: runtimeContext: timeoutCompactionRuntimeContext,
                        runtimeSettings: buildEmbeddedContextEngineRuntimeSettings(...)
        - Overflow path: runtimeContext: overflowCompactionRuntimeContext,
                         runtimeSettings: overflowCompactionRuntimeSettings

    IMPACT:
      Both fields are OPTIONAL in ContextEngine.compact() (types.ts:415-416),
      so tests compile without them. However:
      1. If multiPassCompact threads these to each compact() call, tests
         should verify the passthrough (test 8.15 becomes more meaningful)
      2. Mock params should approximate what the real code passes

    CORRECTED: Added runtimeContext: {} and runtimeSettings: {} to
    baseCompactParams. Empty objects satisfy the types for unit testing
    while keeping tests readable. The full complex shapes are tested
    indirectly via Suite F (which uses the real harness with fully-
    populated mocks).

    VERIFICATION:
      Direct read of ContextEngine.compact() type (types.ts:402-423).
      Direct read of compact calls in run.ts (lines 2503-2519, 2707-2724).
      Direct read of compact.queued.ts (lines 404-433) for another call site.

  ── FIX-R3: SUITE E TEST 8.20 SETUP DESCRIPTION INCOMPLETE ────────────────

    SEVERITY: Low (test description, not logic)

    V3 STATED:
      "SETUP: Pass 1: 200000 → 191000 (4.5% reduction — below 5%).
       Do NOT pass minProgressThreshold."
      "EXPECT: After two consecutive sub-threshold passes, anti-thrash
       triggers."

    ISSUE: The EXPECT clause references "two consecutive" passes, but the
    SETUP only describes one pass. An implementor would need to infer the
    second pass's token values.

    CORRECTED: Added explicit Pass 2 setup:
      Pass 1: 200000 → 191000 (4.5% — below threshold, counter=1)
      Pass 2: 191000 → 183000 (4.2% — below threshold, counter=2)

    VERIFICATION: Math check:
      Pass 1: 191000 < 200000 * 0.95 = 190000? → 191000 > 190000 → NO progress ✓
      Pass 2: 183000 < 191000 * 0.95 = 181450? → 183000 > 181450 → NO progress ✓
      Counter reaches 2 → anti-thrash exit ✓

  ── FIX-R4: MultiPassCompactResult TYPE UNDOCUMENTED ───────────────────────

    SEVERITY: Low (documentation gap, not logic error)

    V3 USED:
      passesCompleted field in: 8.1, 8.2, 8.3, 8.6, 8.7, 8.9, 8.10
      passesCompleted in Suite F harness mock (mockedMultiPassCompact)
      passesCompleted in Suite I tests (12.1, 12.3, 12.4)

    V3 DID NOT:
      Define the type that contains passesCompleted.
      CompactResult (types.ts:126-141) does NOT have passesCompleted.

    ISSUE: multiPassCompact returns an EXTENDED type (CompactResult +
    passesCompleted). This distinction matters because:
      1. engine.compact() returns CompactResult
      2. multiPassCompact() returns MultiPassCompactResult
    The mock factories correctly produce CompactResult (for engine.compact
    mocking), while the assertions and harness mock correctly produce the
    extended type. The gap is only in documentation.

    CORRECTED: Added explicit type documentation:
      type MultiPassCompactResult = CompactResult & { passesCompleted: number };
    Added notes distinguishing engine.compact return type from
    multiPassCompact return type in Section 3 (N1) and Suite E/F headers.

    VERIFICATION:
      Direct read of CompactResult type (types.ts:126-141).
      Grep for "passesCompleted" in test plan — used 14 times but never defined.

  ── FIX-R5: SUITE D SOURCE FILE AMBIGUITY ──────────────────────────────────

    SEVERITY: Low (ambiguous import paths)

    V3 STATED:
      "SOURCE: packages/agent-core/src/harness/compaction/compaction.ts (or
       packages/agent-core/src/harness/messages.ts depending on where prefix
       logic is placed)"

    ISSUE: The "or" clause means test imports could be wrong. The test plan
    had two different import sources:
      from "../messages.js"  — existing COMPACTION_SUMMARY_PREFIX/SUFFIX
      from "./compaction.js" — new ENHANCED_*, END_MARKER, wrapCompactionSummary

    This split means constants that conceptually belong together live in
    different files.

    RESOLUTION: All summary prefix/suffix constants belong in messages.ts
    (where the existing ones already live). The wrapCompactionSummary helper
    also belongs there since it only uses those constants.

    CORRECTED: All Suite D imports now reference "../messages.js".
    The "or" clause removed.

    VERIFICATION:
      Direct read of messages.ts — existing COMPACTION_SUMMARY_PREFIX,
      COMPACTION_SUMMARY_SUFFIX, createCompactionSummaryMessage all here.
      Convention: message-related constants live in messages.ts.
