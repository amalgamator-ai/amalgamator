1. EXPLANATION OF THE V4 TEST PLAN
================================================================================

  V4 is a from-scratch rewrite of the test plan, incorporating all learnings
  from 6 prior iterations (V1, V1 Review, V2, V2 Review, V3, V3 Review)
  totaling 27 cumulative corrections, plus the 7 new corrections from the
  Review V4 port plan (RV4-1 through RV4-7). This is the most refined
  iteration to date.

  ── KEY DESIGN DECISIONS ──────────────────────────────────────────────────────

  1. FROM-SCRATCH REBUILD, NOT INCREMENTAL PATCH

     Rather than patching the V3 Review plan, V4 was written from scratch
     with every test case fully specified. This eliminates "[UNCHANGED FROM
     V3]" references that made the V3 Review hard to implement as a standalone
     document. V4 is self-contained: an implementor needs only this file.

  2. PORT PLAN REVIEW V4 CORRECTIONS INTEGRATED

     The Review V4 port plan corrected 7 issues (5 code fixes + 2 refinements).
     V4 incorporates all of these at the test level:

     - RV4-1 (ToolCall field names): Suite B sub-pass 3 tests use id/name
       fields for ToolCall content blocks, NOT toolCallId/toolName. Test
       fixtures (makeAssistantWithToolCalls) use the correct type definition
       from packages/llm-core/src/types.ts:251-258.

     - RV4-2 (ToolCall.arguments type): Suite B sub-pass 3 tests verify
       truncation of Record<string, unknown> values (object-based), NOT
       JSON string parsing. Test 5.17 specifically verifies that non-string
       values (numbers, booleans, arrays) are preserved unchanged.

     - RV4-3 (findCutPoint property path): Suite C test fixtures use
       entry.message.role (via makeMessageEntry helper that nests role inside
       the message object), NOT entry.role. Section 3 (N2) explicitly
       documents the correct SessionTreeEntry structure.

     - RV4-4 (hasVisibleContent property path): Suite C tests 6.5-6.8 verify
       visible content detection via entry.message.content, NOT entry.content.
       The makeMessageEntry helper places content on message.content.

     - RV4-5 (baseMessagesToSummarize mutability): Suite H test 11.3
       verifies that the pre-pruning injection works with the existing `let`
       declaration at line 884, NOT requiring a const-to-let change.

     - RV4-6 (AbortSignal.any()): No special test needed. Verified as a
       non-issue (Node >= 22.19.0 target, already used in 5+ files).

     - RV4-7 (stale compactParams): Suite E test 8.15 documents this known
       limitation. The test verifies that multiPassCompact passes the same
       params snapshot to every pass, which is correct behavior for the
       default in-place compaction mode.

  3. ALL 27 PRIOR CORRECTIONS BAKED IN

     Every correction from the V1-V3R iterations is incorporated as native
     design rather than as a patch:

     Type accuracy:
     - CompactResult flat type (not nested model) — V2R correction
     - MultiPassCompactResult = CompactResult & { passesCompleted } — V3R FIX-R4
     - ToolCall uses id/name — V4 new (from RV4-1)
     - ToolCall.arguments is Record — V4 new (from RV4-2)

     Path/import accuracy:
     - vi.doMock path "../multi-pass-compaction.js" verified — V2R correction
     - Suite D source resolved to messages.ts — V3R FIX-R5
     - Entry property paths use entry.message.role — V4 new (from RV4-3)

     Boundary math:
     - 5% threshold uses strict-less-than (< not <=) — V2R correction
     - Test 8.20 describes both passes explicitly — V3R FIX-R3
     - Test 4.5/4.6 prove the boundary with exact arithmetic — V4 refinement

     Convention alignment:
     - Shard assignments verified against vitest.*.config.ts files
     - runtimeContext/runtimeSettings in baseCompactParams — V3R FIX-R2
     - Defaults don't clamp (Zod + runtime's job) — V2R correction

     Structural completeness:
     - Suite G test 10.5 covers "mode set, maxPasses absent" — V3R FIX-R1
     - Suite H added for compaction-safeguard integration — V1R correction
     - consecutiveNoProgress counter with reset — V2R correction

  4. TEST ARCHITECTURE

     112 tests across 9 suites, organized in a pyramid:

     Unit (75 tests — Suites A, B, C, D, G):
       Pure functions with deterministic inputs and outputs. No async, no
       mocking, fastest execution. These form the foundation.

     Component (26 tests — Suites E, H):
       Single module with injected mock dependencies. Test loop
       orchestration (multiPassCompact) and hook wiring (compaction-safeguard).

     Integration (11 tests — Suites F, I):
       Multi-module with harness-based mocking (vi.doMock + dynamic import).
       Verify end-to-end data flow through the embedded runner.

  5. NEW IN V4 (BEYOND INCORPORATING CORRECTIONS)

     - Test 8.22: Explicit runtimeContext/runtimeSettings passthrough test
       (was implicit in V3R via baseCompactParams; now has its own test)
     - Test 8.15: Documents the stale compactParams limitation (RV4-7)
       as a behavior test, not just documentation
     - Suite B: Complete rewrite of sub-pass 3 tests for object-based
       truncation (RV4-2), including tests for non-string value preservation
       (5.17), immutability (5.18), and mixed content blocks (5.20)
     - Suite C: Explicit property path documentation in Section 3 (N2)
       with makeMessageEntry helper that correctly nests role/content
     - Inline math proofs for every boundary test (comments showing the
       arithmetic, marked with ✓)

4. CONVERGENCE ASSESSMENT
================================================================================

  The plan has been converging across iterations:

    V1 → V1R: 15 issues (many HIGH severity, structural)
    V2 → V2R:  7 issues (2 HIGH, 2 MEDIUM)
    V3 → V3R:  5 issues (1 MEDIUM, 4 LOW)

  The correction severity has dropped monotonically. V3 Review found no
  structural problems — all 5 issues were documentation or completeness gaps.

  V4 builds on this convergence by:
  1. Incorporating corrections from the port plan review (not the test plan
     review), ensuring test plan and implementation plan are aligned
  2. Writing from scratch to eliminate reference chains
  3. Verifying all types, paths, and math against the actual codebase

  The test plan is at a high confidence level. The remaining risk areas are:

  LOW RISK:
  - Exact export names from Zod schema (test 10.8 uses "compactionSchema" —
    the actual export name may differ; verify at implementation time)
  - Suite H mock setup (depends on existing compaction-safeguard.test.ts
    structure, which may change between now and implementation)
  - Shard "unit-support" covering packages/agent-core — assumed from existing
    test files in that directory; verify against vitest workspace config

  VERY LOW RISK:
  - All types verified against actual source (CompactResult, ToolCall,
    SessionTreeEntry, CompactionSettings, HarnessMessage, MessageEntry)
  - All file paths verified against actual directory structure
  - All shard assignments verified against vitest.*.config.ts files
  - All boundary math verified inline with arithmetic proofs
