2. AREAS REVIEWED (VERIFIED CLEAN)

REVIEW ITEM A: Correctness of multi-pass loop vs Hermes original

  The multiPassCompact() implementation faithfully ports Hermes's multi-pass
  loop from agent/turn_context.py:
  - Max 3 iterations (configurable, clamped [1, 10])
  - 5% progress threshold matching Hermes's 0.95 multiplier
  - Anti-thrashing via CompactionProgressTracker (2 consecutive <10%)
  - Per-pass lifecycle (adoptTranscript + runMaintenance)
  - Token-only progress detection (design decision D1: Hermes also checks
    message count, but OpenClaw's multi-pass loop operates at the
    ContextEngine level where message counts aren't directly available;
    any meaningful compaction reducing message count also reduces tokens)
  - tracker.recordCompaction() correctly called per-pass (V3 review fix)

  VERDICT: CORRECT — Faithful port.

REVIEW ITEM B: CompactionSettings optional field backward compatibility

  maxPasses? and progressThreshold? are optional with ? modifier.
  DEFAULT_COMPACTION_SETTINGS omits them (defaults applied by consuming
  code). Existing callers see undefined -> defaults apply. TypeScript
  structural typing ensures backward compatibility.

  VERDICT: CORRECT — Backward compatible.

REVIEW ITEM C: findCutPoint anchoring property paths

  The anchoring code uses (entry.message as HarnessMessage).role,
  matching the existing findValidCutPoints pattern at line 327. The
  guard conditions (lastUserIdx - startIndex >= 3, lastAssistantIdx -
  startIndex >= 3) prevent degenerate cases where anchoring would leave
  nothing to summarize. The safety floor at line 459 applies AFTER both
  anchoring steps, providing a final guarantee. The anchoring is
  monotonic — cutIndex can only decrease (grow the tail), never increase.

  NOTE: The existing cut-point selection algorithm (lines 403-423,
  including the fallback assignment at line 414) is ORIGINAL OpenClaw
  code, not modified by V4. Line 414 sets cutIndex to the last valid
  cut point as a FALLBACK default before the inner loop searches for
  a better candidate. This is correct behavior.

  VERDICT: CORRECT — Property paths match existing patterns.

REVIEW ITEM D: Pre-compaction pruning logic

  Sub-pass 1 (dedup): Hashes ALL tool results to build the last-seen
  map, but only replaces before the boundary. Deduped content is 60
  chars, below MIN_CONTENT_LENGTH (200), so sub-pass 2 correctly
  skips it. No double-counting.

  Sub-pass 2 (summarize): Replaces remaining long tool results with
  1-line summaries. Tool name extraction uses runtime duck-typing
  via `"toolName" in msg` which matches ToolResultMessage's structure.

  Sub-pass 3 (truncate args): Uses ToolCall fields (id, name, arguments
  as Record<string, unknown>) — NOT ToolResultMessage fields (toolCallId,
  toolName). This matches RV4-1/RV4-2 corrections. Object.assign used
  in map callback (V2 fix for no-map-spread lint rule).

  VERDICT: CORRECT — No double-counting, correct field names.

REVIEW ITEM E: Summary prefix change impact

  COMPACTION_SUMMARY_PREFIX uses "[COMPACTION -- REFERENCE ONLY]"
  directive with clear instructions. COMPACTION_SUMMARY_END_MARKER
  provides a boundary. Both exported from messages.ts and available
  via agent-core's wildcard re-export.

  VERDICT: CORRECT — Appropriate adaptation.

REVIEW ITEM F: Configuration defaults integration

  applyCompactionDefaults() applies per-field defaults without
  blocking on the mode guard. The spread `...compaction` where
  compaction may be undefined is valid ES2018+ behavior ({...undefined}
  produces {}). Hardcoded default values (3, 0.05) match the constants
  MAX_COMPACTION_PASSES and PROGRESS_THRESHOLD. Using constants would
  create an undesirable cross-layer dependency from config to
  agent-core.

  VERDICT: CORRECT — No issues.
