1. EXPLANATION OF THE V3 TEST PLAN
================================================================================

  V3 is a from-scratch rewrite of the test plan that incorporates all 22
  corrections discovered across four prior iterations (V1, V1 Review, V2,
  V2 Review). Rather than patch-on-patch corrections, every test case was
  designed from the start with the verified codebase facts baked in.

  KEY CHARACTERISTICS OF V3:

  1. FRESH CODEBASE VERIFICATION

     All type definitions, shard assignments, mock patterns, and file
     conventions were re-verified against the actual OpenClaw codebase
     before writing. Key verifications:

     - CompactResult type (context-engine/types.ts:126-141): confirmed
       flat type with ok: boolean, compacted: boolean
     - ToolCall interface (llm-core/types.ts:251-258): confirmed
       { id, name, arguments: Record<string, unknown> }
     - applyCompactionDefaults (config/defaults.ts:529-552): confirmed
       only sets mode:"safeguard", does NOT clamp values
     - Zod schema (zod-schema.agent-defaults.ts:158-205): confirmed
       .strict() mode, existing field definitions
     - MessageEntry (harness/types.ts:367-370): confirmed
       { type: "message"; message: AgentMessage }
     - Test model convention: "claude-fable-5" in compaction tests
     - Harness vi.doMock paths: "../" prefix for src/agents/ targets
     - testing barrel: compaction-safeguard.ts exports testing object
     - Message factories: agent-message-fixtures.ts with makeAgentUserMessage,
       makeAgentAssistantMessage, ZERO_USAGE_FIXTURE

  2. NO KNOWN CONTRADICTIONS

     V2's critical contradiction between tests 4.15 and 8.17 (where
     shouldContinueMultiPass behavior conflicted with the multi-pass
     loop's tolerance behavior) was resolved at the design level in
     V2 Review. V3 implements this resolution natively:

     - shouldContinueMultiPass takes consecutiveNoProgress (a counter)
     - Counter must reach 2 for anti-thrash exit
     - multiPassCompact maintains the counter, calling
       compressionMadeProgress after each pass to increment/reset it
     - Single marginal pass does NOT stop the loop (intentional
       enhancement over Hermes)

  3. ALL PORT PLAN FIXES COVERED BY TESTS

     Every correction from the port plan (Review V4) has at least one
     test that would FAIL if the fix were reverted:

     - RV4-1 (ToolCall id/name): Tests 5.4, 5.13
     - RV4-2 (Record<> arguments): Tests 5.10-5.12, 5.15
     - RV4-3 (entry.message.role): Tests 6.1, 6.3
     - RV4-4 (entry.message.content): Tests 6.4, 6.5
     - RV4-5 (already let): N/A (no test needed — no code change)
     - RV4-6 (AbortSignal.any()): N/A (non-issue — confirmed)
     - RV4-7 (stale compactParams): Test 8.15

  4. STRUCTURAL IMPROVEMENTS OVER V2

     a) Test count slightly increased: 110 vs 107 (V2 Review).
        +1 test in Suite A (abort priority, test 4.19)
        +2 tests in Suite D (wrapCompactionSummary, tests 7.7-7.8)
        +1 test in Suite E (exception handling, test 8.14; stale params, 8.15)
        +1 test in Suite G (minProgressThreshold at 1.0, test 10.13)
        -2 tests in Suite B (consolidated combined pass tests)

     b) Suite E and Suite I share a test file (multi-pass-compaction.test.ts)
        to reduce file sprawl while maintaining logical separation via
        nested describe blocks.

     c) Suite D expanded to test wrapCompactionSummary utility (tests 7.7-7.8)
        rather than just constant assertions.

     d) Explicit abort priority test (4.19) verifies that abort signal
        is checked FIRST even when other exit conditions are met.

     V1: 107, V1R: 102, V2: 106, V2R: 107, V3: 110
     Range: 102-110 (stable within ~8% band)
     V3 increase (+3 vs V2R) comes from targeted expansions,
     not structural changes.

  5. NO KNOWN OPEN ISSUES: All previously identified contradictions,
     path errors, type mismatches, and convention misalignments have
     been resolved and verified.

  REMAINING RISKS:

  R1: Implementation may discover additional type constraints not
      visible in the type definitions (e.g., runtime validation in
      non-exported functions). Tests may need adjustment.

  R2: The exact API of multiPassCompact (step 6) is not yet
      implemented — the test plan assumes the parameter shape from
      the port plan. Minor adjustments may be needed once the
      function signature is finalized.

  R3: Suite F harness extension assumes the existing harness is
      compatible with the new vi.doMock. If the harness has been
      modified by other PRs, the extension may need rebasing.

  These are implementation-phase risks, not plan-phase issues.
