  FIX-RV4:  TESTS 8.8 AND 8.19 MOCK SETUP CORRECTED TO AVOID ANTI-THRASH
            AMBIGUITY.

            V4 specified for both tests:
              mockEngine.compact always resolves to
              makeCompactSuccess({ tokensAfter: 150000 })

            PROBLEM: makeCompactSuccess defaults tokensBefore to 200000.
            So every call returns tokensBefore=200000, tokensAfter=150000.

            The multi-pass loop tracks progress as:
              Pass 1: origTokens = result.tokensBefore (200000), newTokens = tokensAfter (150000).
                      Progress: 25%. Counter stays 0.
              Pass 2: origTokens = pass 1 tokensAfter (150000), newTokens = 150000.
                      Progress: 0%. Counter = 1.
              Pass 3: origTokens = 150000, newTokens = 150000.
                      Progress: 0%. Counter = 2. Anti-thrash fires.

            Result: loop stops at 3 passes due to ANTI-THRASH (counter=2),
            which COINCIDENTALLY equals maxPasses=3. The tests pass but
            for the WRONG reason. If maxPasses were 10 (or any value >= 3),
            the tests would still pass — anti-thrash, not maxPasses, is
            what actually limits the loop.

            NOTE: This analysis assumes the loop tracks inter-pass progress
            (previous tokensAfter vs current tokensAfter). If the loop uses
            each pass's result.tokensBefore instead, every pass shows 25%
            progress and only maxPasses limits it. But since this is an
            implementation detail, the test should be robust to EITHER
            approach.

            FIX for 8.8: Use .mockResolvedValueOnce() with DECREASING
            tokensAfter values (all above budget), ensuring every pass
            shows sufficient progress (>5%). Only maxPasses limits the loop.

            FIX for 8.19: Same — use decreasing tokensAfter values so that
            ONLY the default maxPasses=3 stops the loop, not anti-thrash.

  FIX-RV5:  TEST 8.21 SPLIT INTO TWO it() BLOCKS.

            V4 specified two test cases in a single it() block:
              CALL 1: multiPassCompact(..., { maxPasses: 50 })
              EXPECT: at most 10 calls
              CALL 2: multiPassCompact(..., { maxPasses: 0 })
              EXPECT: exactly 1 call

            PROBLEM 1: The mock is not reset between calls, so the
            second assertion ("exactly 1 call") would fail — the mock
            shows accumulated calls from BOTH scenarios.

            PROBLEM 2: With the "always returns tokensAfter=150000" mock,
            anti-thrash fires at pass 3, so the first scenario never
            reaches 10 calls. The assertion "at most 10" passes trivially
            (3 calls is indeed <= 10), but doesn't verify the clamping.

            PROBLEM 3: This violates principle P1 (one assertion focus
            per test).

            FIX: Split into two separate it() blocks (8.21a and 8.21b).
            Test 8.21a uses decreasing tokensAfter values to avoid
            anti-thrash and verify the 10-pass maximum clamp.
            Test 8.21b verifies the 1-pass minimum clamp.

  FIX-RV6:  SUITE F TEST SETUP IMPORT PATTERN CORRECTED.

              let harness: Awaited<ReturnType<

                   loadRunOverflowCompactionHarness,

               The harness module's vi.doMock calls execute at module load

               loadRunOverflowCompactionHarness() then dynamically imports
               run.ts and returns { runEmbeddedAgent }.
            3. The test needs to access mockedMultiPassCompact (a top-level

            FIX: Use static imports matching the existing pattern:

                resetRunOverflowCompactionHarnessMocks,

    CHANGE FROM V4 (FIX-RV5): Test 8.21 split into two it() blocks.

    8.21a it("clamps maxPasses to 10 at maximum")
          SETUP: mockEngine.compact resolves in sequence using
                 .mockImplementation() that returns decreasing tokensAfter:
                   Pass N: tokensAfter = 200000 - (N * 5000)
                   i.e., 195000, 190000, 185000, ..., 150000
                 Each pass shows ~2.6% absolute reduction but sufficient
                 relative progress (>5% from the previous pass's after
                 when tokensBefore matches previous tokensAfter).

                 CORRECTION: Use a mock that ALWAYS shows >5% relative
                 progress. For example, each pass reduces by 10%:

                   let callCount = 0;
                   let currentTokens = 200000;
                   mockEngine.compact.mockImplementation(async () => {
                     callCount++;
                     const before = currentTokens;
                     currentTokens = Math.floor(currentTokens * 0.88);
                     return makeCompactSuccess({
                       tokensBefore: before,
                       tokensAfter: currentTokens,
                     });
                   });

                 12% reduction per pass → well above 5% threshold.
                 After 10 passes: 200000 * 0.88^10 ≈ 55,719 (below budget
                 but the mock's tokensAfter is always above budget since
                 we need 10 passes).

                 Actually, simpler: keep all tokensAfter above budget:
                   let callCount = 0;
                   mockEngine.compact.mockImplementation(async () => {
                     callCount++;
                     return makeCompactSuccess({
                       tokensBefore: 200000 - (callCount - 1) * 5000,
                       tokensAfter: 200000 - callCount * 5000,
                     });
                   });
                 Passes: 200→195, 195→190, ..., 155→150. Each is ~2.6%.
                 This is BELOW 5% threshold. Anti-thrash would fire.

                 USE INSTEAD:
                   mockEngine.compact.mockImplementation(async () => {
                     callCount++;
                     const before = 200000 - (callCount - 1) * 8000;
                     const after = before - Math.ceil(before * 0.06);
                     return makeCompactSuccess({ tokensBefore: before, tokensAfter: after });
                   });
                 6% reduction per pass — above 5% threshold.

                 Alternatively, the simplest correct approach:
                   Use a single mock that always reports tokensBefore=200000,
                   tokensAfter=150000 (25% reduction). With method A
                   (progress from result.tokensBefore), every pass shows
                   25% progress. With method B (inter-pass tracking),
                   pass 2 shows 0% because prev-tokensAfter=150000 and
                   new-tokensAfter=150000. This is the same ambiguity as
                   FIX-RV4.

                   Safest: use the implementation-agnostic mock where each
                   pass's tokensBefore = previous pass's tokensAfter, with
                   >5% reduction each time.

          CALL: multiPassCompact(mockEngine, baseCompactParams, { maxPasses: 50 })
          EXPECT: mockEngine.compact called exactly 10 times (clamped from 50 to 10)
