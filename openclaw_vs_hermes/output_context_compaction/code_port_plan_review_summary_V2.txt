ISSUE #1: shouldCompact DYNAMIC IMPORT IS NON-IDIOMATIC

  Affected: Step 6, line 1194 of V2 plan

  What V2 says:
    const { shouldCompact } = await import("@openclaw/agent-core");

  What's wrong: OpenClaw has NO precedent for dynamic imports of
  @openclaw/agent-core. All existing gateway-layer usage of agent-core
  functions uses top-level static imports. Verified:
    - src/agents/sessions/agent-session.ts: top-level import of shouldCompact
    - All dynamic imports found in the codebase are for LOCAL modules
      (same repository), not for the agent-core package
    - Dynamic imports have per-invocation overhead and break tree-shaking

  Why it matters: Non-idiomatic code that deviates from OpenClaw
  conventions. While functionally correct, it adds unnecessary runtime
  cost inside a loop that may run up to 3 times.

  Fix: Move to a top-level static import:
    import { shouldCompact } from "@openclaw/agent-core";


ISSUE #2: PRE-PRUNING INJECTION REFERENCES UNDECLARED VARIABLES

  Affected: Step 3, lines 715-733 of V2 plan

  What V2 says: "Add pre-pruning call approximately after line 889"
  with code referencing `runtime?.prePruningEnabled` and
  `recentTurnsPreserve * 4`.

  What's wrong: At line 889 in compaction-safeguard.ts, NEITHER of
  these variables is declared:
    - `runtime` is declared at line 940
    - `recentTurnsPreserve` is resolved at line 952
  Inserting code at line 889 that references these variables would cause
  a TypeScript compilation error (ReferenceError at runtime if somehow
  the TS compiler didn't catch it).

  Verification path: The compaction-safeguard hook flow was verified
  line-by-line. Between line 884 (stripRuntimeContextCustomMessages)
  and line 952 (recentTurnsPreserve), the setup section at lines
  930-960 resolves runtime (line 940), recentTurnsPreserve (line 952),
  and other variables. The plan's insertion point is ~60 lines too early.

  Why it matters: The code would not compile. This is a BLOCKING issue.

  Fix: Move injection point to approximately line 960 — after both
  `runtime` (line 940) and `recentTurnsPreserve` (line 952) are
  resolved, but before the provider path at line 970. Both provider
  and LLM paths then benefit from smaller pruned inputs.


ISSUE #3: TOOL CALL CONTENT BLOCK TYPE NAME WRONG

  Affected: Step 3, Sub-Pass 3 (lines 679-686 of V2 plan)

  What V2 says: "For each tool_use content block (type === 'tool_use')"

  What's wrong: OpenClaw's ToolCall interface uses `type: "toolCall"`,
  NOT `type: "tool_use"`. Verified from:
    packages/llm-core/src/types.ts, lines 250-258:
      interface ToolCall {
        type: "toolCall";  ← NOT "tool_use"
        id: string;
        name: string;
        arguments: Record<string, unknown>;
      }

  Also verified: OpenClaw internally supports MULTIPLE variant names
  ("toolCall", "toolUse", "functionCall") via a Set in tool-call-id.ts,
  but the canonical type in the interface definition is "toolCall".

  Why it matters: Sub-pass 3 (tool call argument truncation) would
  silently skip ALL tool call blocks, making the entire sub-pass
  non-functional. No errors, just zero truncation.

  Fix: Use `type === "toolCall"` in the content block check.


ISSUE #4: ToolResultMessage FIELD NAME WRONG

  Affected: Step 3, Sub-Pass 2 (lines 662-677 of V2 plan)

  What V2 says: "ToolResultMessage has: { role: 'toolResult', tool_use_id,
  content }" and "Find the corresponding assistant message (walking
  backward) that contains a tool_use block with matching id"

  What's wrong: OpenClaw's ToolResultMessage uses `toolCallId`, NOT
  `tool_use_id`. Verified from:
    packages/llm-core/src/types.ts, lines 306-314:
      interface ToolResultMessage {
        role: "toolResult";
        toolCallId: string;  ← NOT tool_use_id
        toolName: string;    ← also available directly
        content: (TextContent | ImageContent)[];
        isError: boolean;
        timestamp: number;
      }

  Why it matters: Matching tool results to their assistant tool calls
  would always fail (property undefined → no match found → no pruning).
  Sub-pass 2 would be non-functional.

  Fix: Use `msg.toolCallId` for the ID field. Also use `msg.toolName`
  directly instead of walking backward (see Issue #8).


ISSUE #5: ToolCall ARGUMENTS FIELD NAME WRONG

  Affected: Step 3, Sub-Pass 3 (lines 681-686 of V2 plan)

  What V2 says: "Serialize input to JSON", "Deep-clone the input object",
  "Replace the content block's input with the truncated clone"

  What's wrong: OpenClaw's ToolCall interface uses `arguments`, NOT
  `input`. Verified from:
    packages/llm-core/src/types.ts, lines 250-258:
      interface ToolCall {
        type: "toolCall";
        id: string;
        name: string;
        arguments: Record<string, unknown>;  ← NOT input
      }

  Why it matters: Accessing `block.input` on a ToolCall would return
  undefined. The serialized length check would always be 0, and no
  truncation would occur.

  Fix: Use `block.arguments` throughout Sub-Pass 3. Serialize
  `block.arguments` to JSON, deep-clone `block.arguments`, truncate
  string values in the clone, replace `block.arguments` with the result.


──── MODERATE ISSUES (1) — Would cause incorrect runtime behavior ──────────

ISSUE #6: TIMEOUT PATH POST-COMPACTION CODE NOT EXPLICITLY PRESERVED

  Affected: Step 7, Call Site 1 (lines 1354-1426 of V2 plan)

  What V2 says: "REPLACE WITH: ... PRESERVE: runOwnsCompactionAfterHook
  at line 2533 still fires once with the timeoutCompactResult"

  What's wrong: The timeout path's existing post-compaction block
  (lines 2534-2550 in run.ts) includes three critical operations that
  V2 does not mention preserving:
    1. lastCompactionTokensAfter update (line 2541)
    2. runPostCompactionSideEffects (lines 2544-2549, for ownsCompaction)
    3. Post-compaction guard arming and continue statement

  Verified from actual source: After runOwnsCompactionAfterHook at
  line 2533, the code checks if (timeoutCompactResult.compacted) and
  performs these operations. If they are inadvertently removed during
  the replacement, the timeout path would:
    - Lose token tracking (lastCompactionTokensAfter not updated)
    - Skip side effects for context engines with ownsCompaction=true
    - Potentially not continue the retry loop correctly

  Why it matters: Token tracking regression and potential context engine
  state inconsistency for the timeout recovery path.

  Fix: Explicitly list ALL preserved post-compaction code:
    - REMOVE: only adoptCompactionTranscript at line 2531
    - PRESERVE: runOwnsCompactionAfterHook (line 2533)
    - PRESERVE: lastCompactionTokensAfter update (line 2541)
    - PRESERVE: runPostCompactionSideEffects (lines 2544-2549)
    - PRESERVE: post-compaction guard arming and continue


──── MINOR ISSUES (2) — Dead code or missed optimization ───────────────────

ISSUE #7: REDUNDANT ANTI-THRASHING CHECK AT END OF LOOP

  Affected: Step 6, lines 1204-1209 of V2 plan

  What V2 says:
    // ── Anti-thrashing check for next pass ──
    if (!tracker.shouldAttemptCompaction()) {
      return buildResult(passes, lastCompactResult, "anti_thrash", startTime);
    }

  What's wrong: The tracker's recordCompaction() is NOT called inside
  the loop — by design, the CALLER records overall effectiveness after
  the loop returns (see D7 in V2). Since the tracker state doesn't
  change within the loop, tracker.shouldAttemptCompaction() at line
  1207 always returns the same value as the gate at line 1067.

  This is dead code. Not harmful, but confusing — it implies the
  tracker might be updated mid-loop.

  Why it matters: Code maintainability. A future reader might waste
  time understanding why this check is here.

  Fix: Remove the redundant check. Add a comment at the gate
  explaining it covers the entire invocation.


ISSUE #8: ToolResultMessage.toolName SIMPLIFIES SUMMARIZATION

  Affected: Step 3, Sub-Pass 2 (lines 672-676 of V2 plan)

  What V2 says: "Find the corresponding assistant message (walking
  backward) that contains a tool_use block with matching id" to
  extract the tool name.

  What's wrong: ToolResultMessage already has a `toolName: string`
  field. Walking backward through assistant messages to find the
  tool name is unnecessary when it's directly available on the
  tool result message.

  The backward walk IS still needed for extracting tool INPUT
  (the arguments passed to the tool call), which IS only available
  on the assistant message's ToolCall block. But the tool name itself
  can be read directly.

  Why it matters: Unnecessary complexity and potential for bugs in
  the backward-walk logic. Direct field access is simpler and faster.

  Fix: Use msg.toolName directly. Only fall back to backward walk
  for extracting the tool's input arguments (for richer summaries).
  If the arguments can't be found (no matching assistant message),
  pass an empty object as the input — the summarizeToolResult()
  function handles missing inputs gracefully.
