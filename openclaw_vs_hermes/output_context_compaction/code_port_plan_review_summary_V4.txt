──── SIGNIFICANT ISSUES (2) — Would cause TypeScript compilation or runtime failures ────

ISSUE #1: ToolCall FIELD NAMES WRONG

  Affected: Step 3, sub-pass 3 (truncate tool call arguments) and sub-pass 4

  What V4 says:
    Content block: { type: "toolCall", toolCallId, toolName, arguments }

  What the actual type is (packages/llm-core/src/types.ts:251-258):
    export interface ToolCall {
      type: "toolCall";
      id: string;                       // NOT toolCallId
      name: string;                      // NOT toolName
      arguments: Record<string, unknown>;
      thoughtSignature?: string;
      executionMode?: "sequential" | "parallel";
    }

  Why V4 got this wrong:
    V4 incorporated lessons L25 (ToolResultMessage.toolCallId) and L29
    (ToolResultMessage.toolName) from the V2 review. These are the
    CORRECT field names for ToolResultMessage. But V4 then applied these
    same field names to ToolCall content blocks in assistant messages,
    which are a DIFFERENT type with DIFFERENT field names.

    ToolResultMessage: { toolCallId, toolName }  ← correct
    ToolCall:          { id, name }               ← V4 got this wrong

  Verification path:
    - packages/llm-core/src/types.ts line 251: ToolCall interface
    - Field "id: string" at line 253
    - Field "name: string" at line 254
    - Field "arguments: Record<string, unknown>" at line 255

  Why it matters: Accessing tc.toolCallId and tc.toolName on a ToolCall
  object would return undefined, silently producing wrong results. TypeScript
  would catch this at compile time because the fields don't exist on the
  ToolCall interface.

  Fix: Use id, name for ToolCall content blocks. Reserve toolCallId,
  toolName for ToolResultMessage.


ISSUE #2: ToolCall.arguments IS Record<string, unknown>, NOT string

  Affected: Step 3, sub-pass 3 (truncate tool call arguments)

  What V4 says:
    "If ToolCall.arguments is a string > 500 chars:
     a. Parse as JSON
     b. Truncate string values > 200 chars (keep head + "...[truncated]")
     c. Re-serialize
     d. On JSON parse failure: truncate raw string with head + "...[truncated]""

  What the actual type is:
    arguments: Record<string, unknown>

  Why V4 got this wrong:
    This is a direct translation artifact from Hermes. In Hermes (Python),
    tool call arguments are stored as a JSON string:
      tc.get("function", {}).get("arguments", "")
    V4 ported the string-based logic directly without adapting to OpenClaw's
    already-parsed representation.

  Why it matters:
    - Checking string.length > 500 on a Record would always return false
      (typeof check would fail)
    - JSON.parse() on an already-parsed object would no-op (it's already an object)
    - The entire sub-pass 3 would be inert

  Fix: Adapt to object-based truncation:
    a. Estimate size: JSON.stringify(tc.arguments).length > 500
    b. Walk the object's values recursively
    c. For string values > 200 chars: replace with truncated version
    d. Return a new Record (no JSON parse/re-serialize needed)


──── MODERATE ISSUES (2) — Would cause incorrect behavior ──────────────────────

ISSUE #3: findCutPoint ANCHORING USES WRONG PROPERTY PATH

  Affected: Step 4 (cut point enhancement, user/assistant anchoring)

  What V4 says:
    const lastUserIdx = findLastIndex(entries, startIndex, cutIdx,
      (e) => e.type === "message" && "role" in e && e.role === "user");

  What the actual type structure is:
    MessageEntry = { type: "message"; message: AgentMessage }

    The entry itself has NO `role` field. The role is nested:
      entry.message.role  (not  entry.role)

  Existing code pattern (findValidCutPoints, line 323):
    const role = (entry.message as HarnessMessage).role;

  Existing code pattern (findCutPoint, line 431):
    cutEntry.type === "message" && cutEntry.message.role === "user"

  Why it matters: The predicate `"role" in e` would return false for every
  MessageEntry because `role` is not a direct property of the entry — it's
  on `entry.message`. The anchoring would NEVER match any entries, making
  it a complete no-op.

  Fix: Use entry.message to access the role:
    entry.type === "message" && (entry.message as HarnessMessage).role === "user"


ISSUE #4: hasVisibleContent HELPER ACCESSES WRONG PROPERTY PATH

  Affected: Step 4 (cut point enhancement, assistant message anchoring)

  What V4 says:
    function hasVisibleContent(entry: SessionTreeEntry): boolean {
      if (entry.type !== "message") return false;
      const msg = entry as any;
      if (!msg.content) return false;   // ← checks entry.content
      ...

  What the actual type structure is:
    MessageEntry = { type: "message"; message: AgentMessage }

    The content array is on entry.message.content, not entry.content.
    The entry itself has: type, id, parentId, timestamp, appendMode?
    It does NOT have a content field.

  Why it matters: `msg.content` would always be undefined (the entry has
  no content field), causing hasVisibleContent to always return false. The
  assistant message anchoring would never match any entries.

  Fix: Access content through the message:
    const msg = (entry as MessageEntry).message;
    const content = (msg as any).content;


──── MINOR ISSUE (1) — Incorrect documentation, no functional impact ───────────

ISSUE #5: baseMessagesToSummarize IS ALREADY `let`, NOT `const`

  Affected: Step 3 (compaction-safeguard.ts modification)

  What V4 says:
    "VARIABLE MUTABILITY: baseMessagesToSummarize is currently declared with
     `const`. It must be changed to `let` to allow reassignment after pruning."

  What the actual code is (compaction-safeguard.ts line 884):
    let baseMessagesToSummarize = stripRuntimeContextCustomMessages(
      preparation.messagesToSummarize,
    );
    // ... and reassigned at line 898:
    baseMessagesToSummarize = branchMessages;

  Why it matters: The instruction to change const to let would confuse
  implementors, as the variable is already `let`. Applying the instruction
  literally would produce no change (let to let). At worst, an implementor
  might worry they're looking at the wrong variable.

  Fix: Remove the const→let instruction. Note that it's already let.


──── REFINEMENTS (2) — Non-issues or documentation improvements ────────────────

REF-1: AbortSignal.any() RISK DOWNGRADED

  V4 listed this as a Low-Medium risk. Actual: OpenClaw targets Node >= 22.19.0
  (package.json engines field). AbortSignal.any() is supported since Node 22.10.0
  and is already used in 5+ files across the codebase. This is not a risk.

REF-2: STALE compactParams ON SESSION ROTATION

  multiPassCompact passes the same compactParams snapshot to every pass.
  If a context engine plugin rotates sessions between passes, subsequent
  passes would reference stale sessionId/sessionFile values. For the default
  in-place compaction this is a non-issue. Documented as a known limitation
  with maxPasses=1 as an escape hatch for rotation plugins.

  prevented all the issues from V1-V3 from recurring. The NEW issues
  found in Review V4 fall into two categories:

    Category A: TYPE FIELD CONFUSION (Issues #1, #2)
      V4 correctly learned that ToolResultMessage uses toolCallId/toolName
      (lessons L25, L29 from V2 Review). But it then INCORRECTLY applied
      these same field names to ToolCall content blocks, which have
      different field names (id/name). This is a cross-type confusion
      error — the lessons were correct but over-applied.

      Additionally, V4 ported Hermes's string-based arguments handling
      directly without noticing that OpenClaw's ToolCall.arguments is
      already a parsed Record<string, unknown>, not a JSON string. This
      is a language-translation artifact.

    Category B: NESTED TYPE ACCESS (Issues #3, #4)
      V4 correctly identified that SessionTreeEntry and MessageEntry are
      the relevant types. But the anchoring code accessed properties
      directly on the entry (entry.role, entry.content) instead of
      through the nested message (entry.message.role, entry.message.content).
      This is a nesting-depth error — the code looked one level too shallow.

  Both categories represent translation-level issues (Python→TypeScript
  type system differences) rather than architectural issues. The overall
  architecture, type placement, variable scoping, and lifecycle design
  from V4 are all confirmed correct.
