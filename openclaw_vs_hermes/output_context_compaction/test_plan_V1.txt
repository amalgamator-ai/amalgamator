1. TESTING STRATEGY OVERVIEW
================================================================================

  FRAMEWORK:     Vitest (matches OpenClaw's existing test infrastructure)
  RUNNER CONFIG: Existing vitest shard configs; new tests slot into
                 vitest.agents-core.config.ts and vitest.agents-support.config.ts
  CO-LOCATION:   Test files placed adjacent to source files (OpenClaw convention)
  NAMING:        {module}.test.ts for unit/integration,
                 {module}.e2e.test.ts for end-to-end
  MOCKING:       vi.hoisted() for module-level mocks, vi.fn() for function stubs,
                 vi.mock() with vi.importActual() for partial module overrides

  COVERAGE GOALS:
    - Every new exported function has at least one happy-path and one error test
    - Every Hermes regression test that has a corresponding concept in the port
      has a mapped test case in OpenClaw
    - Every corrected property path (FIX-1 through FIX-5 in Review V4) has an
      explicit assertion verifying the correct path
    - Configuration defaults and boundary values are tested
    - Abort/timeout propagation is tested at every async boundary

  DESIGN PRINCIPLES:
    DP-1: Test behavior, not implementation. Mock at module boundaries
          (LLM calls, token estimation, session I/O), not internal helpers.
    DP-2: Use OpenClaw's existing fixture factories (makeAgentAssistantMessage,
          makeAgentUserMessage, castAgentMessage) wherever possible.
    DP-3: Token estimation mocks return deterministic values based on content
          length (length/4 heuristic), matching compaction-partial-summary.test.ts
          and compaction-safeguard.test.ts patterns.
    DP-4: Each test suite is independently runnable.
    DP-5: No external service dependencies. All LLM calls are mocked.

    4.6 it("returns true when messages grew but tokens dropped significantly")
        WHAT: Token reduction trumps message count increase.
        INPUT:  { messagesBefore: 50, messagesAfter: 55,
                  tokensBefore: 100000, tokensAfter: 60000 }
        EXPECT: true
        HERMES: test_rows_grew_but_tokens_dropped_is_progress

    4.7 it("returns true when tokens grew but messages dropped significantly")
        WHAT: Message reduction alone is sufficient.
        INPUT:  { messagesBefore: 50, messagesAfter: 25,
                  tokensBefore: 100000, tokensAfter: 110000 }
        EXPECT: true
        HERMES: test_tokens_grew_but_rows_dropped_is_progress

    4.8 it("returns false when token reduction is below 5% threshold")
        WHAT: Sub-5% token drop is noise, not signal. Tests both 3% (no)
              and 6% (yes) to verify the material floor.
        INPUT A: { tokensBefore: 100000, tokensAfter: 97000,
                   messagesBefore: 50, messagesAfter: 50 }
        EXPECT A: false (3% drop)
        INPUT B: { tokensBefore: 100000, tokensAfter: 94000,
                   messagesBefore: 50, messagesAfter: 50 }
        EXPECT B: true (6% drop)
        HERMES: test_sub_5pct_token_drop_is_not_progress

    4.9 it("returns false when original tokens are zero (degenerate)")
        WHAT: Zero-token baseline must not be read as a win.
        INPUT:  { tokensBefore: 0, tokensAfter: 0,
                  messagesBefore: 0, messagesAfter: 0 }
        EXPECT: false
        HERMES: test_zero_orig_tokens_is_not_progress

    4.10 it("respects custom minProgressThreshold")

         INPUT:  { tokensBefore: 100000, tokensAfter: 92000,
