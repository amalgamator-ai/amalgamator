  ── FIX-T1: TEST 4.12 BOUNDARY MATH ERROR CORRECTED ────────────────────────────

    SEVERITY: Medium (wrong expected value would make the test incorrect)

    V2 STATED:
      NOTE: Hermes uses `new_tokens < orig_tokens * 0.95` which means
      exactly 5% reduction (950 out of 1000) returns true.

    ACTUAL:
      `950 < 1000 * 0.95` = `950 < 950` = FALSE.
      The strict `<` operator means exactly 5% reduction does NOT count
      as progress. You need MORE than 5% (e.g., 949/1000 = 5.1%).

    CORRECTED:
      Test 4.12 now expects:
        compressionMadeProgress(10, 10, 1000, 950) → false
        compressionMadeProgress(10, 10, 1000, 949) → true
      The NOTE text was corrected to state "returns false."

    VERIFICATION:
      Hermes code trace line 198:
        `return orig_tokens > 0 and new_tokens < orig_tokens * 0.95`
      950 < 950 is unambiguously false in both Python and TypeScript.

  ── FIX-T5: SUITE G CLAMPING LOCATION CLARIFIED ────────────────────────────────

    SEVERITY: Medium (wrong test expectations for defaults function behavior)

    V2 STATED:
      Test 10.5: materializeCompactionConfig({ maxPasses: 0 })
                 → result.maxPasses === 1 (clamped)
      Test 10.6: materializeCompactionConfig({ minProgressThreshold: 0 })
                 → result.minProgressThreshold === 0.01 (clamped)

    ACTUAL: applyCompactionDefaults (defaults.ts:529-552) ONLY sets
    missing defaults. It does NOT clamp values. The function:
      1. Returns unchanged if no `agents.defaults` block
      2. Returns unchanged if `compaction.mode` already set
      3. Otherwise sets `mode: "safeguard"` — nothing else

    No existing defaults function in OpenClaw clamps values. The
    convention is:
      Layer 1: Zod schema `.min()/.max()` REJECTS out-of-range input
      Layer 2: Runtime code clamps as safety measure

    CORRECTED:
      - Tests 10.5/10.6 (clamping in defaults) → REMOVED from defaults section
      - NEW tests 10.10/10.11/10.12 added to Zod schema section for range
        REJECTION (not clamping)
      - Suite E test 8.20 retained for runtime clamping (belt-and-suspenders)
      - Suite G test count: 13 → 14 (net +1 from restructuring)

    VERIFICATION: Direct read of applyCompactionDefaults implementation
    and existing Zod schema patterns (recentTurnsPreserve uses
    z.number().int().min(0).max(12) which rejects, not clamps).

  ── FIX-T6: TESTS 4.15 AND 8.16/8.17 CONTRADICTION RESOLVED ───────────────────

    SEVERITY: High (contradictory test expectations in core multi-pass logic)

    V2 STATED:
      Test 4.15: shouldContinueMultiPass with progressMade=false
                 → { continue: false, reason: "no_progress" }
      Test 8.17: Multi-pass loop CONTINUES after first sub-5% pass
                 (only stops after 2 consecutive)

    CONTRADICTION: If shouldContinueMultiPass returns false on ANY
    no-progress pass (test 4.15), then the loop in multiPassCompact
    would stop immediately — making it impossible for test 8.17 to see
    the loop continue past a marginal pass.

    DESIGN RESOLUTION:
      shouldContinueMultiPass does NOT receive `progressMade` directly.
      Instead, the caller (multiPassCompact) maintains a
      `consecutiveNoProgress` counter:
        - After each pass: call compressionMadeProgress
        - If false: counter++
        - If true: counter = 0
        - Pass counter to shouldContinueMultiPass

      shouldContinueMultiPass checks:
        1. abortSignal → false, "aborted"
        2. passNumber >= maxPasses → false, "max_passes_reached"
        3. tokensAfter <= targetTokens → false, "target_reached"
        4. consecutiveNoProgress >= 2 → false, "anti_thrash"
        5. Otherwise → true

      This matches tests 8.16/8.17 (loop continues past one marginal
      pass) and is an INTENTIONAL enhancement over Hermes (which stops
      immediately). The enhancement gives the compactor a second chance
      when a pass makes marginal progress.

    CORRECTED:
      - Old test 4.15 (progressMade=false → continue: false): REPLACED
        with new 4.15 (consecutiveNoProgress=1 → continue: true)
      - Test 4.18 (consecutiveNoProgress=2 → continue: false): unchanged
      - Tests 8.16/8.17: no change needed (they were correct; it was
        4.15 that contradicted them)
      - `progressMade` field removed from shouldContinueMultiPass params;
        replaced by `consecutiveNoProgress: number`

    SEVERITY: Low (convention divergence)

      function materializeCompactionConfig(

          agents: { defaults: { compaction } },
        });

    The existing test uses proper type narrowing via NonNullable<>,
    avoiding the `as any` escape hatch. The parameter type ensures
    only valid compaction fields can be passed.

    CORRECTED: Suite G now uses the existing type pattern with
    NonNullable<>. Also imports `OpenClawConfig` from `"./types.js"`
    matching the existing test's import pattern.
