1. ARCHITECTURE OVERVIEW
================================================================================

OpenClaw's compaction system is split across TWO layers:

  ┌──────────────────────────────────────────────────────────┐
  │ LAYER 1: Agent Core SDK (packages/agent-core/)           │
  │   Portable, platform-independent compaction primitives   │
  │   - shouldCompact()  — threshold check                   │
  │   - prepareCompaction() — cut point & message extraction │
  │   - compact() — single-pass summary generation           │
  │   - estimateTokens() — char-based heuristic              │
  │   File: packages/agent-core/src/harness/compaction/      │
  ├──────────────────────────────────────────────────────────┤
  │ LAYER 2: Gateway / Embedded Runner (src/agents/)         │
  │   Platform-specific orchestration & error recovery       │
  │   - Preemptive overflow detection before prompt          │
  │   - Post-turn overflow & timeout recovery (retry loop)   │
  │   - compaction-safeguard hook (LLM summary quality)      │
  │   - Context pruning (cache-TTL based tool result trim)   │
  │   - Safety timeout wrapper (180s default)                │
  │   File: src/agents/embedded-agent-runner/                │
  ├──────────────────────────────────────────────────────────┤
  │ LAYER 3: Context Engine Plugin Interface                 │
  │   Pluggable contract for external context management     │
  │   - Engines can own compaction lifecycle                  │
  │   - bootstrap → ingest → assemble → compact → afterTurn  │
  │   File: src/context-engine/types.ts                      │
  └──────────────────────────────────────────────────────────┘

  Agent Harness (packages/agent-core/src/harness/agent-harness.ts)
  provides a public compact() method but does NOT auto-trigger.
  Auto-compaction is orchestrated by the embedded runner (Layer 2).

2. ENTRY POINTS & TRIGGER CHAIN
================================================================================

There are FOUR trigger paths for compaction:

─── PATH A: Pre-Prompt Preemptive Compaction ──────────────────────────────────

  File: src/agents/embedded-agent-runner/run/preemptive-compaction.ts
  File: src/agents/embedded-agent-runner/run/attempt.ts (line ~4605)

  BEFORE each LLM API call, the runner estimates token pressure:

    1. Call shouldPreemptivelyCompactBeforePrompt({
         messages, systemPrompt, prompt,
         contextTokenBudget, reserveTokens, ...
       })

    2. Estimates token pressure from:
       - Transcript messages (walk all messages)
       - System prompt
       - Current user prompt
       - Multiplied by SAFETY_MARGIN (1.2)

    3. Computes overflow:
       overflowTokens = estimatedPromptTokens - promptBudgetBeforeReserve
       where promptBudgetBeforeReserve = contextTokenBudget - effectiveReserveTokens

    4. Routes to one of:
       - "fits" → proceed normally
       - "compact_only" → set preflightRecovery, skip prompt submission
       - "truncate_tool_results_only" → truncate, don't compact
       - "compact_then_truncate" → compact first, then truncate

    5. If shouldCompact:
       - Sets promptError = "Context overflow: prompt too large (precheck)"
       - Sets skipPromptSubmission = true
       - Attempt returns with preflightRecovery set

─── PATH B: Post-Turn Overflow Recovery ───────────────────────────────────────

  File: src/agents/embedded-agent-runner/run.ts (lines ~2585–2878)

  After a failed API call, the runner detects context overflow errors:

    1. isLikelyContextOverflowError() checks the error text
    2. If overflow detected AND overflowCompactionAttempts < 3:
       - Increment overflowCompactionAttempts
       - Call compactContextEngineWithSafetyTimeout(contextEngine, params, timeout)
       - If compacted: adoptCompactionTranscript(), continue retry loop
    3. If all 3 attempts exhausted → return terminal error

─── PATH C: Timeout-Based Compaction ──────────────────────────────────────────

  File: src/agents/embedded-agent-runner/run.ts (lines ~2426–2555)

  When the LLM times out and context usage is high:

    1. Detect timeout (timedOut flag)
    2. Check tokenUsedRatio > 0.65 (65% of context window)
    3. If timeoutCompactionAttempts < 2:
       - Increment timeoutCompactionAttempts
       - Call compactContextEngineWithSafetyTimeout()
       - If compacted: continue retry loop
    4. If 2 attempts exhausted → return timeout error

─── PATH D: Manual /compact Command ──────────────────────────────────────────

  File: packages/agent-core/src/harness/agent-harness.ts (lines ~808–885)

  Direct invocation via harness.compact(customInstructions):
    1. Validates harness is "idle"
    2. Sets phase to "compaction"
    3. prepareCompaction() with DEFAULT_COMPACTION_SETTINGS
    4. Fires session_before_compact hook (can cancel or override)
    5. Calls compact() from compaction module (unless hook provided result)
    6. Persists CompactionEntry to session storage
    7. Fires session_compact hook (notification only)
    8. Returns CompactionResult

  Also: src/agents/command/cli-compaction.ts for CLI binding

─── RETRY LOOP STRUCTURE ─────────────────────────────────────────────────────

  File: src/agents/embedded-agent-runner/run.ts

  while (true) {
    if (runLoopIterations >= MAX_RUN_LOOP_ITERATIONS) break;
    runLoopIterations++;

    // Execute attempt (may trigger preemptive compaction internally)
    const attemptResult = await runAttempt(...);

    // Handle preemptive compaction result
    if (preflightRecovery?.handled) continue;  // retry

    // Handle timeout with high context usage
    if (timedOut && tokenUsedRatio > 0.65 && timeoutCompactionAttempts < 2) {
      await compactContextEngineWithSafetyTimeout(...);
      continue;  // retry
    }

    // Handle overflow error
    if (contextOverflowError && overflowCompactionAttempts < 3) {
      await compactContextEngineWithSafetyTimeout(...);
      continue;  // retry
    }

    // If all retries exhausted → return error
  }

  Constants:
    MAX_OVERFLOW_COMPACTION_ATTEMPTS = 3
    MAX_TIMEOUT_COMPACTION_ATTEMPTS = 2

3. COMPACTION DECISION LOGIC
================================================================================

─── AGENT-CORE shouldCompact() ────────────────────────────────────────────────

  File: packages/agent-core/src/harness/compaction/compaction.ts (lines 236–245)

  function shouldCompact(
    contextTokens: number,
    contextWindow: number,
    settings: CompactionSettings,
  ): boolean {
    if (!settings.enabled) return false;
    return contextTokens > contextWindow - settings.reserveTokens;
  }

  This is a SIMPLE threshold check — no anti-thrashing, no progress tracking.

─── GATEWAY PREEMPTIVE CHECK ──────────────────────────────────────────────────

  File: src/agents/embedded-agent-runner/run/preemptive-compaction.ts (lines 248–329)

  function shouldPreemptivelyCompactBeforePrompt(params):
    1. Estimate token pressure from messages + system prompt + prompt
    2. Apply SAFETY_MARGIN (1.2x)
    3. Compute effective reserve tokens (min-capped at MIN_PROMPT_BUDGET)
    4. Compute overflow = estimated - (budget - reserve)
    5. If overflow > 0, evaluate tool-result reduction potential
    6. Route: "fits" | "compact_only" | "truncate_tool_results_only" | "compact_then_truncate"

  Token estimation constants:
    ESTIMATED_CHARS_PER_TOKEN = 4
    TOOL_RESULT_CHARS_PER_TOKEN = 2
    JSON_PAYLOAD_CHARS_PER_TOKEN = 3
    MESSAGE_BOUNDARY_OVERHEAD_TOKENS = 12
    CONTENT_BLOCK_OVERHEAD_TOKENS = 6
    IMAGE_BLOCK_TOKENS = 2,000
    TRUNCATION_ROUTE_BUFFER_TOKENS = 512

4. CORE COMPACTION: agent-core compact()
================================================================================

File: packages/agent-core/src/harness/compaction/compaction.ts

─── prepareCompaction() ───────────────────────────────────────────────────────

  Signature:
    function prepareCompaction(
      pathEntries: SessionTreeEntry[],
      settings: CompactionSettings,
    ): Result<CompactionPreparation | undefined, CompactionError>

  Algorithm:
    1. Find the last compaction entry (prevCompactionIndex)
    2. Extract previous summary for iterative updates
    3. Determine boundary: start from after last compaction's firstKeptEntryId
    4. Estimate tokensBefore via estimateContextTokens(buildSessionContext(pathEntries).messages)
    5. Find cut point via findCutPoint(entries, boundaryStart, boundaryEnd, keepRecentTokens)
    6. Collect messagesToSummarize (boundaryStart to cut point)
    7. Collect turnPrefixMessages if cut splits a turn
    8. Extract file operations from messages
    9. Return CompactionPreparation

  Returns undefined when:
    - No entries, or last entry is already a compaction

─── compact() ────────────────────────────────────────────────────────────────

  Signature:
    async function compact(
      preparation: CompactionPreparation,
      model: Model,
      apiKey: string | undefined,
      headers?: Record<string, string>,
      customInstructions?: string,
      signal?: AbortSignal,
      thinkingLevel?: ThinkingLevel,
      streamFn?: StreamFn,
      runtime?: AgentCoreCompletionRuntimeDeps,
    ): Promise<Result<CompactionResult, CompactionError>>

  Algorithm:
    IF split turn AND turnPrefixMessages:
      Run BOTH in parallel (Promise.all):
        - generateSummary(messagesToSummarize, ..., previousSummary)
        - generateTurnPrefixSummary(turnPrefixMessages, ...)
      Combine: "{history}\n\n---\n\n**Turn Context (split turn):**\n\n{prefix}"
    ELSE:
      generateSummary(messagesToSummarize, ..., previousSummary)

    Append file operations metadata (readFiles, modifiedFiles)
    Return CompactionResult { summary, firstKeptEntryId, tokensBefore, details }

  This is a SINGLE-PASS LLM call — no multi-pass iteration.

─── generateSummary() ─────────────────────────────────────────────────────────

  Signature:
    async function generateSummary(
      currentMessages: AgentMessage[],
      model: Model,
      reserveTokens: number,
      apiKey: string | undefined,
      headers?: Record<string, string>,
      signal?: AbortSignal,
      customInstructions?: string,
      previousSummary?: string,
      thinkingLevel?: ThinkingLevel,
      streamFn?: StreamFn,
      runtime?: AgentCoreCompletionRuntimeDeps,
    ): Promise<Result<string, CompactionError>>

  Algorithm:
    1. maxTokens = min(0.8 * reserveTokens, model.maxTokens)
    2. Choose prompt:
       - No previousSummary → SUMMARIZATION_PROMPT (fresh summary)
       - Has previousSummary → UPDATE_SUMMARIZATION_PROMPT (iterative update)
    3. Append customInstructions if provided
    4. convertToLlm(currentMessages) → serializeConversation()
    5. Build prompt: <conversation>...</conversation> [+ <previous-summary>...] + instructions
    6. Call completeSummarization(model, context, options)
    7. Extract text content from response
    8. Return summary string

  Summary structure (SUMMARIZATION_PROMPT):
    ## Goal
    ## Constraints & Preferences
    ## Progress (### Done, ### In Progress, ### Blocked)
    ## Key Decisions
    ## Next Steps
    ## Critical Context

  Iterative update (UPDATE_SUMMARIZATION_PROMPT):
    Same structure, with explicit rules:
    - PRESERVE all existing information
    - ADD new progress, decisions, and context
    - UPDATE Progress section (move In Progress → Done)
    - PRESERVE exact file paths, function names, error messages

5. SUMMARIZATION PIPELINE (summarizeInStages / summarizeWithFallback)
================================================================================

File: src/agents/compaction.ts

The gateway layer has a more sophisticated summarization pipeline than
the agent-core's single-pass generateSummary().

─── summarizeInStages() ───────────────────────────────────────────────────────

  Signature:
    async function summarizeInStages(params: {
      messages, model, apiKey, headers, signal,
      reserveTokens, maxChunkTokens, contextWindow,
      customInstructions, summarizationInstructions,
      previousSummary, parts, minMessagesForSplit,
    }): Promise<string>

  Algorithm:
    1. Build stage split plan via buildStageSplitPlanWithWorker()
       - Determines "single" vs "split" mode
    2. If "single": delegate to summarizeWithFallback()
    3. If "split":
       a. For each chunk: summarizeWithFallback(..., previousSummary=undefined)
       b. Collect partial summaries
       c. If multiple: merge via summarizeWithFallback() with MERGE_SUMMARIES_INSTRUCTIONS
       d. If single: return directly

  This is the CLOSEST OpenClaw has to multi-pass — it chunks messages
  and summarizes each chunk separately, then merges.

─── summarizeWithFallback() ───────────────────────────────────────────────────

  Signature:
    async function summarizeWithFallback(params: {
      messages, model, apiKey, headers, signal,
      reserveTokens, maxChunkTokens, contextWindow,
      customInstructions, summarizationInstructions, previousSummary,
    }): Promise<string>

  Algorithm:
    1. Try full summarization via summarizeChunks()
    2. If fails: Build oversized fallback plan
       - Separate small and oversized messages
       - Try summarizing only small messages
       - Append notes about oversized messages
    3. If partial summary available (from failed chunk), use it
    4. Final fallback: "Context contained N messages (K oversized)..."

─── summarizeChunks() ─────────────────────────────────────────────────────────

  Signature:
    async function summarizeChunks(params: {
      messages, model, apiKey, headers, signal,
      reserveTokens, maxChunkTokens,
      customInstructions, summarizationInstructions, previousSummary,
    }): Promise<string>

  Algorithm:
    1. Build chunks via buildSummaryChunksWithWorker()
    2. Initialize summary = previousSummary
    3. For each chunk (sequential, not parallel):
       - Call generateSummary(chunk, ..., previousSummary=summary)
       - With retryAsync(3 attempts, 500ms–5000ms delay, jitter=0.2)
       - On success: update summary iteratively
       - On failure: preserve partial summary, throw with .partialSummary

  This ITERATES over chunks sequentially, feeding the previous
  chunk's summary as previousSummary to the next. This is closest
  to Hermes's iterative summary update.

─── CHUNKING STRATEGY ─────────────────────────────────────────────────────────

  File: src/agents/compaction-planning.ts

  chunkMessagesByMaxTokens(messages, maxTokens):
    - Split messages into chunks that fit under maxTokens
    - Apply SAFETY_MARGIN (1.2x) to each message estimate
    - Never split tool_call/tool_result pairs

  splitMessagesByTokenShare(messages, parts):
    - Split into N roughly equal token-share chunks
    - Track pendingToolCallIds to keep tool_call/tool_result together
    - Default parts = 2

  computeAdaptiveChunkRatio(messages, contextWindow):
    - Adapts chunk size based on message sizes
    - Range: MIN_CHUNK_RATIO (0.15) to BASE_CHUNK_RATIO (0.40)
    - Accounts for SUMMARIZATION_OVERHEAD_TOKENS (4096)

6. COMPACTION SAFEGUARD HOOK (GATEWAY LAYER)
================================================================================

File: src/agents/agent-hooks/compaction-safeguard.ts

This is a comprehensive hook registered on session_before_compact that
completely replaces the agent-core's default compact() with:

─── HOOK REGISTRATION ─────────────────────────────────────────────────────────

  compactionSafeguardExtension(api):
    api.on("session_before_compact", async (event, ctx) => { ... })

─── ALGORITHM ─────────────────────────────────────────────────────────────────

  1. STRIP runtime context custom messages
  2. CHECK for real conversation content
     - If no real content: write minimal compaction boundary to prevent re-trigger loop
  3. EXTRACT file operations and tool failures
  4. RESOLVE instructions (event → runtime config → DEFAULT_COMPACTION_INSTRUCTIONS)
  5. TRY provider-based summarization (if configured)
     - Falls through to LLM on failure
  6. RESOLVE model + credentials
  7. PRUNE history for context share:
     - buildHistoryPrunePlanWithWorker()
     - If new content > max history budget: drop oldest chunks
     - Summarize dropped chunks separately
  8. SPLIT preserved recent turns:
     - splitPreservedRecentTurns() — keep last N user turns verbatim
     - DEFAULT_RECENT_TURNS_PRESERVE = 3 (max 12)
  9. COMPUTE adaptive chunk ratio
  10. SUMMARIZE via LLM with quality guard:
      - Loop up to qualityGuardMaxRetries + 1 attempts (default 1+1=2)
      - Call summarizeViaLLM() → summarizeInStages()
      - If split turn: generate separate turn prefix summary
      - auditSummaryQuality() on each attempt
      - Regenerate with quality feedback instructions on failure
  11. ASSEMBLE final summary:
      - Cap main body at MAX_COMPACTION_SUMMARY_CHARS (16,000)
      - Append suffix (split turn, preserved turns, tool failures, file ops, workspace)
      - capCompactionSummaryPreservingSuffix() protects tail sections
  12. RETURN CompactionResult via hook → SDK persists entry

─── KEY FEATURES ──────────────────────────────────────────────────────────────

  - QUALITY GUARD: Audits summary structure, retries with feedback
  - PRESERVED TURNS: Keeps last N user turns verbatim in summary
  - TOOL FAILURE TRACKING: Extracts and preserves error details
  - PREVIOUS SUMMARY REDISTILL: Prepends old summary with prune instructions
  - WORKSPACE CONTEXT: Reads AGENTS.md sections for post-compaction context
  - IDENTIFIER PRESERVATION: Policy-based opaque identifier protection
  - OVERSIZED MESSAGE HANDLING: Separate fallback for large messages

─── LIMITATIONS ───────────────────────────────────────────────────────────────

  - Single-pass compaction (no loop checking if tokens are below threshold)
  - No progress tracking (5% improvement check from Hermes)
  - No anti-thrashing guard
  - Quality guard only retries the summary, not the compaction threshold

7. HEAD/TAIL PROTECTION & CUT POINTS
================================================================================

File: packages/agent-core/src/harness/compaction/compaction.ts

─── findCutPoint() ────────────────────────────────────────────────────────────

  Signature:
    function findCutPoint(
      entries: SessionTreeEntry[],
      startIndex: number,
      endIndex: number,
      keepRecentTokens: number,
    ): CutPointResult

  Algorithm:
    1. Find valid cut points (entry types that can be boundaries):
       - message entries with roles: user, assistant, bashExecution, custom,
         branchSummary, compactionSummary
       - branch_summary entries
       - custom_message entries
       - EXCLUDES: toolResult (cannot split tool_call/result pairs)
    2. Walk backward from end, accumulating tokens per message
    3. When accumulated >= keepRecentTokens:
       - Find the nearest valid cut point >= current position
    4. Walk backward to avoid cutting inside a compaction or message boundary
    5. Detect split turn:
       - If cut is NOT at a user message → find the turn start
       - isSplitTurn = true when the cut lands mid-turn

  Default: keepRecentTokens = 20,000 tokens

  Result:
    CutPointResult {
      firstKeptEntryIndex: number;
      turnStartIndex: number;
      isSplitTurn: boolean;
    }

─── HEAD PROTECTION ───────────────────────────────────────────────────────────

  The system always keeps:
    - The compaction summary message (replaces everything before cut point)
    - Everything from firstKeptEntry onward

  The compaction summary message is inserted as a compactionSummary-role
  message at the beginning of the context.

─── TAIL PROTECTION ───────────────────────────────────────────────────────────

  Controlled by keepRecentTokens (default: 20,000):
    - Walk backward accumulating tokens
    - Keep approximately 20K tokens of recent context
    - Never split tool_call/tool_result pairs

  Gateway layer adds:
    - DEFAULT_RECENT_TURNS_PRESERVE = 3 (keep last 3 user turns verbatim)
    - MAX_RECENT_TURNS_PRESERVE = 12

─── NO EXPLICIT protect_first_n ───────────────────────────────────────────────

  Unlike Hermes, OpenClaw does NOT have an explicit "protect first N messages"
  parameter. The system prompt is not part of the session tree entries —
  it's rebuilt fresh each turn. The first user message gets no special
  protection beyond the keepRecentTokens budget.

8. TOOL RESULT PRUNING (CONTEXT PRUNING)
================================================================================

File: src/agents/agent-hooks/context-pruning/
      - settings.ts   — configuration
      - pruner.ts      — core pruning logic
      - runtime.ts     — runtime integration

This is a SEPARATE system from compaction — it runs as a context hook
that trims tool results before they become stale.

─── PRUNING MODES ─────────────────────────────────────────────────────────────

  - "off" — disabled
  - "cache-ttl" — trim based on prompt cache TTL expiry

─── DEFAULT SETTINGS ──────────────────────────────────────────────────────────

  DEFAULT_CONTEXT_PRUNING_SETTINGS = {
    mode: "cache-ttl",
    ttlMs: 5 * 60 * 1000,        // 5 minutes
    keepLastAssistants: 3,        // protect last 3 assistant turns
    softTrimRatio: 0.3,           // soft-trim at 30% of context
    hardClearRatio: 0.5,          // hard-clear at 50% of context
    minPrunableToolChars: 50,000, // minimum chars before pruning
    tools: {},                    // allow/deny glob patterns
    softTrim: {
      maxChars: 4,000,            // max chars after soft trim
      headChars: 1,500,           // keep first 1500 chars
      tailChars: 1,500,           // keep last 1500 chars
    },
    hardClear: {
      enabled: true,
      placeholder: "[Old tool result content cleared]",
    },
  }

─── PRUNING ALGORITHM ─────────────────────────────────────────────────────────

  - Tracks prompt-cache TTL per tool result
  - When TTL expires AND context pressure is high:
    - SOFT TRIM: head + tail preservation (keep first/last N chars)
    - HARD CLEAR: replace entire tool result with placeholder
  - Respects tool allow/deny globs
  - Protects last N assistant turns

  This is the closest equivalent to Hermes's _prune_old_tool_results().

10. SESSION STORAGE & PERSISTENCE
================================================================================

File: packages/agent-core/src/harness/session/session.ts

─── SESSION TREE MODEL ────────────────────────────────────────────────────────

  Sessions are append-only trees stored as JSONL files.
  Each entry has: { type, id, parentId, timestamp }

  Entry types: message, thinking_level_change, model_change,
               compaction, branch_summary, custom, custom_message,
               label, session_info, leaf

─── COMPACTION ENTRY ──────────────────────────────────────────────────────────

  CompactionEntry {
    type: "compaction";
    id: string;
    parentId: string | null;
    timestamp: string;
    summary: string;
    firstKeptEntryId: string;  // ID of first retained entry
    tokensBefore: number;      // context tokens before compaction
    details?: unknown;         // implementation-specific (file ops)
    fromHook?: boolean;        // true if hook provided summary
  }

  When building session context (buildSessionContext):
    1. Walk all pathEntries
    2. Find the last compaction entry
    3. Insert compactionSummary message for it
    4. Only include message entries AFTER the compaction's firstKeptEntryId
    5. Earlier messages are replaced by the summary

─── IN-PLACE vs ROTATION ─────────────────────────────────────────────────────

  OpenClaw uses IN-PLACE compaction by default:
    - Appends a CompactionEntry to the session tree
    - Does NOT rotate session IDs
    - Does NOT create child sessions
    - Session tree remains a single append-only file

  The context engine plugin interface supports session rotation
  (CompactResult.sessionId, CompactResult.sessionFile) but the
  default compaction does not use it.

11. SAFETY TIMEOUT & ABORT HANDLING
================================================================================

File: src/agents/embedded-agent-runner/compaction-safety-timeout.ts

─── TIMEOUT VALUE ─────────────────────────────────────────────────────────────

  EMBEDDED_COMPACTION_TIMEOUT_MS = 180,000  (180 seconds / 3 minutes)

  Configurable via:
    config.agents?.defaults?.compaction?.timeoutSeconds

  Resolution:
    resolveCompactionTimeoutMs(cfg):
      finiteSecondsToTimerSafeMilliseconds(cfg?.agents?.defaults?.compaction?.timeoutSeconds)
      ?? EMBEDDED_COMPACTION_TIMEOUT_MS

─── compactWithSafetyTimeout() ────────────────────────────────────────────────

  Signature:
    async function compactWithSafetyTimeout<T>(
      compact: (abortSignal?: AbortSignal) => Promise<T>,
      timeoutMs: number = 180_000,
      opts?: { abortSignal?: AbortSignal; onCancel?: () => void },
    ): Promise<T>

  Algorithm:
    1. Create composed abort signal (timeout + external)
    2. Race compact() against external abort signal
    3. On timeout: call onCancel(), reject with "Compaction timed out"
    4. On external abort: call onCancel(), reject with AbortError
    5. Clean up signal listeners in finally

─── compactContextEngineWithSafetyTimeout() ───────────────────────────────────

  Wraps contextEngine.compact() with the same safety timeout.
  Threads abort signal into compact() params so cooperating engines
  can cancel in-flight work.

─── HARNESS ABORT SIGNAL ──────────────────────────────────────────────────────

  In agent-harness.ts compact():
    - Creates a FRESH AbortController for the hook signal
    - Signal is NOT connected to the turn's abort controller
    - compact() function receives signal=undefined

  In the embedded runner:
    - Turn has its own abort controller
    - Compaction gets its own composed signal (timeout + external)
    - Both are independent

12. MULTI-PASS / RETRY SEMANTICS (CURRENT STATE)
================================================================================

OpenClaw does NOT have true multi-pass compaction. Here's what it has:

─── WHAT EXISTS ───────────────────────────────────────────────────────────────

  1. OVERFLOW RETRY LOOP (run.ts):
     - Up to MAX_OVERFLOW_COMPACTION_ATTEMPTS = 3 retries
     - Each retry triggers a fresh compact() call
     - BUT no progress check between retries
     - No 5% improvement threshold
     - Simply retries and hopes for better results

  2. TIMEOUT RETRY LOOP (run.ts):
     - Up to MAX_TIMEOUT_COMPACTION_ATTEMPTS = 2 retries
     - Each retry triggers a fresh compact() call
     - Only triggers when tokenUsedRatio > 0.65

  3. SUMMARIZATION CHUNKING (compaction.ts):
     - summarizeChunks() processes chunks sequentially
     - Each chunk builds on the previous summary
     - This is iterative summarization, NOT iterative compaction

  4. QUALITY GUARD (compaction-safeguard.ts):
     - Up to qualityGuardMaxRetries + 1 attempts (default 2)
     - Only retries the SUMMARY GENERATION, not the compaction decision
     - Checks summary structure and identifier preservation

─── WHAT IS MISSING (vs Hermes) ───────────────────────────────────────────────

  1. NO multi-pass loop that checks if tokens are below threshold
     after each compaction pass

  2. NO progress detection (>5% token reduction) between passes

  3. NO anti-thrashing guard (consecutive ineffective compressions)

  4. NO iterative summary refinement at the COMPACTION level
     (only at the chunk summarization level)

  5. NO head protection decay (protect_first_n decaying after first pass)

  6. NO explicit protect_first_n parameter for first user messages

  7. NO tool output 1-line summaries (Hermes's _summarize_tool_result)
     Only full replacement with placeholders or soft/hard trim

  8. NO disambiguation directives in the summary prefix
     (Hermes's extensive SUMMARY_PREFIX with "REFERENCE ONLY" etc.)

16. ERROR HANDLING PATTERNS
================================================================================

─── RESULT TYPE PATTERN ───────────────────────────────────────────────────────

  Agent-core uses Result<T, E> = { ok: true; value: T } | { ok: false; error: E }
  Functions return Result instead of throwing (prepareCompaction, compact, generateSummary)

─── COMPACTION SAFEGUARD ERROR HANDLING ───────────────────────────────────────

  - Abort/timeout errors always propagate (isAbortError, isTimeoutError)
  - Model/auth resolution failure → cancel compaction (preserve history)
  - Summarization failure → cancel compaction (preserve history)
  - Quality guard failure during retry → keep last successful summary
  - Provider failure → fall through to LLM path

─── RUN LOOP ERROR HANDLING ───────────────────────────────────────────────────

  - Overflow error → retry with compaction (up to 3 times)
  - Timeout error → retry with compaction (up to 2 times)
  - Compaction failure → surface original error
  - Exhausted retries → terminal error
  - Partial summary → preserved via .partialSummary on Error

─── RETRY SEMANTICS ───────────────────────────────────────────────────────────

  summarizeChunks: retryAsync with 3 attempts, 500ms–5000ms, jitter=0.2
  shouldRetry: abort and timeout errors NOT retried

│ Compaction provider plugins   │ No           │ Yes          │
│ Context engine plugin system  │ No           │ Yes (full)   │
