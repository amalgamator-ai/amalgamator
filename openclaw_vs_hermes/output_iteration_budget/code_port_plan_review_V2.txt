A.5  CRITICAL ARCHITECTURAL FINDING (V2-only)
-----------------------------------------------

  [Unchanged from V2. The two-level loop architecture finding is correct
   and verified against actual source code. The inner loop in
   agent-core/agent-loop.ts (lines 306-437) is confirmed as the
   tool-calling loop with the while(hasMoreToolCalls) structure.]

  [FIX #6] ADDITIONAL FINDING: shouldStopAfterTurn ALTERNATIVE

    The existing AgentLoopConfig ALREADY has a shouldStopAfterTurn callback
    (types.ts line 218) that is ALREADY invoked in agent-loop.ts (lines
    409-419) after each turn. It is called after every assistant turn
    INCLUDING tool-calling turns. It receives ShouldStopAfterTurnContext
    with the assistant message, tool results, context, and newMessages.

    shouldStopAfterTurn is NOT currently in AgentOptions (lines 104-153
    of agent.ts) and is NOT mapped in createLoopConfig (lines 474-508).

    Using shouldStopAfterTurn for budget enforcement would eliminate
    changes to agent-core/types.ts and agent-core/agent-loop.ts (2 of 3
    agent-core files). Only agent.ts would need changes (add to
    AgentOptions and map in createLoopConfig).

    However, the V2 plan's onBeforeToolCallingRound is PREFERRED because:
    - It's a dedicated callback with clear purpose separation
    - It won't conflict with future uses of shouldStopAfterTurn
    - It prevents the next LLM call BEFORE it happens (saves API cost)
    - shouldStopAfterTurn is async-capable; sync onBeforeToolCallingRound
      avoids unnecessary async overhead in the hot loop

    The shouldStopAfterTurn approach is documented as a viable fallback
    if modifying agent-core/types.ts and agent-core/agent-loop.ts is
    rejected during code review.

      toolCallingRound += 1;

STEP 8: Integrate budget creation and exhaustion detection in run.ts
--------------------------------------------------------------------------------

  [FIX #1] CORRECTED: Missing payloadCount check in exhaustion detection

  TARGET FILE (MODIFY):
    src/agents/embedded-agent-runner/run.ts

  CHANGES:

    Items 1-4 are unchanged from V2. (Imports, budget initialization,
    tracking variables, attempt dispatch.)

    [FIX #1] Item 5: CORRECTED budget exhaustion detection.

    After the attempt result is processed, in the "Successful Completion"
    section (~line 3508), BEFORE the existing retry checks
    (reasoning-only, empty-response), add budget exhaustion detection:

      // --- Budget Exhaustion Detection ---
      if (
        iterationBudget &&
        iterationBudget.remaining <= 0 &&
        payloadCount === 0 &&            // [FIX #1] CRITICAL: only trigger
                                         //   if no text response produced.
                                         //   If model exhausted budget but
                                         //   naturally finished with text on
                                         //   the last allowed round, return
                                         //   the text response normally.
        !attempt.clientToolCalls &&       // [FIX #1] Not a client tool call
        !budgetSummaryAttempt &&
        !aborted &&
        !promptError
      ) {
        // Budget exhausted during this attempt's inner loop.
        // The inner loop broke because budget.consume() returned false.
        if (budgetConfig.forceSummaryOnExhaustion) {
          budgetExhaustedSummaryPending = true;
          // Continue to the next outer-loop iteration, which will inject
          // the summary prompt (Step 11).
          continue;
        } else {
          // Return error immediately
          return buildBudgetExhaustionResult({
            budget: iterationBudget,
            durationMs: Date.now() - started,
            agentMeta,
            livenessState: resolveRunLivenessState({
              payloadCount: 0,
              aborted,
              timedOut,
              attempt,
              incompleteTurnText: null,
            }),
          });
        }
      }

    WHY payloadCount === 0 IS CRITICAL:

      Without this check, the following scenario is mishandled:

      Budget=90. Model uses 89 rounds of tool calling, then on round 90
      (last allowed), the model produces a TEXT response instead of
      tool calls. The inner loop exits naturally (hasMoreToolCalls=false).
      Budget.remaining=0, but there IS a text response.

      Without the fix: run.ts would trigger the budget exhaustion handler
      and either request a summary (wasteful) or return an error
      (incorrect -- the model already answered).

      With the fix: payloadCount > 0, so the budget exhaustion check is
      skipped. The text response flows through the normal success path.
      Budget metadata (budgetUsed/budgetMax) is still included in the
      result meta (Step 13).

    Item 6: Handle summary attempt completion.

    [FIX #8] CORRECTED: The summary attempt return should include all
    standard result fields for consistency with the normal success path.

      // --- Budget Summary Attempt Result ---
      if (budgetSummaryAttempt) {
        budgetSummaryAttempt = false;
        const summaryText = resolveFinalAssistantVisibleText(
          sessionLastAssistant,
        );
        if (summaryText) {
          // Summary produced -- return as result with budget metadata.
          // Include standard result fields alongside budget-specific ones.
          return {
            payloads: [{ text: summaryText }],
            meta: {
              durationMs: Date.now() - started,
              agentMeta,
              aborted,
              finalAssistantVisibleText: summaryText,
              ...(iterationBudget
                ? {
                    budgetUsed: iterationBudget.used,
                    budgetMax: iterationBudget.maxTotal,
                  }
                : {}),
              error: {
                kind: "budget_exhausted" as const,
                message: `Budget exhausted: ${iterationBudget!.used}/${iterationBudget!.maxTotal}`,
              },
            },
            didSendViaMessagingTool: attempt.didSendViaMessagingTool,
            didDeliverSourceReplyViaMessageTool:
              attempt.didDeliverSourceReplyViaMessageTool === true,
            messagingToolSentTexts: attempt.messagingToolSentTexts,
            messagingToolSentMediaUrls: attempt.messagingToolSentMediaUrls,
            messagingToolSentTargets: attempt.messagingToolSentTargets,
            messagingToolSourceReplyPayloads:
              attempt.messagingToolSourceReplyPayloads,
            heartbeatToolResponse: attempt.heartbeatToolResponse,
            successfulCronAdds: attempt.successfulCronAdds,
            acceptedSessionSpawns: attempt.acceptedSessionSpawns,
          };
        }
        // Fallback if summary didn't produce text
        return buildBudgetExhaustionResult({
          budget: iterationBudget!,
          durationMs: Date.now() - started,
          agentMeta,
          summaryError: "Summary call did not produce visible text",
        });
      }

C.2  MEDIUM RISK (additions)
-----------------------------

  [FIX #4] Callback threading (Step 7)
    REVISED RISK: The beforeToolCall threading pattern should NOT be
    followed because beforeToolCall is overwritten by
    AgentSession.installAgentToolHooks(). The corrected approach sets the
    callback directly on the Agent instance after session creation.

    - Risk: Setting the property after session creation might not persist
      if the session recreates or replaces the agent.
    - Mitigation: AgentSession does not recreate the agent after initial
      construction. The property persists.

  [FIX #7] Agent-harness.ts createLoopConfig
    ADDITIONAL RISK: agent-harness.ts has its own createLoopConfig method.
    If the embedded agent code path goes through AgentHarness instead of
    Agent directly, the callback must also be threaded there.

    - Risk: Missing the harness path silently disables the budget.
    - Mitigation: During implementation, trace the exact code path from
      runEmbeddedAttempt to runAgentLoop and verify which createLoopConfig
      is called.
