--- FIX 1: Honor subagent iteration caps ---
  FILE: src/agents/embedded-agent-runner/run.ts

  WHAT WAS REQUESTED:
    The reviewer found that subagentMaxIterations is accepted in config and
    defaulted to 50, but the runtime always constructs IterationBudget with
    maxIterations (default 90). A configured subagent cap is silently ignored.

  WHAT WAS DONE:
    Added `isSubagentRun` detection using `params.spawnedBy` (non-null when
    the run is spawned by a parent agent via sessions_spawn). The budget
    constructor now selects:
      - subagentMaxIterations (default 50) when isSubagentRun is true
      - maxIterations (default 90) otherwise

    This matches the Hermes source design where parent agents default to 90
    iterations and each subagent defaults to 50 (hermes_code_trace.txt §10).

  WHY THIS FIX IS CORRECT:
    params.spawnedBy is the canonical indicator for subagent sessions in the
    embedded runner (RunEmbeddedAgentParams.spawnedBy in run/params.ts:83).
    The field is populated when sessions_spawn creates the run and is null/
    undefined for top-level parent runs. This aligns with how other subagent-
    aware features (tool policy, compaction hooks) detect subagent sessions.


--- FIX 2: Count each budgeted tool round once ---
  FILE: src/agents/embedded-agent-runner/run.ts

  WHAT WAS REQUESTED:
    The reviewer found that the same IterationBudget is consumed twice per
    tool-calling iteration:
      1. In the outer run loop (line 1945): iterationBudget.consume()
      2. In onBeforeToolCallingRound callback (line 2168): iterationBudget.consume()
    This makes the configured limit effectively halved for tool-using runs.

  WHAT WAS DONE:
    Removed the outer-loop budget consumption (the 4-line block at lines
    1941-1946). The onBeforeToolCallingRound callback is now the single
    canonical consumption point. This means each tool-calling round within
    the agent-core inner loop consumes exactly one budget unit.

  WHY THIS FIX IS CORRECT:
    The outer run loop covers retry/recovery iterations (compaction, auth,
    timeout, empty-response, reasoning-only retries). These are programmatic
    recovery mechanisms, not user-visible agent iterations. They are already
    bounded by their own independent limits (MAX_OVERFLOW_COMPACTION_ATTEMPTS,
    MAX_TIMEOUT_COMPACTION_ATTEMPTS, maxReasoningOnlyRetryAttempts, etc.).
    In the Hermes source, analogous non-productive iterations (execute_code,
    compression restarts) are explicitly refunded via budget.refund().

    By making onBeforeToolCallingRound the sole consumption point:
    - Each tool-calling round = exactly 1 budget unit (no double-counting)
    - Non-tool administrative retries don't consume budget (they're bounded
      separately and would be refunded in Hermes anyway)
    - The configured maxIterations accurately reflects the user-visible limit

    Budget summary attempt correctness is preserved: the refund() at line 3897
    gives back one unit, and the summary attempt (which should not make tool
    calls) does not trigger onBeforeToolCallingRound. If the model
    unexpectedly requests tools during the summary, consume() returns false
    and the inner loop stops.
