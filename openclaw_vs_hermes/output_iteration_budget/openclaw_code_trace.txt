1. ARCHITECTURE OVERVIEW & GAP ANALYSIS
================================================================================

OpenClaw has NO equivalent of Hermes's IterationBudget class. Instead, it has:

A) Tool Loop Detection — a content-hash-based heuristic (tool-loop-detection.ts)
   that watches for repeated tool calls with identical arguments and results.
   DISABLED by default (enabled: false). Detects specific patterns (repeated
   failures, ping-pong, polling loops, unknown tools) but does NOT count total
   iterations. Fails when volatile messageIds defeat content-hash dedup (#89090).

B) Post-Compaction Loop Guard — detects tool-call loops that persist after
   context compaction. Only watches a small window post-compaction.

C) Channel Bot-Pair Loop Protection — prevents bot-to-bot reply loops in
   messaging channels. Rate-limit style (events per window), not iteration-based.

D) Run Retry Limit (MAX_RUN_LOOP_ITERATIONS) — caps the outer retry loop
   around LLM API calls. This is NOT an iteration budget; it guards against
   retry storms (rate limits, overloads, auth failures). Default: 24 base +
   8 per profile candidate, min 32, max 160.

What is MISSING compared to Hermes:
  - Per-agent turn counter (Hermes: 90 parent, 50 subagent)
  - Thread-safe consume/refund semantics
  - Budget-exhaustion summary (forcing model to summarize)
  - Configurable per-agent iteration caps
  - Refund for execute_code/compression restarts
  - Grace call mechanism
  - The tool loop detection is DISABLED by default

2. COMPONENT #1: Tool Loop Detection (Heuristic-Based)
================================================================================

File: src/agents/tool-loop-detection.ts (821 lines)

Purpose: Watches recent tool-call history for repeated no-progress patterns
and triggers warning/blocking decisions. This is the closest OpenClaw analog
to Hermes's ToolCallGuardrailController.

--- 2.1 Detection Patterns ---

Five detector kinds:
  - generic_repeat:       Same tool + same args repeated N times
  - unknown_tool_repeat:  Repeated calls to a tool that doesn't exist
  - known_poll_no_progress: Polling tools (command_status, process poll/log)
  - global_circuit_breaker: Any tool repeated 30+ times with no progress
  - ping_pong:            Alternating A-B-A-B pattern between two tools

--- 2.2 Thresholds (DEFAULT — disabled by default!) ---

  const DEFAULT_LOOP_DETECTION_CONFIG = {
    enabled: false,                          // ← DISABLED
    historySize: 30,                         // sliding window
    warningThreshold: 10,                    // emit "warning" level
    unknownToolThreshold: 10,                // block unknown tool
    criticalThreshold: 20,                   // emit "critical" / block
    globalCircuitBreakerThreshold: 30,       // absolute circuit breaker
    detectors: {
      genericRepeat: true,
      knownPollNoProgress: true,
      pingPong: true,
    },
  };

--- 2.3 Key Functions ---

function detectToolCallLoop(
  state: SessionState,
  toolName: string,
  params: unknown,
  config?: ToolLoopDetectionConfig,
  scope?: ToolLoopDetectionScope,
): LoopDetectionResult
  - Returns { stuck: false } or { stuck: true, level, detector, count, message }
  - Checks all detectors in priority order
  - "critical" level → blocks tool execution
  - "warning" level → emits guidance message but allows execution

function recordToolCall(
  state: SessionState,
  toolName: string,
  params: unknown,
  toolCallId?: string,
  config?: ToolLoopDetectionConfig,
  scope?: ToolLoopDetectionScope,
): void
  - Records tool call in sliding-window history
  - Maintains toolCallHistory[] on SessionState
  - Caps at historySize entries

function recordToolCallOutcome(
  state: SessionState,
  params: {
    toolName, toolParams, toolCallId, result, error, config, runId
  },
): ToolCallRecord | undefined
  - Records the outcome (result hash) of a completed tool call
  - Enables no-progress detection (same result = no progress)
  - Special handling for volatile send results (#89090 fix)

function hashToolCall(toolName: string, params: unknown): string
  - SHA-256 of stable JSON serialization of tool name + params

--- 2.4 Volatile Send Result Handling ---

Problem: Messaging tool results contain per-call volatile IDs (messageId,
timestamps) that defeat content-hash dedup (#89090).

Solution: stripVolatileSendIds() removes known volatile keys before hashing.
  VOLATILE_SEND_RESULT_KEYS: messageId, message_id, messageIds, platformMessageId,
    fileId, pollId, receipt, runId, idempotencyKey, ts, timestamp, sentAt, etc.

--- 2.5 Streak Detection Logic ---

getNoProgressStreak(): Walks history backward counting consecutive calls with
  the same toolName + argsHash + identical resultHash. Breaks on any result
  change. Returns count + latestResultHash.

getPingPongStreak(): Detects alternating A-B-A-B patterns in the tail of
  history. Requires noProgressEvidence (all results within each side are
  identical) for critical-level blocking.

getUnknownToolRepeatStreak(): Counts consecutive calls to the same tool
  where the error message indicates "unknown tool".

--- 2.6 Loop Veto Handling ---

The detector's own "blocked" result (deniedReason: "tool-loop") is treated
specially: isLoopVetoResult() returns true, and the result gets NO hash.
This prevents the loop block from "resetting" the streak (the block result
itself would otherwise count as a different outcome).

3. COMPONENT #2: Post-Compaction Loop Guard
================================================================================

File: src/agents/embedded-agent-runner/post-compaction-loop-guard.ts (152 lines)

Purpose: Detects identical tool-call loops that persist after automatic
context compaction. If compaction didn't break the loop, abort to prevent
unbounded token spending.

--- 3.1 API ---

function createPostCompactionLoopGuard(
  config?: ToolLoopPostCompactionGuardConfig,
  options?: { enabled?: boolean },
): PostCompactionLoopGuard

Returns object with:
  armPostCompaction(): void
    - Arms the guard for windowSize attempts (default: 3)
    - Called after every automatic compaction in run.ts

  observe(call: { toolName, argsHash, resultHash }): PostCompactionGuardVerdict
    - Called on each tool outcome via observeToolOutcome callback
    - If armed, counts matching (tool + args + result) entries
    - If matches >= windowSize → returns shouldAbort: true

  snapshot(): { armed, remainingAttempts }

--- 3.2 Error Class ---

class PostCompactionLoopPersistedError extends Error
  - Carries detector, count, toolName
  - Static fromVerdict() factory
  - Used to abort the run via AbortController

--- 3.3 Integration in run.ts (lines 1599-1628) ---

  const postCompactionGuard = createPostCompactionLoopGuard(
    resolvedLoopDetectionConfig?.postCompactionGuard,
    { enabled: resolvedLoopDetectionConfig?.enabled !== false },
  );

  // After each compaction:
  postCompactionGuard.armPostCompaction();  // lines 2554, 2804, 3843

  // On each tool outcome (via observeToolOutcome callback):
  const verdict = postCompactionGuard.observe(observation);
  if (verdict.shouldAbort) {
    postCompactionAbortError ??= PostCompactionLoopPersistedError.fromVerdict(verdict);
    laneTaskAbortController.abort(postCompactionAbortError);
  }

4. COMPONENT #3: Channel Bot-Pair Loop Protection
================================================================================

File: src/channels/turn/bot-loop-protection.ts (45 lines)
File: src/plugin-sdk/pair-loop-guard-runtime.ts (280 lines)

Purpose: Prevents bot-to-bot reply loops in messaging channels using
rate-limit-style suppression.

--- 4.1 Mechanism ---

  - Tracks bidirectional bot pairs (sender+receiver sorted for symmetry)
  - Counts events in a rolling window (default: 60s)
  - When maxEventsPerWindow (default: 20) exceeded → cooldown
  - During cooldown (default: 60s) → suppress replies

--- 4.2 Types ---

type PairLoopGuardConfig = {
  enabled?: boolean;
  maxEventsPerWindow?: number;   // default: 20
  windowSeconds?: number;        // default: 60
  cooldownSeconds?: number;      // default: 60
};

type PairLoopGuardResult =
  | { suppressed: false }
  | { suppressed: true; cooldownUntilMs: number };

--- 4.3 Integration ---

Channel turn adapters call:
  recordChannelBotPairLoopAndCheckSuppression(facts)
before delivering a bot reply. If suppressed, reply is dropped.

Global singleton: channelBotPairLoopGuard created once per process.

5. COMPONENT #4: Run Retry Limit (MAX_RUN_LOOP_ITERATIONS)
================================================================================

File: src/agents/embedded-agent-runner/run/helpers.ts (lines 106-128)

Purpose: Defensive cap on the outer run loop across ALL retry branches
(rate limits, overloads, auth failures, compaction retries, empty response
retries, etc.). NOT an iteration budget — it's a retry-storm breaker.

--- 5.1 Constants ---

  const BASE_RUN_RETRY_ITERATIONS = 24;
  const RUN_RETRY_ITERATIONS_PER_PROFILE = 8;
  const MIN_RUN_RETRY_ITERATIONS = 32;
  const MAX_RUN_RETRY_ITERATIONS = 160;

--- 5.2 Resolution ---

function resolveMaxRunRetryIterations(
  profileCandidateCount: number,
  cfg?: OpenClawConfig,
  agentId?: string,
): number
  - Reads config: agents.defaults.runRetries or per-agent runRetries
  - Formula: base + max(1, profileCount) * perProfile
  - Clamped to [min, max] range
  - Default effective: 24 + 1*8 = 32 (with 1 profile)

--- 5.3 Config Type ---

type AgentRunRetriesConfig = {
  base?: number;       // default: 24
  perProfile?: number; // default: 8
  min?: number;        // default: 32
  max?: number;        // default: 160
};

--- 5.4 Exhaustion Handling ---

File: src/agents/embedded-agent-runner/run/retry-limit.ts (54 lines)

function handleRetryLimitExhaustion(params): EmbeddedAgentRunResult
  - If failover decision = "fallback_model" → throw FailoverError
  - Otherwise → return error payload:
    "Request failed after repeated internal retries. Please try again..."

NOTE: This DOES NOT ask the model to summarize (unlike Hermes's
handle_max_iterations). It just returns an error message.

6. COMPONENT #5: Agent Runner Main Loop (run.ts)
================================================================================

File: src/agents/embedded-agent-runner/run.ts (~4100 lines)
File: src/agents/embedded-agent-runner/run/attempt.ts (~5800 lines)

--- 6.1 Outer Loop (run.ts, line 1885) ---

  while (true) {
    if (runLoopIterations >= MAX_RUN_LOOP_ITERATIONS) {
      // Exceeded retry limit → handleRetryLimitExhaustion()
      break;
    }
    runLoopIterations += 1;
    // ... dispatch one LLM attempt ...
    const result = await runEmbeddedAttempt({ ... });
    // ... handle result, retry decisions, compaction, failover ...
  }

This loop increments on every LLM API call attempt, including retries
for errors, compaction restarts, auth rotation, etc. It is NOT the same
as an iteration budget — it does not count productive tool-calling turns.

--- 6.2 What Is Tracked ---

  runLoopIterations           — total loop iterations (retry guard)
  overflowCompactionAttempts  — compaction retries
  reasoningOnlyRetryAttempts  — reasoning-only response retries
  emptyResponseRetryAttempts  — empty response retries
  compactionContinuationRetries — continuation after compaction
  autoCompactionCount         — number of auto-compactions

--- 6.3 What Is NOT Tracked ---

  - Total number of productive tool-calling turns
  - Per-turn iteration count
  - Agent-level budget consumption
  - Subagent vs parent budget differentiation

--- 6.4 Attempt Dispatch (attempt.ts) ---

Each runEmbeddedAttempt() call:
  1. Builds the LLM prompt with system message + history
  2. Calls the provider API (streaming or non-streaming)
  3. Processes the response (tool calls, text, errors)
  4. Returns the result to the outer loop

The attempt function processes ALL tool calls from a single LLM response,
then returns. There is no inner tool-calling loop within attempt.ts;
the outer run.ts loop manages the turn cycle.

--- 9.2 Storage ---

Shared in-memory Map: diagnosticSessionStates (global singleton)
  - Max 2000 entries, pruned every 60s
  - TTL: 30 minutes for idle entries
  - Keyed by sessionKey (preferred) or sessionId

--- 9.3 Access Functions ---

  - Gets or creates a SessionState entry
  - Handles sessionKey/sessionId migration

  - Read-only peek without creating entries

NOTE: This state is per-process and NOT thread-safe (Node.js is single-threaded,
so this is acceptable). Hermes uses threading.Lock because Python agents can
run concurrently; OpenClaw doesn't need this.

13. MISSING: Iteration Budget (Gap Analysis)
================================================================================

What Hermes has that OpenClaw LACKS:

  1. IterationBudget class
     - Thread-safe per-agent turn counter
     - consume() / refund() semantics
     - Separate budgets: parent=90, subagent=50
     → OpenClaw has NO equivalent. No code counts total LLM API calls
       per user turn or per agent run.

  2. Budget-aware loop condition
     - Hermes: while (api_call_count < max_iterations AND budget.remaining > 0)
     → OpenClaw: while (true) with only runLoopIterations as a retry guard
       (not a productive-turn counter)

  3. Budget exhaustion → forced summary
     - Hermes: handle_max_iterations() injects summary request, strips tools
     → OpenClaw: retry limit → generic error message, no summary

  4. Per-agent configurable iteration caps
     - Hermes: config.yaml → agent.max_turns (parent), delegation.max_iterations (sub)
     → OpenClaw: runRetries config only controls the retry storm guard,
       not productive iterations

  5. Budget refund for cheap operations
     - Hermes: execute_code, compression restarts → refund()
     → OpenClaw: N/A (no budget to refund against)

  6. Grace call mechanism
     - Hermes: _budget_grace_call allows one extra iteration after exhaustion
     → OpenClaw: N/A

  7. Activity observability
     - Hermes: get_activity_summary() includes budget_used/budget_max
     → OpenClaw: diagnostic session state has no budget fields

  8. Tool loop detection is DISABLED by default
     - Hermes: warnings always-on, hard stops opt-in
     → OpenClaw: entire loop detection system is opt-in (enabled: false)
