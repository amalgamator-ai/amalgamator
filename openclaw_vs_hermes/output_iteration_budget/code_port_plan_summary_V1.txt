1.3  GAP ANALYSIS
──────────────────

  Identified 8 specific gaps where Hermes has capabilities OpenClaw lacks:
  1. Per-agent turn counter (IterationBudget class)
  2. Budget-aware loop condition (productive iteration tracking)
  3. Budget exhaustion → forced summary (handle_max_iterations)
  4. Configurable per-agent iteration caps
  5. Budget refund for compaction restarts
  6. Grace call mechanism
  7. Activity observability with budget fields
  8. Tool loop detection disabled by default

  Assessed which gaps to port (6 of 8) and which to skip for V1 (2 of 8:
  grace call mechanism and execute_code refund, because they don't have
  direct OpenClaw equivalents).

1.4  DESIGN DECISIONS
──────────────────────

  Made the following key design decisions:

  a) DON'T port ToolCallGuardrailController — OpenClaw already has a
     sophisticated tool-loop-detection.ts with 5 detector kinds. The
     architectures differ (sliding window vs per-turn state machine)
     but both solve the same problem. Replacing would be higher risk
     and lower value than adding the missing iteration budget.

  b) DON'T add threading.Lock — Node.js is single-threaded, so the
     IterationBudget class needs no synchronization.

  c) DO use the "consume after productive response" integration strategy
     rather than "consume at loop top" — this has a single integration
     point and avoids modifying the 22 continue paths in run.ts.

  d) DO add config flag (enabled: true by default) for safe rollback
     without code changes.

  e) DO enable tool loop detection warnings by default — aligns with
     Hermes's design principle and addresses documented OpenClaw issues.

  f) DO use a callback pattern for the summary LLM call in budget
     exhaustion handler — avoids tight coupling with provider layer.
