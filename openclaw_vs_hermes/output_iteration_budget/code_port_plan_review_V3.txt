---------------------------------------------------------

  [FIX #1] CORRECTED HARNESS RESOLUTION:

    The embedded agent runner call chain:

      run.ts
        -> runEmbeddedAttemptWithBackend(params)  [run/backend.ts]
          -> runAgentHarnessAttempt(params)        [run/backend.ts]
            -> ...
              -> creates AgentSession with Agent instance
              -> Agent or CoreAgentHarness calls runAgentLoop(config)

    TWO createLoopConfig implementations exist:

      1. Agent.createLoopConfig (agent-core/agent.ts, lines 474-507)
         - Maps: beforeToolCall, afterToolCall, prepareNextTurn, etc.
         - Does NOT map: shouldStopAfterTurn, onBeforeToolCallingRound (new)

      2. CoreAgentHarness.createLoopConfig (agent-core/harness/agent-harness.ts,
         lines 486-542)
         - Does NOT extend Agent -- standalone class
         - Has `private session: Session` (NOT `this.agent`)
         - Maps: beforeToolCall (via hook emit), afterToolCall (via hook emit),
           transformContext, prepareNextTurn, getSteeringMessages,
           getFollowUpMessages
         - Does NOT map: shouldStopAfterTurn, onBeforeToolCallingRound

    [FIX #1] CRITICAL CORRECTION: The V3 plan stated
    "CoreAgentHarness wraps an Agent, so it can access the Agent's
    properties" and suggested `this.agent?.onBeforeToolCallingRound`.
    This is WRONG. CoreAgentHarness has:

        private session: Session;   // line 223

    NOT `this.agent`. The harness wraps a Session, which in turn may
    contain an Agent. But the harness's createLoopConfig does NOT read
    any Agent properties. It builds all callbacks from its own methods
    (emitHook, drainQueuedMessages, etc.).

    CORRECTED APPROACH for onBeforeToolCallingRound in the harness:
    Add a dedicated public property to CoreAgentHarness and map it
    directly in createLoopConfig. Set it from the outside in attempt.ts.
    (This was the V3 plan's "fallback" approach; it is now the PRIMARY.)

    WHY !timedOut IS NEEDED (FIX #2):

      Without it, the following scenario is mishandled:

      The attempt times out during tool execution (timedOutDuringPrompt=false).
      The timeout return path (lines 3628-3707) only fires when
      timedOutDuringPrompt=true, so the code continues to the retry section.
      Budget.remaining=0, payloadCount=0. Without !timedOut, the budget
      exhaustion handler fires instead of letting the timeout be handled
      by the existing timeout recovery mechanisms.

      The compaction continuation check (line 3829) includes !timedOut for
      exactly this reason.

    WHY !emptyAssistantReplyIsSilent IS NEEDED (FIX #3):

      If the agent completed its work silently (intentional no-visible-text
      output, e.g. for silent notification processing), payloadCount=0 is
      expected. If the budget also happens to be at 0, we should NOT trigger
      budget exhaustion -- the work completed successfully.

    WHY !attempt.yieldDetected IS NEEDED (FIX #3):

      If the agent voluntarily yielded (paused to wait for user input),
      it may produce payloadCount=0 with budget=0. The yield should be
      respected, not overridden by budget exhaustion handling.

    [FIX #4] Item 6a: Clear stale retry instructions.

      When budget exhaustion triggers the summary flow, clear any stale
      retry instructions from previous iterations. These could create
      redundant or conflicting prompt instructions during the summary
      attempt:

        if (budgetConfig.forceSummaryOnExhaustion) {
          iterationBudget.refund();
          budgetExhaustedSummaryPending = true;
          budgetExhaustedSummaryInstruction = BUDGET_EXHAUSTION_SUMMARY_INSTRUCTION;
          // [FIX #4] Clear stale retry instructions so the summary
          // attempt's prompt contains only the budget summary instruction.
          reasoningOnlyRetryInstruction = null;
          emptyResponseRetryInstruction = null;
          compactionContinuationRetryInstruction = null;
          continue;
        }

      WHY THIS MATTERS:

        Without clearing, the following scenario causes a confusing prompt:

        1. Iteration A: LLM returns reasoning-only response ->
           reasoningOnlyRetryInstruction = "please provide visible answer"
           -> continue
        2. Iteration B: retry with visible-answer instruction -> LLM enters
           tool-calling loop -> budget exhausts -> budget exhaustion handler
           fires -> budgetExhaustedSummaryInstruction = "please summarize"
           -> continue
        3. Iteration C: summary attempt -> prompt includes BOTH
           "please provide visible answer" AND "please summarize"

        Clearing the stale instructions in step 2 prevents this.

  [FIX #5] CORRECTED: Item 3 (Budget interaction with failover)

  3. Budget interaction with failover (Steps 8-10)
     RISK: When a FailoverError triggers mid-run, the budget state may be
     inconsistent (partially consumed).

     [FIX #5] CORRECTED BEHAVIOR: The budget RESETS on failover, not
     persists. FailoverError propagates up from the while(true) loop in
     runEmbeddedAgentInternal. The outer runEmbeddedAgent wrapper catches
     it and retries with a different model by calling
     runEmbeddedAgentInternal again. The new call creates a NEW
     IterationBudget, so the failover model gets a fresh budget.

     V3 incorrectly stated: "The budget persists across the restart,
     which is the desired behavior -- the agent has already used those
     iterations regardless of which provider served them."

     ACTUAL BEHAVIOR: Each failover retry gets a fresh budget. This is
     acceptable because:
     - Failover typically occurs due to provider errors, not productive work
     - The iterations consumed before failover were wasted (error scenarios)
     - A fresh budget for the new model ensures the agent can complete its task
     - If total-work capping across failover is needed, it should be
       implemented at the outer runEmbeddedAgent level, not inside
       runEmbeddedAgentInternal. This is out of scope for this port.
