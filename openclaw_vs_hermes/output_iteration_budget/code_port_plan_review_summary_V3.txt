FIX #1 -- MEDIUM: CoreAgentHarness has `this.session`, not `this.agent`
------------------------------------------------------------------------------

  AFFECTED: Step 6D (Map in CoreAgentHarness.createLoopConfig), Part A.5

  WHAT WAS WRONG:
    V3 plan stated: "CoreAgentHarness wraps an Agent, so it can access
    the Agent's properties" and suggested:
      onBeforeToolCallingRound: this.agent?.onBeforeToolCallingRound

    Verification against agent-harness.ts revealed:
    - CoreAgentHarness has `private session: Session` (line 223)
    - There is NO `this.agent` property on the class
    - The createLoopConfig method (lines 486-542) builds all callbacks
      from the harness's own methods (emitHook, drainQueuedMessages,
      createTurnState, etc.), not from Agent properties
    - None of the existing callback mappings read from an Agent instance

  WHY IT MATTERS:
    The suggested code `this.agent?.onBeforeToolCallingRound` will produce
    a TypeScript compile error. The primary integration path for budget
    enforcement in the harness code path is broken.

  HOW FIXED:
    Promoted the V3 plan's own fallback to the PRIMARY approach:
    1. Add `public onBeforeToolCallingRound?: (round: number) => boolean`
       as a dedicated property on CoreAgentHarness
    2. Map it directly in createLoopConfig: `onBeforeToolCallingRound:
       this.onBeforeToolCallingRound`
    3. Set from outside (attempt.ts or wherever the harness is created)

    This matches the harness's existing pattern where callbacks are
    self-contained, not read from a wrapped Agent.

FIX #2 -- MEDIUM: Missing `!timedOut` in budget exhaustion condition
------------------------------------------------------------------------------

  AFFECTED: Step 8, Item 6 (budget exhaustion detection in run.ts)

  WHAT WAS WRONG:
    V3 plan's budget exhaustion condition omitted `!timedOut`:

      if (
        iterationBudget &&
        iterationBudget.remaining <= 0 &&
        payloadCount === 0 &&
        !attempt.clientToolCalls &&
        !budgetSummaryAttempt &&
        !aborted &&
        !promptError
      )

    The analogous compaction continuation retry check (actual code at
    lines 3823-3835 of run.ts) INCLUDES `!timedOut`:

      if (
        !emptyAssistantReplyIsSilent &&
        attemptCompactionCount > 0 &&
        payloadCount === 0 &&
        !aborted &&
        !promptError &&
        !timedOut &&              // ← PRESENT in compaction check
        !attempt.clientToolCalls &&
        !attempt.yieldDetected &&
        ...
      )

  WHY IT MATTERS:
    Without `!timedOut`, a timed-out attempt where the timeout occurred
    during tool execution (timedOutDuringPrompt=false) could reach the
    budget exhaustion check. The timeout return path (lines 3628-3707)
    only fires when `timedOutDuringPrompt` is true, so tool-execution
    timeouts fall through to the retry section.

    If the budget is also exhausted at this point (budget.remaining=0,
    payloadCount=0), the budget exhaustion handler would fire instead
    of letting the existing timeout recovery mechanisms handle it.

  HOW FIXED:
    Added `!timedOut` to the budget exhaustion condition, matching the
    compaction continuation pattern.

FIX #3 -- LOW: Missing `!emptyAssistantReplyIsSilent` and
               `!attempt.yieldDetected` conditions
------------------------------------------------------------------------------

  AFFECTED: Step 8, Item 6 (budget exhaustion detection in run.ts)

  WHAT WAS WRONG:
    V3 plan's condition omitted two guards present in the analogous
    compaction continuation retry check:

    - `!emptyAssistantReplyIsSilent`: Prevents treating a successful
      silent completion (intentional no-visible-text, e.g. silent
      notification processing) as a budget exhaustion error when the
      budget coincidentally reaches 0.

    - `!attempt.yieldDetected`: Prevents treating a voluntary agent yield
      (pause for user input) as budget exhaustion when the budget
      coincidentally reaches 0.

  WHY IT MATTERS:
    Both are edge cases (budget=0 AND silent/yield), but without the
    guards, these valid completions would be incorrectly converted to
    budget exhaustion errors. The compaction continuation check guards
    against both for the same reason.

  HOW FIXED:
    Added both conditions to the budget exhaustion check.

FIX #4 -- LOW: Stale retry instructions not cleared during budget exhaustion
------------------------------------------------------------------------------

  AFFECTED: Steps 8/11 (budget exhaustion and summary injection in run.ts)

  WHAT WAS WRONG:
    When budget exhaustion triggers the summary flow (forceSummaryOnExhaustion
    = true), the V3 plan sets budgetExhaustedSummaryInstruction but does not
    clear the other retry instruction variables:
    - reasoningOnlyRetryInstruction
    - emptyResponseRetryInstruction
    - compactionContinuationRetryInstruction

    These variables might still hold values from previous retry iterations.
    The promptAdditions filter (lines 1934-1940) would include ALL non-null
    instructions in the summary attempt's prompt.

  WHY IT MATTERS:
    If a reasoning-only or empty-response retry occurred before budget
    exhaustion, the summary attempt's prompt would include BOTH the budget
    summary instruction AND the stale retry instruction:
    - "please provide a visible answer" (stale)
    - "you've reached the budget limit, please summarize" (new)

    These are redundant at best and contradictory at worst.

  HOW FIXED:
    Added explicit nulling of all three retry instruction variables when
    setting the budget summary instruction:
      reasoningOnlyRetryInstruction = null;
      emptyResponseRetryInstruction = null;
      compactionContinuationRetryInstruction = null;


------------------------------------------------------------------------------
FIX #5 -- LOW: FailoverError budget persistence claim incorrect
------------------------------------------------------------------------------

  AFFECTED: Risk Analysis C.3, item 3 (Budget interaction with failover)

  WHAT WAS WRONG:
    V3 plan stated: "FailoverError causes the entire run to restart with a
    new provider. The budget persists across the restart, which is the
    desired behavior -- the agent has already used those iterations
    regardless of which provider served them."

    This is factually incorrect. FailoverError propagates up from the
    while(true) loop inside runEmbeddedAgentInternal(). The outer
    runEmbeddedAgent() function (line 602) catches it and retries by
    calling runEmbeddedAgentInternal() again. The new call creates a
    NEW IterationBudget, so the budget RESETS on failover.

  WHY IT MATTERS:
    The documentation gives wrong guidance about failover behavior. An
    implementer relying on this claim might skip adding cross-failover
    budget tracking if it were needed. In practice, the actual behavior
    (fresh budget per failover) is acceptable for this feature.

  HOW FIXED:
    Corrected the risk analysis to state that the budget resets on failover,
    not persists. Documented why the reset behavior is acceptable.


------------------------------------------------------------------------------
FIX #6 -- LOW: Harness instance access from attempt.ts underspecified
------------------------------------------------------------------------------

  AFFECTED: Step 7, item 2 (Thread callback to harness)

  WHAT WAS WRONG:
    V3 plan said to set `harness.onBeforeToolCallingRound` from attempt.ts,
    but did not explain how to obtain the harness instance. The harness is
    created inside runAgentHarnessAttempt (the function that backend.ts
    delegates to), which is likely in the agent-core harness package.
    attempt.ts does not have direct access to the harness.

  WHY IT MATTERS:
    An implementer following Step 7 item 2 literally would find there is
    no `harness` variable in scope in attempt.ts.

  HOW FIXED:
    Provided two concrete approaches:
    (a) PREFERRED: Modify runAgentHarnessAttempt to read
        onBeforeToolCallingRound from the attempt params and set it
        on the harness instance after creation.
    (b) ALTERNATIVE: If only Agent.createLoopConfig is invoked (not the
        harness's), then only setting it on activeSession.agent is needed.
    Added grep guidance for finding runAgentHarnessAttempt's definition.

ITERATION 1 -- V1 (Original Plan)
-----------------------------------
  Generated an 11-step porting plan. Core design decisions were sound:
  - IterationBudget as a simple class (correct)
  - Budget orthogonal to existing loop detection (correct)
  - Config-driven rollback via enabled flag (correct)
  - No threading.Lock for Node.js (correct)

  However, several assumptions about OpenClaw's internals were wrong:
  - Assumed ChatMessage type exists (it doesn't)
  - Assumed error.kind accepts any string (it's a union)
  - Assumed run.ts accesses diagnostic session state (it doesn't)
  - Assumed resolveAgentConfig auto-discovers new fields (it doesn't)
  - Proposed impractical callback for summary LLM call

  Scope: ~400 lines across 12 files
