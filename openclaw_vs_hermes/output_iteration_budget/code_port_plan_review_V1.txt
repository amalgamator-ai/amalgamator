A.1  WHAT WE PORT (IN SCOPE)
─────────────────────────────

  1. IterationBudget class
     - Per-agent iteration counter with consume()/refund()/used/remaining
     - Adapted from: agent/iteration_budget.py (62 lines)
     - This is the core high-impact module

  2. Budget-aware loop condition
     - Integrate budget.consume() into run.ts outer loop
     - Differentiate productive iterations from retry iterations
     - Budget checks complement (not replace) existing runLoopIterations guard

  3. Budget-exhaustion forced summary
     - When budget exhausted → set a flag → next loop iteration injects a
       summary request with tools stripped → return that response
     - Adapted from: agent/chat_completion_helpers.py (handle_max_iterations)
     - [FIX #8] Uses in-loop summary approach, not callback abstraction

  4. Configuration
     - Add maxIterations to AgentDefaultsConfig (default: 90)
     - Add per-agent override in AgentConfig
     - [FIX #6] Defer subagentMaxIterations to V2; use per-agent config
       for subagent budgets instead (each agent ID can have its own
       iterationBudget.maxIterations)

  5. Budget refund for compaction restarts
     - Compaction restarts are not "productive" iterations → refund
     - Aligns with Hermes's refund-on-compression-restart logic

  6. Observability
     - [FIX #3] Add budget metadata to EmbeddedAgentRunResult.meta
       (NOT to diagnostic session state, which run.ts cannot access)

  7. Enable tool loop detection warnings by default
     - Change default from enabled: false → enabled: true (warnings only)
     - Aligns with Hermes's "warnings always-on" design principle


A.2  WHAT WE DON'T PORT (OUT OF SCOPE)
────────────────────────────────────────

  1. ToolCallGuardrailController
     - OpenClaw already has tool-loop-detection.ts with 5 detector kinds
     - Different architecture (sliding window vs per-turn state machine)
     - Both are valid approaches; no need to replace

  2. Threading/Lock semantics
     - Node.js is single-threaded — no threading.Lock needed

  3. Grace call mechanism
     - Hermes's _budget_grace_call adds one extra iteration after exhaustion
     - We achieve the same effect via the in-loop budget-exhaustion summary
       which allows one more iteration (the summary call)

  4. execute_code refund
     - OpenClaw has no equivalent "execute_code" tool; skip for V1

  5. Kanban worker integration
     - OpenClaw has no equivalent kanban/task queue system; skip for V1

  6. Config ghost detection (hermes doctor)
     - Not relevant to OpenClaw's config system; skip

  7. [FIX #6] subagentMaxIterations as a separate config field
     - Deferred to V2. In V1, subagent budget is controlled per-agent:
       each subagent agent ID can have its own iterationBudget.maxIterations
       via the agents.list[] config. This is more flexible than a single
       global subagent default and aligned with OpenClaw's existing per-agent
       config model.

  8. [FIX #4] Budget preservation across FailoverError
     - FailoverError propagates outside run.ts; re-invocation resets budget.
     - Accepted limitation for V1. Documented in risk analysis.
     - V2 can pass budget state through RunEmbeddedAgentParams if needed.

STEP 1: Create IterationBudget class
────────────────────────────────────────────────────────────────────────────────

  TARGET FILE (NEW):
    src/agents/iteration-budget.ts

  DESCRIPTION:
    Create the core IterationBudget class — a simple counter that tracks how
    many productive LLM API calls an agent has made in the current run, with
    consume/refund semantics. This is a direct TypeScript adaptation of
    Hermes's agent/iteration_budget.py (62 lines) minus the threading.Lock.

  IMPLEMENTATION:

    /**
     * Per-agent iteration budget — counts productive LLM API calls.
     *
     * Each agent run (parent or subagent) gets its own IterationBudget.
     * The budget is capped at `maxIterations` (default 90 for parent
     * agents; configurable per agent via agents.list[].iterationBudget).
     *
     * Compaction-restart iterations are refunded via {@link refund} so
     * they don't eat into the budget.
     *
     * Ported from Hermes: agent/iteration_budget.py
     */
    export class IterationBudget {
      readonly maxTotal: number;
      private _used: number = 0;

      constructor(maxTotal: number) {
        this.maxTotal = Math.max(1, Math.floor(maxTotal));
      }

      /** Try to consume one iteration. Returns true if allowed. */
      consume(): boolean {
        if (this._used >= this.maxTotal) {
          return false;
        }
        this._used += 1;
        return true;
      }

      /** Give back one iteration (e.g. for compaction restarts). */
      refund(): void {
        if (this._used > 0) {
          this._used -= 1;
        }
      }

      /** Number of iterations consumed so far. */
      get used(): number {
        return this._used;
      }

      /** Number of iterations remaining before budget exhaustion. */
      get remaining(): number {
        return Math.max(0, this.maxTotal - this._used);
      }
    }

  NOTES:
    - No threading.Lock — Node.js is single-threaded
    - maxTotal is floored and clamped to >= 1 for safety
    - Uses TypeScript getter properties (get used, get remaining) matching
      Python @property pattern
    - Named export (not default) following OpenClaw convention
    - File uses kebab-case matching OpenClaw's naming convention
      (e.g., tool-loop-detection.ts, stable-stringify.ts)

       * Resolves the effective iteration budget configuration for an agent run.
       * Per-agent config (merged by resolveAgentConfig) overrides global defaults;
       * missing fields fall back to hardcoded defaults.
       *
       * Follows the same resolution pattern as resolveMaxRunRetryIterations().
       */
      export function resolveIterationBudgetConfig(
        cfg?: OpenClawConfig,
        agentId?: string,
      ): ResolvedIterationBudget {
        const configBudget =
          (cfg && agentId
            ? resolveAgentConfig(cfg, agentId)?.iterationBudget
            : undefined) ?? cfg?.agents?.defaults?.iterationBudget;

        return {
          enabled: configBudget?.enabled ?? true,
          maxIterations: Math.max(
            1,
            configBudget?.maxIterations ?? DEFAULT_MAX_ITERATIONS,
          ),
          forceSummaryOnExhaustion:
            configBudget?.forceSummaryOnExhaustion ?? true,
        };
      }

  NOTES:

      1. resolveAgentConfig(cfg, agentId) → already-merged per-agent config
      2. ?? cfg.agents.defaults.iterationBudget → global fallback
      3. ?? hardcoded defaults
    - Math.max(1, ...) clamping ensures maxIterations is always >= 1
    - resolveAgentConfig is already imported in this file (line 8)

STEP 7: Add budget-exhaustion result builder
────────────────────────────────────────────────────────────────────────────────

  TARGET FILE (NEW):
    src/agents/embedded-agent-runner/run/budget-exhaustion.ts

  DESCRIPTION:
    Simple function that builds an EmbeddedAgentRunResult for budget
    exhaustion cases. Used when forceSummaryOnExhaustion is disabled
    (returns an error immediately) or when the summary call itself fails.

    [FIX #1] Uses correct types — no ChatMessage (which doesn't exist).
    [FIX #8] Removed makeCompletionCall callback — summary logic is handled
    in-loop (Step 9) rather than via a callback abstraction.
    [FIX #12] Follows handleRetryLimitExhaustion() pattern closely.

  IMPLEMENTATION:

    import type {
      EmbeddedAgentMeta,
      EmbeddedAgentRunResult,
      EmbeddedRunLivenessState,
    } from "../types.js";
    import type { IterationBudget } from "../../iteration-budget.js";

    /**
     * Builds a terminal EmbeddedAgentRunResult for iteration budget exhaustion.
     *
     * Called when:
     * 1. Budget exhausted and forceSummaryOnExhaustion is disabled → returns error
     * 2. Budget exhausted and the forced summary call itself failed → fallback error
     *
     * Follows the same return pattern as handleRetryLimitExhaustion().
     */
    export function buildBudgetExhaustionResult(params: {
      budget: IterationBudget;
      durationMs: number;
      agentMeta: EmbeddedAgentMeta;
      livenessState?: EmbeddedRunLivenessState;
      summaryError?: unknown;
    }): EmbeddedAgentRunResult {
      const { budget, durationMs, agentMeta, livenessState, summaryError } =
        params;

      const text = summaryError
        ? `I reached the maximum iterations (${budget.maxTotal}) ` +
          `but couldn't summarize. Error: ${String(summaryError)}`
        : `Iteration budget exhausted ` +
          `(${budget.used}/${budget.maxTotal} productive iterations). ` +
          `Please try again with a simpler request, or increase ` +
          `agents.defaults.iterationBudget.maxIterations in your config.`;

      return {
        payloads: [{ text, isError: true }],
        meta: {
          durationMs,
          agentMeta,
          ...(livenessState ? { livenessState } : {}),
          error: {
            kind: "budget_exhausted",
            message: `Budget exhausted: ${budget.used}/${budget.maxTotal}`,
          },
        },
      };
    }

  NOTES:
    - Mirrors the structure of handleRetryLimitExhaustion() in retry-limit.ts
    - No async — this is a pure result builder
    - summaryError parameter handles the fallback case when the in-loop
      summary attempt fails (Step 9)
    - Returns isError: true so downstream knows it's an error condition

  INTEGRATION STRATEGY:

    The approach is "consume at loop top for the PREVIOUS iteration's
    productivity" rather than "consume inline." This has key advantages:

    - Single consumption point (loop top) — easy to audit
    - Productive flag is set at specific known points — easy to identify
    - All 22 `continue` paths that are retries DON'T set the flag,
      so they never consume budget
    - No need to modify any existing retry paths
    - The flag naturally resets (set to false after consumption)

    Which iterations consume budget?
    - Tool-call response processed → YES (productive)
    - Final text response → NO (this is the result, not a turn)
    - Rate limit retry → NO (continue without flag)
    - Compaction restart → NO (continue without flag, also refunded in Step 10)
    - Reasoning-only retry → NO (continue without flag)
    - Empty response retry → NO (continue without flag)
    - Auth rotation → NO (continue without flag)
    - Any error recovery → NO (continue without flag)

        expect(budget.consume()).toBe(true);   // 1/3

        expect(budget.consume()).toBe(true);   // 3/3

        const budget = new IterationBudget(2);
        expect(budget.consume()).toBe(true);   // 1/2

        expect(budget.consume()).toBe(false);  // exhausted

        expect(budget.consume()).toBe(false);  // exhausted again
      });

        const budget = new IterationBudget(5);
        budget.refund();  // Nothing consumed yet
        budget.refund();
        expect(budget.used).toBe(0);
        expect(budget.remaining).toBe(5);
      });

      test("used reflects consume and refund accurately", () => {
        const budget = new IterationBudget(10);
        expect(budget.used).toBe(0);
        budget.consume();
        expect(budget.used).toBe(1);
        budget.consume();
        expect(budget.used).toBe(2);
        budget.refund();
        expect(budget.used).toBe(1);
      });

      test("remaining equals maxTotal minus used", () => {
        const budget = new IterationBudget(5);
        expect(budget.remaining).toBe(5);
        budget.consume();
        expect(budget.remaining).toBe(4);
        budget.consume();
        budget.consume();

      });

      test("maxTotal is clamped to at least 1", () => {

        expect(budget.maxTotal).toBe(1);
        expect(budget.remaining).toBe(1);
      });

      test("maxTotal is floored for fractional values", () => {
        const budget = new IterationBudget(3.7);
        expect(budget.maxTotal).toBe(3);
      });

      test("negative maxTotal is clamped to 1", () => {

C.3  KNOWN LIMITATIONS (V1)
─────────────────────────────

  1. [FIX #4] Budget lost on FailoverError
     When the run loop throws FailoverError and the outer caller re-invokes
     runEmbeddedAgent with a different model, the budget resets to full.
     This means total iterations across model failovers can exceed maxIterations.

     Impact: LOW — failover is rare, and the new model gets a fresh budget
     which is reasonable (it hasn't done any work with that model yet).

     V2 resolution: Pass budget state through RunEmbeddedAgentParams so
     failover inherits remaining budget.

  2. [FIX #6] No separate subagent budget default
     V1 uses per-agent config for subagent budgets instead of a global
     subagentMaxIterations default. Each subagent agent ID can have its
     own iterationBudget.maxIterations.

     Impact: LOW — operators who want different subagent budgets can set
     them per-agent in config. The global default of 90 applies to all
     agents equally unless overridden.

     V2 resolution: Add subagentMaxIterations to config with detection
     via the spawnedBy parameter in RunEmbeddedAgentParams.

  3. [FIX #3] No live budget tracking in diagnostic session state
     Budget usage is reported in the run result meta, not in the
     process-local diagnostic session state. This means stuck-session
     diagnostics can't see budget progress in real-time.

     Impact: LOW — the run result still reports budget usage, and
     stuck-session detection has other signals (lastActivity, toolCallHistory).

     V2 resolution: Thread diagnostic session state ref through run.ts
     params and update budget fields from the run loop.
