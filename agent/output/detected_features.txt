RANK #1: Multi-Pass Context Compaction
================================================================================
Overall Score: 8.0

Feature Name:       Multi-Pass Context Compaction
Category:           Core / Context Management

Hermes Status:      IMPLEMENTED (mature, production)
OpenClaw Status:    INADEQUATE (single-pass only)

SCORING:
  Community Demand:  8/10 (multiple high-reaction issues)
  Gap Severity:      8/10 (OpenClaw has compaction but single-pass, loses context)
  Impact:            9/10 (directly affects conversation quality for ALL users)
  Feasibility:       7/10 (OpenClaw already has compaction infrastructure to extend)
  Independence:      9/10 (self-contained improvement to existing system)

HERMES IMPLEMENTATION SUMMARY:
  Key Files:
    - agent/context_compressor.py       (1,500+ lines - multi-pass orchestrator)
    - agent/context_engine.py           (200 lines - pluggable engine ABC)
    - agent/conversation_compression.py (200 lines - high-level entry point)

  Architecture:
    - ContextCompressor.compress(messages, current_tokens): main entry
    - Multi-pass iteration: continues until token threshold met OR progress < 5%
    - Tail protection: preserves last N messages (token-budget-aware sliding)
    - Head protection: protects first N non-system messages
    - Tool result pruning: clears old tool outputs before LLM pass
    - Structured summary: SUMMARY_PREFIX prevents stale-task confusion
    - Iterative merge: new turn info merged into prior summary
    - Fallback mode: deterministic handoff when summarizer unavailable
    - Configurable: _MIN_SUMMARY_TOKENS, _SUMMARY_RATIO, _SUMMARY_TOKENS_CEILING
    - Image shrinking: try_shrink_image_parts_in_messages() for size recovery

OPENCLAW GAP DESCRIPTION:
  OpenClaw's compaction (src/agents/embedded-agent-runner/compact.runtime.ts) is
  single-pass. It runs once, generates a summary, and replaces the conversation.
  Key issues:
  - No iterative multi-pass (stops after one attempt even if still over budget)
  - No progress threshold detection (Hermes stops if <5% improvement per pass)
  - No structured summary prefix (risk of LLM resuming stale tasks)
  - Single 180s wall-clock timeout with no partial-progress reuse (#92043)
  - reserveTokens default (15000) insufficient headroom (#77780)
  - Context silently killed after compaction (#60213)
  - Issue #58398 directly requests Claude Code's multi-layer architecture

COMMUNITY EVIDENCE:
  Issue #37057 [closed] reactions=21 "feat: RTK exec proxy — compress tool output
    to save context tokens" - High demand for better context compression
  Issue #2254 [closed] reactions=20 "Large session files" - Context growth problems
  Issue #5771 [closed] reactions=11 "Context overflow error" - Overflow handling
  Issue #64250 [closed] reactions=5 "Context limit exceeded" - Recurring problem
  Issue #60213 [closed] reactions=0 comments=10 "compaction silently kills session
    — all conversation memory lost" - Quality problem
  Issue #92043 [open] reactions=2 comments=10 "180s compaction timeout...no partial-
    progress reuse" - Timeout architecture problem
  Issue #77780 [open] reactions=2 "compaction: reserveTokens default leaves
    insufficient headroom" - Configuration gap
  Issue #58398 [open] reactions=1 comments=5 "Adopt Claude Code's multi-layer
    compaction architecture" - DIRECT REQUEST for this feature
  Issue #51612 [closed] reactions=3 "Built-in persistent memory system with
    compaction tree" - Alternative approach request
  Issue #84857 [closed] reactions=4 "Compaction preflight throws error" - Bug

PORTING APPROACH:
  1. Extend existing compact.runtime.ts with multi-pass loop
  2. Add progress detection (abort if improvement < threshold per pass)
  3. Implement head/tail message protection with token budget awareness
  4. Add tool result pruning pass before LLM summarization
  5. Add summary prefix to prevent stale-task confusion
  6. Port ContextEngine ABC interface for pluggable compression engines
  7. Adapt Hermes's _MIN_SUMMARY_TOKENS, _SUMMARY_RATIO constants

RISK ASSESSMENT:
  - LOW: OpenClaw already has compaction infrastructure; this is enhancement
  - MEDIUM: Token counting accuracy must match OpenClaw's existing estimation
  - LOW: Can be A/B tested (old single-pass vs new multi-pass) via config

RANK #2: Iteration Budget & Agent Loop Safety
================================================================================
Overall Score: 7.6

Feature Name:       Iteration Budget & Agent Loop Safety
Category:           Core / Resource Management

Hermes Status:      IMPLEMENTED (production)
OpenClaw Status:    MISSING (basic loop detection only)

SCORING:
  Community Demand:  7/10 (multiple tool-loop and runaway issues)
  Gap Severity:      9/10 (missing entirely; OpenClaw has only heuristic detection)
  Impact:            8/10 (prevents runaway costs, stuck agents)
  Feasibility:       8/10 (small module, clean interfaces)
  Independence:      9/10 (standalone, no dependencies on other missing features)

HERMES IMPLEMENTATION SUMMARY:
  Key Files:
    - agent/iteration_budget.py    (62 lines - thread-safe budget)
    - agent/tool_guardrails.py     (safety guardrails controller)

  Architecture:
    - IterationBudget: shared parent/subagent counter
    - consume() -> bool: try to use one iteration
    - refund(): give back iteration (for execute_code)
    - Parent: max_iterations (default 90)
    - Subagent: delegation.max_iterations (default 50)
    - Thread-safe via threading.Lock
    - ToolCallGuardrailController: enforces execution policies (allow/defer/deny)

OPENCLAW GAP DESCRIPTION:
  OpenClaw has no explicit iteration budget. The agent loop runs until the LLM
  stops calling tools or a timeout fires. Loop detection is heuristic
  (loopDetection based on content-hash dedup, which volatile messageId defeats).
  Key issues:
  - Issue #6890: explicit request for "max iteration number in agent configuration"
  - Issue #75468: request for "general-purpose max iteration limit"
  - Issue #89090: loopDetection cannot block message tool loops
  - Issue #79301: request for tool-use loop detection (repeated writes)
  - Issue #75355: circuit breaker blocks tool but not agent turn
  - Issue #77625: feedback loop / infinite reasoning recursion

COMMUNITY EVIDENCE:
  Issue #6890 [open] reactions=3 "Add Ralph Loop feature and add max iteration
    number into the agent configuration" - DIRECT REQUEST
  Issue #75468 [closed] reactions=2 "Agent safeguards - content hash dedup for
    file writes + general-purpose max iteration limit" - DIRECT REQUEST
  Issue #89090 [closed] reactions=2 "loopDetection cannot block message tool
    loops — volatile messageId in result defeats all detection paths"
  Issue #79301 [closed] reactions=2 "Tool-use loop detection to prevent repeated
    writes to same path"
  Issue #75355 [closed] reactions=2 "Circuit breaker blocks tool but not agent
    turn; exec loop only warns, never blocks"
  Issue #77625 [open] reactions=2 "feedback loop / infinite reasoning recursion"
  Issue #74859 [open] reactions=2 "zombie Agent loop when signal is pre-aborted"
  Issue #82518 [closed] reactions=2 "Gateway OOM-killed during tool-heavy session"

PORTING APPROACH:
  1. Create packages/agent-core/iteration-budget.ts (simple counter class)
  2. Integrate with embedded agent runner's turn loop
  3. Add agents.defaults.maxIterations config option (default 90)
  4. Add per-subagent budget with agents.defaults.delegation.maxIterations
  5. Wire budget check into before-tool-call pipeline
  6. Add refund logic for code execution tools

RISK ASSESSMENT:
  - LOW: Simple standalone module with clear integration points
  - LOW: Can default to large budget (no behavior change for existing users)
  - MEDIUM: Must handle edge case where budget exhausts mid-tool-chain
