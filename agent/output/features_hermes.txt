FEATURE #1: Core Agent Conversation Loop
================================================================================
Category:       Core / Agent Runtime
Type:           Core (fundamental to operation)

Description:
    The central agent runtime that drives all conversations. The AIAgent class
    in run_agent.py (~5,600 LOC) implements a while-budget-available loop:
    call LLM, dispatch tool calls, handle results, repeat. Accepts ~60
    parameters (credentials, routing, callbacks, session context, budget).
    Exposes two interfaces: chat(message) -> str for simple use, and
    run_conversation(user_message, system_message, history, task_id) -> dict
    for the full pipeline.

Key Implementation Files:
    - run_agent.py                         (248KB, ~5,600 LOC - AIAgent class)
    - agent/agent_init.py                  (1,836 lines - __init__ extraction)
    - agent/conversation_loop.py           (2,600+ lines - main turn loop)
    - agent/turn_context.py                (490 lines - per-turn prologue)
    - agent/turn_finalizer.py              (turn cleanup, memory sync, stats)
    - agent/turn_retry_state.py            (per-turn retry counters)

Architecture Notes:
    - AIAgent.__init__ extracted to agent_init.py to reduce bloat
    - Per-turn prologue in build_turn_context(): stdio guarding, MCP tool
      refresh, surrogate sanitization, task/turn ID generation, retry counter
      resets, system prompt restore, DB session creation, crash-resilience
      persistence, preflight compression, plugin hooks, memory prefetch
    - Conversation loop handles: streaming, tool dispatch (sequential/parallel),
      retry strategies, context overflow recovery, thinking/reasoning budget,
      interrupt handling, fallback chains, response format validation
    - Messages follow OpenAI format; reasoning stored in assistant_msg["reasoning"]
    - Thread-safe interrupt mechanism via shared signals + tool worker tracking

Dependencies:
    - Provider transports (anthropic, chat_completions, bedrock, codex_responses)
    - Tool registry & executor
    - Context compressor
    - Memory manager
    - Session DB (hermes_state.py)
    - Plugin lifecycle hooks

Complexity Estimate: VERY HIGH
    Massive core file with deep integrations to every subsystem; the heart
    of the entire agent. Porting requires understanding the full call chain.

Language/Frameworks: Python, openai SDK, anthropic SDK, asyncio, threading

FEATURE #2: Context Compression System
================================================================================
Category:       Core / Context Management
Type:           Core (fundamental to operation)

Description:
    Automatic context window compression via auxiliary LLM summarization.
    When conversation history approaches the model's context limit, the
    compressor runs multi-pass compaction: protects head and tail messages,
    prunes old tool results, then summarizes the middle via an auxiliary model.
    Supports iterative updates (merging new turn info into prior summaries).

Key Implementation Files:
    - agent/context_compressor.py          (1,500+ lines - main orchestrator)
    - agent/context_engine.py              (200 lines - abstract plugin interface)
    - agent/conversation_compression.py    (200 lines - high-level orchestration)

Architecture Notes:
    - ContextCompressor class with: should_compress(prompt_tokens),
      compress(messages, current_tokens), update_from_response(usage)
    - Tail protection: preserves last N messages (token budget aware)
    - Head protection: protects first N non-system messages
    - Multi-pass: iterates until threshold met or progress < 5% per pass
    - Tool result pruning before LLM pass
    - Structured summary with SUMMARY_PREFIX to prevent stale-task confusion
    - Fallback mode: deterministic handoff when summarizer unavailable
    - ContextEngine ABC allows pluggable compression engines (compressor, LCM)
    - Abstract methods: should_compress, compress, on_session_start/end/reset
    - Optional tools: lcm_grep, lcm_describe for context engine plugins
    - compress_context() is the main entry point; handles image shrinking too
    - Constants: _MIN_SUMMARY_TOKENS, _SUMMARY_RATIO, _SUMMARY_TOKENS_CEILING

Dependencies:
    - Auxiliary LLM client (agent/auxiliary_client.py)
    - Model metadata (context length resolution)
    - Session DB for session rotation on compression

Complexity Estimate: HIGH
    Multi-pass summarization with token budgeting, tail/head protection,
    and plugin extensibility. Core algorithm is well-isolated but requires
    auxiliary LLM integration.

Language/Frameworks: Python, openai SDK

FEATURE #3: Prompt Caching (Anthropic)
================================================================================
Category:       Core / Cost Optimization
Type:           Core (fundamental to operation)

Description:
    Implements Anthropic's prompt caching strategy (system_and_3 layout) that
    reduces input token costs by ~75% on multi-turn conversations. Places
    cache_control breakpoints on the system prompt plus the last 3 non-system
    messages. Supports 5-minute (1.25x cost) and 1-hour (2x cost) TTLs.

Key Implementation Files:
    - agent/prompt_caching.py              (80 lines)

Architecture Notes:
    - apply_anthropic_cache_control(messages, cache_ttl, native_anthropic)
    - 4 cache breakpoints: system prompt + last 3 non-system messages
    - TTL options: "5m" (default) or "1h" (amortizes across pauses)
    - Transparent: inserted as message-level or block-level cache_control field
    - SACRED DESIGN PROPERTY: per-conversation prompt caching must not break;
      never mutate past context, swap toolsets, or rebuild system prompts
      mid-conversation (only exception: context compression)
    - Slash commands mutating system-prompt state must default to deferred
      invalidation with optional --now flag

Dependencies:
    - Anthropic provider transport
    - System prompt builder (stable prefix)

Complexity Estimate: LOW
    Small, focused module. Concept is simple but the invariant (never break
    cache) has deep implications across the entire codebase.

Language/Frameworks: Python, anthropic SDK

FEATURE #4: System Prompt Builder (3-Tier Architecture)
================================================================================
Category:       Core / Prompt Engineering
Type:           Core (fundamental to operation)

Description:
    Assembles the system prompt from three tiers: Stable (identity, tool
    guidance, skills index, environment hints), Context (context files like
    AGENTS.md/.cursorrules + caller system_message), and Volatile (memory
    snapshot, USER.md, external memory provider block, timestamp). Built once
    per session and cached for prefix cache warmth across turns.

Key Implementation Files:
    - agent/system_prompt.py               (500+ lines - 3-tier assembly)
    - agent/prompt_builder.py              (1,000+ lines - fragment generators)

Architecture Notes:
    - build_system_prompt_parts(agent, system_message) -> {stable, context, volatile}
    - build_system_prompt(agent, system_message) -> concatenated string
    - restore_or_build_system_prompt() -> use cached or rebuild
    - Stable tier: DEFAULT_AGENT_IDENTITY, HERMES_AGENT_HELP_GUIDANCE,
      MEMORY_GUIDANCE, SESSION_SEARCH_GUIDANCE, SKILLS_GUIDANCE,
      KANBAN_GUIDANCE, TASK_COMPLETION_GUIDANCE, PARALLEL_TOOL_CALL_GUIDANCE,
      TOOL_USE_ENFORCEMENT_GUIDANCE
    - Context tier: context files discovery (AGENTS.md, .cursorrules, CLAUDE.md),
      platform hints per messaging platform
    - Volatile tier: memory snapshot, USER.md, external memory block, timestamp
    - load_soul_md() loads ~/.hermes/SOUL.md for primary identity/persona
    - build_environment_hints() probes Python/Node.js/Ruby toolchain versions
    - build_context_files_prompt() discovers project context files
    - PLATFORM_HINTS dict for Telegram, Discord, WhatsApp, Slack, etc.
    - Invariant: only rebuilt on session start or after context compression

Dependencies:
    - Memory manager (volatile tier)
    - Skills system (skills index in stable tier)
    - Configuration (persona, platform hints)
    - Context file discovery

Complexity Estimate: MEDIUM
    Well-structured but many fragments to assemble. Platform hints and
    context file discovery add breadth.

Language/Frameworks: Python

      stepfun, xai, xiaomi, zai

      Gemini thinking_config translation)
    - Model metadata fallback chain: models.dev hardcoded -> provider /models API

FEATURE #7: Error Classification & Fallback Chains
================================================================================
Category:       Core / Reliability
Type:           Core (fundamental to operation)

Description:
    Classifies API errors by type (rate_limit, model_overloaded, auth,
    malformed_response, etc.) and recommends retry/fallback actions. Implements
    decorrelated jittered exponential backoff. Supports ordered fallback chains
    that automatically switch providers on rate-limit/exhaustion.

Key Implementation Files:
    - agent/error_classifier.py            (400+ lines)
    - agent/retry_utils.py                 (130 lines)
    - hermes_cli/fallback_config.py        (fallback model chain config)

Architecture Notes:
    - ClassifiedError: error + reason (FailoverReason enum) + recommended_fallback
    - FailoverReason: rate_limit, model_overloaded, malformed_response, auth, etc.
    - classify_api_error(): classifies by HTTP status, error code, body text
    - Provider-specific: OpenAI 429/503, Anthropic 529/401, OpenRouter headers,
      Bedrock model_not_found/throttling, Z.AI Coding Plan 429s
    - jittered_backoff(): decorrelated jitter with atomic counter seed
    - adaptive_rate_limit_backoff(): Z.AI-specific progressive waits (30s->120s)
    - Fallback chains: ordered list of backup providers, activated on exhaustion
    - is_zai_coding_overload_error(): detect Z.AI Coding Plan 429s

Dependencies:
    - Provider transports (error sources)
    - Agent conversation loop (retry consumer)

Complexity Estimate: MEDIUM
    Error classification is well-encapsulated. Provider-specific patterns
    need per-provider knowledge but the framework is clean.

Language/Frameworks: Python

FEATURE #8: Streaming & Response Handling
================================================================================
Category:       Core / UX
Type:           Core (fundamental to operation)

Description:
    Token-by-token streaming from LLM providers with live text assembly,
    stateful scrubbers for split content blocks (thinking tags, memory context
    fences), and progressive message updates across all platforms. Supports
    streaming transports: edit (progressive message edits), draft (native
    animated preview on Telegram), and auto (prefer draft, fallback to edit).

Key Implementation Files:
    - agent/conversation_loop.py           (_stream_response, _interruptible_api_call)
    - agent/think_scrubber.py              (StreamingThinkScrubber)
    - agent/memory_manager.py              (StreamingContextScrubber)
    - gateway/stream_consumer.py           (GatewayStreamConsumer)
    - gateway/stream_events.py             (structured stream event types)
    - gateway/stream_dispatch.py           (stream routing)

Architecture Notes:
    - _stream_response(): processes token-by-token from provider, fires callbacks
    - StreamingThinkScrubber: stateful tag scrubber for <think> blocks split
      across streaming deltas
    - StreamingContextScrubber: scrubs <memory-context> fences split across deltas
    - GatewayStreamConsumer: bridges sync agent callbacks to async platform edits
    - Buffering: accumulates text, respects edit interval (default 0.6s)
    - Rate limiting: configurable edit interval, buffer threshold (100 chars)
    - Cursor animation: "..." cursor appended during streaming
    - Fresh final: optionally sends fresh message instead of final edit
    - Stream events: MessageChunk, MessageStop, Commentary, ToolCallChunk

Dependencies:
    - Provider transports (streaming source)
    - Platform adapters (edit_message support)
    - Agent display (CLI streaming)

Complexity Estimate: HIGH
    Stateful streaming across sync/async boundaries with platform-specific
    behavior. Split-tag scrubbers are particularly tricky.

Language/Frameworks: Python, asyncio, threading

FEATURE #10: Tool Execution Engine

    gating. Determines which tools can safely run in parallel (read-only tools,

    ThreadPoolExecutor. Includes middleware hooks, interrupt support, and
    per-context-window result budgeting.

Key Implementation Files:
    - agent/tool_executor.py               (1,000+ lines)
    - agent/tool_dispatch_helpers.py        (500+ lines)
    - agent/tool_guardrails.py             (safety guardrails)
    - agent/tool_result_classification.py   (result categorization)

Architecture Notes:
    - execute_tool_calls_sequential(): one at a time
    - execute_tool_calls_concurrent(): parallel with ThreadPoolExecutor(max_workers=8)
    - _should_parallelize_tool_batch(): safety gating
    - _NEVER_PARALLEL_TOOLS: clarify (interactive)
    - _PARALLEL_SAFE_TOOLS: read-only (web_search, read_file, skill_view, etc.)
    - _PATH_SCOPED_TOOLS: read_file, write_file, patch (safe if different paths)
    - _DESTRUCTIVE_PATTERNS: rm, cp, mv, sed -i, git reset, etc.
    - _budget_for_agent(): scale result budget to context window
    - _apply_tool_request_middleware_for_agent(): plugin middleware hooks
    - make_tool_result_message(): construct tool result message dict
    - _extract_file_mutation_targets(): per-turn file verifier inputs
    - _trajectory_normalize_msg(): strip image blobs for trajectory saving
    - ToolCallGuardrailController: enforces execution policies (allow/defer/deny)

Dependencies:
    - Tool registry
    - Agent conversation loop
    - File safety (write-denied paths)
    - Plugin hooks (pre/post_tool_call)

Complexity Estimate: HIGH
    Parallelism safety gating with path overlap detection, interrupt handling,
    and middleware chains. The concurrent execution model is well-isolated
    but requires careful testing.

Language/Frameworks: Python, concurrent.futures

FEATURE #13: Webhook System
================================================================================
Category:       Communication / Messaging
Type:           Integration (connects to external systems)

Description:
    Generic inbound webhook receiver that accepts HTTP requests, validates
    HMAC signatures, renders payloads through Jinja2 prompt templates, and
    routes to the agent or directly delivers to messaging platforms. Supports
    dynamic routes, idempotency, rate limiting, profile multiplexing, and
    deliver-only mode (zero LLM cost).

Key Implementation Files:
    - gateway/platforms/webhook.py         (WebhookAdapter)

Architecture Notes:
    - aiohttp.web.TCPSite listening on configurable host:port (default 0.0.0.0:8644)
    - Per-route HMAC secrets or global secret
    - Dynamic routes loaded from YAML config at startup
    - Idempotency: TTL cache prevents duplicate runs on webhook retries
    - Rate limiting: fixed-window per-route (configurable, default 30/min)
    - Profile multiplexing: /p/{profile}/hook/{name} URL structure
    - Prompt templates: Jinja2-style formatting of webhook payload
    - Deliver-only mode: skip agent, deliver rendered prompt directly
    - Cross-platform delivery: routes responses to Telegram/Discord/Slack etc.
    - Events filtering: only process specified event types per route

Dependencies:
    - Gateway infrastructure
    - Jinja2 template engine
