PART A -- SCOPE & STRATEGY

A.1  WHAT WE PORT (IN SCOPE)
-----------------------------

  1. IterationBudget class
     - Per-agent iteration counter with consume()/refund()/used/remaining
     - Adapted from: agent/iteration_budget.py (62 lines)
     - This is the core high-impact module

  2. Budget-aware inner loop termination
     - Thread a budget callback from run.ts -> attempt.ts -> agent-core
     - The agent-core inner loop (agent-loop.ts) calls the callback before
       each tool-calling round. If the budget is exhausted, the loop stops.
     - Budget checks complement (not replace) existing loop guards

  3. Budget-exhaustion forced summary
     - When budget exhausts -> attempt returns with budgetExhausted flag ->
       run.ts injects a summary prompt + limits to 1 round -> returns result
     - Adapted from: agent/chat_completion_helpers.py (handle_max_iterations)

  4. Configuration
     - Add maxIterations to AgentDefaultsConfig (default: 90)
     - Add per-agent override in AgentConfig
     - Subagent budgets controlled per-agent via agents.list[].iterationBudget

  5. Budget refund for compaction restarts
     - When the outer run.ts loop compacts context and retries, refund 1
       iteration for the interrupted round
     - Aligns with Hermes's refund-on-compression-restart logic

  6. Observability
     - Add budgetUsed/budgetMax to EmbeddedAgentRunMeta
     - Populated from the IterationBudget instance in the final result

  7. Enable tool loop detection warnings by default
     - Change default from enabled: false -> enabled: true (warnings only)
     - Aligns with Hermes's "warnings always-on" design principle


A.2  WHAT WE DON'T PORT (OUT OF SCOPE)
----------------------------------------

  1. ToolCallGuardrailController
     - OpenClaw has tool-loop-detection.ts with 5 detector kinds
     - Different architecture (sliding window vs per-turn state machine)
     - Both are valid approaches; no need to replace

  2. Threading/Lock semantics
     - Node.js is single-threaded -- no threading.Lock needed

  3. Grace call mechanism
     - Hermes's _budget_grace_call adds one extra iteration after exhaustion
     - We achieve the same effect via the in-loop budget-exhaustion summary
       which allows one more LLM round (the summary call) with tools limited

  4. execute_code refund
     - OpenClaw has no equivalent "execute_code" tool; skip for V1

  5. Kanban worker integration
     - OpenClaw has no equivalent kanban/task queue system; skip

  6. subagentMaxIterations as a separate config field
     - Deferred to V2. In V1, subagent budget is controlled per-agent:
       each subagent agent ID can have its own iterationBudget.maxIterations
       via the agents.list[] config.

  7. Budget preservation across FailoverError
     - FailoverError propagates outside run.ts; re-invocation resets budget.
     - Accepted limitation. Documented in risk analysis.

  8. Live budget tracking in diagnostic session state
     - Budget usage is reported in the run result meta only.
     - Diagnostic session state integration deferred for simplicity.

A.5  CRITICAL ARCHITECTURAL FINDING (V2-only)
-----------------------------------------------

  V1 assumed the tool-calling iteration loop was in run.ts (the outer
  while(true) loop). This is WRONG.

  OpenClaw has a TWO-LEVEL LOOP ARCHITECTURE:

    OUTER LOOP (run.ts, while(true)):
      - Handles retries, compaction, auth rotation, failover
      - Each iteration dispatches ONE ATTEMPT via runEmbeddedAttemptWithBackend
      - MAX_RUN_LOOP_ITERATIONS guards against retry storms
      - All 18 `continue` paths are for error recovery
      - The final return at line 4075 is the only success exit

    INNER LOOP (agent-core/agent-loop.ts, while(hasMoreToolCalls)):
      - Handles the agentic tool-calling cycle
      - Each iteration: streamAssistantResponse -> executeToolCalls -> repeat
      - This is where the model iterates: LLM -> tools -> LLM -> tools -> ...
      - The loop stops when the model produces text (no more tool calls)
      - No existing iteration budget or cap

  The call chain:
    run.ts
     -> runEmbeddedAttemptWithBackend()   [run/backend.ts]
       -> runEmbeddedAttempt()            [run/attempt.ts, ~5800 lines]
         -> promptActiveSession()         [wraps activeSession.prompt()]
           -> agent.prompt()              [agent-core/agent.ts]
             -> runPromptMessages()
               -> runAgentLoop()          [agent-core/agent-loop.ts]
                 -> while(hasMoreToolCalls) {  <-- THE REAL LOOP
                      streamAssistantResponse()  // LLM call
                      executeToolCalls()          // tool execution
                    }

  CONSEQUENCE FOR BUDGET:
    Counting outer-loop (run.ts) iterations would be nearly useless:
    - A normal request typically runs 1 outer iteration
    - All the tool-calling rounds happen inside agent-core's inner loop
    - MAX_RUN_LOOP_ITERATIONS (default 32-160) already caps the outer loop

    The iteration budget MUST be threaded into the inner loop via a
    callback. The IterationBudget instance lives in run.ts (persisting
    across attempts), but its consume() is called from within agent-core's
    loop via a callback closure.

  WHY V1 MISSED THIS:
    The V1 plan assumed run.ts's while(true) was the tool-calling loop,
    likely because:
    - run.ts is ~4100 lines with 18 continue paths -- looks like a busy loop
    - The code trace described it as the "main loop"
    - agent-core is in a separate package (packages/agent-core)
    - attempt.ts is ~5800 lines -- the inner loop is deeply nested

  V2 APPROACH:
    1. Add a lightweight callback (onBeforeToolCallingRound) to AgentLoopConfig
    2. The callback is a closure over run.ts's IterationBudget instance
    3. agent-loop.ts calls it before each inner-loop round
    4. If budget.consume() returns false, the loop breaks
    5. run.ts detects exhaustion via budget.remaining <= 0 after attempt return
    6. run.ts handles summary injection at the outer-loop level

    This keeps IterationBudget in the main source (no agent-core dependency
    on internal types) and adds only ~10 lines to agent-core.

STEP 1: Create IterationBudget class
--------------------------------------------------------------------------------

  TARGET FILE (NEW):
    src/agents/iteration-budget.ts

  DESCRIPTION:
    Create the core IterationBudget class -- a simple counter that tracks how
    many productive LLM API calls an agent has made in the current run, with
    consume/refund semantics. This is a direct TypeScript adaptation of
    Hermes's agent/iteration_budget.py (62 lines) minus the threading.Lock.

  IMPLEMENTATION:

    /**
     * Per-agent iteration budget -- counts productive LLM API calls.
     *
     * Each agent run (parent or subagent) gets its own IterationBudget.
     * The budget is capped at `maxIterations` (default 90 for parent
     * agents; configurable per agent via agents.list[].iterationBudget).
     *
     * Compaction-restart iterations are refunded via {@link refund} so
     * they don't eat into the budget.
     *
     * Ported from Hermes: agent/iteration_budget.py
     */
    export class IterationBudget {
      readonly maxTotal: number;
      private _used: number = 0;

      constructor(maxTotal: number) {
        this.maxTotal = Math.max(1, Math.floor(maxTotal));
      }

      /** Try to consume one iteration. Returns true if allowed. */
      consume(): boolean {
        if (this._used >= this.maxTotal) {
          return false;
        }
        this._used += 1;
        return true;
      }

      /** Give back one iteration (e.g. for compaction restarts). */
      refund(): void {
        if (this._used > 0) {
          this._used -= 1;
        }
      }

      /** Number of iterations consumed so far. */
      get used(): number {
        return this._used;
      }

      /** Number of iterations remaining before budget exhaustion. */
      get remaining(): number {
        return Math.max(0, this.maxTotal - this._used);
      }
    }

  NOTES:
    - No threading.Lock -- Node.js is single-threaded
    - maxTotal is floored and clamped to >= 1 for safety
    - Uses TypeScript getter properties (get used, get remaining)
    - Named export (not default) following OpenClaw convention
    - File uses kebab-case matching OpenClaw naming (tool-loop-detection.ts)

       * Resolves the effective iteration budget for an agent run.

       * defaults; missing fields fall back to hardcoded defaults.
       *
       * Follows the same resolution pattern as resolveMaxRunRetryIterations().
       */
      export function resolveIterationBudgetConfig(
        cfg?: OpenClawConfig,
        agentId?: string,
      ): ResolvedIterationBudget {
        const configBudget =
          (cfg && agentId
            ? resolveAgentConfig(cfg, agentId)?.iterationBudget
            : undefined) ?? cfg?.agents?.defaults?.iterationBudget;

        return {
          enabled: configBudget?.enabled ?? true,
          maxIterations: Math.max(
            1,
            configBudget?.maxIterations ?? DEFAULT_MAX_ITERATIONS,
          ),
          forceSummaryOnExhaustion:
            configBudget?.forceSummaryOnExhaustion ?? true,
        };
      }

  NOTES:
    - Resolution chain mirrors resolveMaxRunRetryIterations() exactly
    - Math.max(1, ...) clamping ensures maxIterations is always >= 1
    - resolveAgentConfig is already imported in this file

  TARGET FILE (MODIFY):
    packages/agent-core/src/agent-loop.ts

  DESCRIPTION:
    Add iteration counting and budget callback invocation to the inner
    while(hasMoreToolCalls) loop. This is the minimal change to agent-core.

  CHANGES:

    1. Inside runAgentLoop(), before the inner while loop (~line 310),
       add a counter:

      let toolCallingRound = 0;

    2. At the TOP of the inner while loop body (~line 311), BEFORE
       streamAssistantResponse is called, add:

      toolCallingRound += 1;
      if (
        config.onBeforeToolCallingRound &&
        !config.onBeforeToolCallingRound(toolCallingRound)
      ) {
        // Caller-signaled stop (e.g. budget exhausted)
        hasMoreToolCalls = false;
        break;
      }

    NOTE ON CALLBACK PLACEMENT:
      The callback is called BEFORE each LLM call, not after. This means:
      - Round 1: callback(1) -> if false, NO LLM call -> loop exits
      - Round N: callback(N) -> if false, NO LLM call -> loop exits

      This matches Hermes's budget.consume() at the TOP of the loop.
      When the budget is exhausted, the loop stops BEFORE making another
      LLM call, preventing wasted API calls.

    3. The counter resets to 0 for each outer-loop iteration (follow-up
       messages). This is fine because the budget callback captures the
       IterationBudget via closure, and the IterationBudget maintains
       cumulative state across all rounds and attempts.

  TOTAL AGENT-CORE CHANGE: ~10 lines (1 type field + 6 lines of logic)

  NOTES:
    - The callback is synchronous (returns boolean, not Promise<boolean>)
      because budget.consume() is a synchronous operation. This avoids
      adding async overhead to the hot loop.
    - The callback is optional -- existing callers are unaffected.
    - If the callback is not provided, the loop behaves exactly as before.
    - The round parameter is informational; the actual budget logic is in
      the closure (the IterationBudget instance in run.ts).

  TARGET FILE (NEW):
    src/agents/embedded-agent-runner/run/budget-exhaustion.ts

  DESCRIPTION:
    Simple function that builds an EmbeddedAgentRunResult for budget
    exhaustion cases. Used when forceSummaryOnExhaustion is disabled
    or when the summary call fails.

    Mirrors the structure of handleRetryLimitExhaustion() in retry-limit.ts

  IMPLEMENTATION:

    import type {
      EmbeddedAgentMeta,
      EmbeddedAgentRunResult,
      EmbeddedRunLivenessState,
    } from "../types.js";
    import type { IterationBudget } from "../../iteration-budget.js";

    /**
     * Builds a terminal EmbeddedAgentRunResult for iteration budget
     * exhaustion.
     *
     * Called when:
     * 1. Budget exhausted + forceSummaryOnExhaustion disabled -> error
     * 2. Budget exhausted + forced summary call failed -> fallback error
     *
     * Follows the same return pattern as handleRetryLimitExhaustion().
     */
    export function buildBudgetExhaustionResult(params: {
      budget: IterationBudget;
      durationMs: number;
      agentMeta: EmbeddedAgentMeta;
      livenessState?: EmbeddedRunLivenessState;
      summaryError?: unknown;
    }): EmbeddedAgentRunResult {
      const { budget, durationMs, agentMeta, livenessState, summaryError } =
        params;

      const text = summaryError
        ? `I reached the maximum iterations (${budget.maxTotal}) ` +
          `but couldn't summarize. Error: ${String(summaryError)}`
        : `Iteration budget exhausted ` +
          `(${budget.used}/${budget.maxTotal} productive iterations). ` +
          `Please try again with a simpler request, or increase ` +
          `agents.defaults.iterationBudget.maxIterations in your config.`;

      return {
        payloads: [{ text, isError: true }],
        meta: {
          durationMs,
          agentMeta,
          ...(livenessState ? { livenessState } : {}),
          error: {
            kind: "budget_exhausted",
            message: `Budget exhausted: ${budget.used}/${budget.maxTotal}`,
          },
        },
      };
    }

  NOTES:
    - Mirrors handleRetryLimitExhaustion() structure exactly
    - No async -- this is a pure result builder
    - summaryError handles the fallback case when summary fails
    - Returns isError: true so downstream knows it's an error

C.3  KNOWN LIMITATIONS
-----------------------

  1. Budget lost on FailoverError
     When the run loop throws FailoverError and the outer caller re-invokes
     runEmbeddedAgent with a different model, the budget resets to full.

     Impact: LOW -- failover is rare, and a fresh budget for a new model
     is reasonable (it hasn't done any work with that model).

     Resolution: Pass budget state through RunEmbeddedAgentParams so
     failover inherits remaining budget.

  2. No separate subagent budget default
     Each subagent agent ID can have its own iterationBudget.maxIterations
     via per-agent config. No global subagent default.

     Impact: LOW -- operators who want different subagent budgets can set
     them per-agent. The default of 90 applies to all agents equally.

     Resolution: Add subagentMaxIterations with detection via spawnedBy.

  3. No live budget tracking in diagnostic session state
     Budget usage is reported in the run result meta, not in real-time
     diagnostic session state.

     Impact: LOW -- run result still reports budget usage.

     Resolution: Thread diagnostic session ref through run.ts and
     update budget fields from the callback.

  4. Summary attempt not strictly tool-free
     The summary attempt relies on the instruction to prevent tool calls.
     If the model ignores the instruction, it may make one more tool call
     before the outer loop returns.

     Impact: LOW -- the summary attempt is still bounded by being a
     single outer-loop iteration.

     Resolution: Add suppressTools flag to the attempt params that
     omits tools from the LLM API request entirely.
