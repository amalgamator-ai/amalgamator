A.2  What We Don't Port (Out of Scope)
-----------------------------------------

  1. ToolCallGuardrailController (476 lines)
     - OpenClaw already has tool-loop-detection.ts (821 lines) with
       equivalent pattern detection. Porting would duplicate functionality.
     - IterationBudget is orthogonal and complementary to loop detection.

  2. threading.Lock (Python thread safety)
     - Node.js is single-threaded. No locking needed.

  3. Grace call mechanism (Hermes: _budget_grace_call)
     - Hermes-specific design for its loop structure. Not needed in
       OpenClaw where budget exhaustion triggers a dedicated summary
       attempt via the outer loop.

  4. execute_code refund
     - Hermes-specific tool. OpenClaw doesn't have an equivalent
       low-cost programmatic tool category.

  5. Subagent budget differentiation
     - Out of scope for this port. OpenClaw's agent-to-agent maxTurns
       already constrains subagent conversations.

  6. Ollama context-limit refund
     - Hermes-specific provider workaround.

A.5  Architecture: Two-Level Loop & Harness Resolution
---------------------------------------------------------

  [Discovered in V2, verified in V3 with definitive harness resolution]

  OpenClaw has a two-level loop architecture:

  OUTER LOOP (src/agents/embedded-agent-runner/run.ts, line 1885):
    while (true) {
      - Check runLoopIterations >= MAX_RUN_LOOP_ITERATIONS
      - Dispatch one LLM attempt via runEmbeddedAttemptWithBackend()
      - Process result: success, retry, compaction, failover, timeout
    }
    This loop manages retries, compaction, error recovery. It is NOT the
    tool-calling loop. runLoopIterations guards against retry storms.

  INNER LOOP (packages/agent-core/src/agent-loop.ts, line 310):
    while (hasMoreToolCalls || pendingMessages.length > 0) {
      - onBeforeToolCallingRound callback (NEW -- Step 6)
      - Stream LLM response (streamAssistantResponse)
      - Execute tool calls (executeToolCalls)
      - emit turn_end
      - shouldStopAfterTurn callback
      - Get steering messages
    }
    This is the actual tool-calling loop. Each iteration = 1 LLM API call
    + tool execution. This is where IterationBudget.consume() is called.

  BUDGET ENFORCEMENT STRATEGY:
    IterationBudget sits between these loops:
    - Created in run.ts (outer loop scope)
    - Consumed in agent-loop.ts (inner loop, via callback)
    - Exhaustion detected in run.ts (after attempt returns)
    - Summary injected via run.ts (next outer-loop iteration)

  [V3-NEW] HARNESS RESOLUTION:

    The embedded agent runner call chain is:

      run.ts
        -> runEmbeddedAttemptWithBackend(params)  [run/backend.ts]
          -> runAgentHarnessAttempt(params)        [run/backend.ts]
            -> ...
              -> creates AgentSession with Agent instance
              -> Agent or CoreAgentHarness calls runAgentLoop(config)

    TWO createLoopConfig implementations exist:

      1. Agent.createLoopConfig (agent-core/agent.ts, lines 474-507)
         - Maps: beforeToolCall, afterToolCall, prepareNextTurn, etc.
         - Does NOT map: shouldStopAfterTurn, onBeforeToolCallingRound (new)

      2. CoreAgentHarness.createLoopConfig (agent-core/harness/agent-harness.ts, ~line 486)
         - Wraps Agent, does NOT extend it
         - Maps: beforeToolCall (via hook emit), afterToolCall (via hook emit)
         - Does NOT map: shouldStopAfterTurn, prepareNextTurn, onBeforeToolCallingRound

    CRITICAL: onBeforeToolCallingRound MUST be mapped in BOTH createLoopConfig
    methods. If mapped in only one, the budget silently fails to enforce in
    whichever code path uses the other.

    The safest approach: set onBeforeToolCallingRound as a public property on
    Agent, and have BOTH createLoopConfig methods read it from the Agent
    instance. This is the same pattern used for beforeToolCall and afterToolCall.

    CoreAgentHarness wraps an Agent, so it can access the Agent's properties.
    During implementation, verify the harness accesses the wrapped agent via
    a public property or constructor argument.

  [V3-NEW] shouldStopAfterTurn ALTERNATIVE:

    Using the existing shouldStopAfterTurn callback (already in AgentLoopConfig,
    already invoked at line 409-419 of agent-loop.ts) would eliminate changes to
    types.ts and agent-loop.ts. Only agent.ts and harness/agent-harness.ts would
    need changes (2 files instead of 4).

    shouldStopAfterTurn is RETAINED as a documented fallback approach if the
    onBeforeToolCallingRound approach is rejected during PR review. The tradeoffs:

      onBeforeToolCallingRound (RECOMMENDED):
        + Dedicated purpose separation
        + Synchronous (no async overhead in hot loop)
        + Prevents wasted LLM call at budget boundary
        + Won't conflict with future uses of shouldStopAfterTurn
        - Touches 4 agent-core files

      shouldStopAfterTurn (FALLBACK):
        + Touches only 2 agent-core files
        + Uses existing mechanism
        - Allows one extra LLM call at budget boundary (~1% overhead)
        - Occupies a general-purpose callback slot
        - Async overhead (Promise creation) on every turn

    If using shouldStopAfterTurn as fallback:
      1. Add shouldStopAfterTurn to AgentOptions (agent.ts)
      2. Add as public property on Agent (agent.ts)
      3. Map in Agent.createLoopConfig (agent.ts)
      4. Map in CoreAgentHarness.createLoopConfig (agent-harness.ts)
      5. Set on agent instance in attempt.ts
      6. Callback: async (ctx) => !iterationBudget.consume()

STEP 1: Create IterationBudget class
--------------------------------------------------------------------------------

  PURPOSE:
    Port Hermes's IterationBudget (agent/iteration_budget.py, 62 lines) to
    TypeScript as a simple counter without thread-safety primitives.

  TARGET FILE (NEW):
    src/agents/iteration-budget.ts

  IMPLEMENTATION:

    /**
     * Per-agent iteration budget counter.
     *
     * Each agent run gets an IterationBudget that caps the total number of
     * LLM API calls (tool-calling rounds) allowed. The budget is consumed
     * once per inner-loop turn in agent-core's runAgentLoop.
     *
     * Ported from Hermes's agent/iteration_budget.py (62 lines).
     * Node.js is single-threaded so no locking is needed.
     */
    export class IterationBudget {
      public readonly maxTotal: number;
      private _used = 0;

      constructor(maxTotal: number) {
        if (maxTotal < 1) {
          throw new Error(`maxTotal must be >= 1, got ${maxTotal}`);
        }
        this.maxTotal = maxTotal;
      }

      /** Try to consume one iteration. Returns true if allowed. */
      consume(): boolean {
        if (this._used >= this.maxTotal) {
          return false;
        }
        this._used += 1;
        return true;
      }

      /** Give back one iteration (e.g. for compaction restarts). */
      refund(): void {
        if (this._used > 0) {
          this._used -= 1;
        }
      }

      get used(): number {
        return this._used;
      }

      get remaining(): number {
        return Math.max(0, this.maxTotal - this._used);
      }
    }

  DIFFERENCES FROM HERMES:
    - No threading.Lock (Node.js is single-threaded)
    - Constructor validates maxTotal >= 1 (defensive, TypeScript style)
    - Uses TypeScript get accessors (same semantics as Python @property)

  FILE SIZE: ~40 lines (vs Hermes's 62 with docstrings and lock).

  DEPENDENCIES: None (pure TypeScript, no external imports).

        enabled: boolean;
        maxIterations: number;
        forceSummaryOnExhaustion: boolean;
      };

      export function resolveIterationBudgetConfig(
        cfg?: OpenClawConfig,
        agentId?: string,
      ): ResolvedIterationBudgetConfig {
        const configBudget: IterationBudgetConfig | undefined =
          (cfg && agentId
            ? resolveAgentConfig(cfg, agentId)?.iterationBudget
            : undefined) ?? cfg?.agents?.defaults?.iterationBudget;

        return {
          enabled: configBudget?.enabled ?? DEFAULT_ITERATION_BUDGET_ENABLED,
          maxIterations: Math.max(
            1,
            configBudget?.maxIterations ?? DEFAULT_MAX_ITERATIONS,
          ),
          forceSummaryOnExhaustion:
            configBudget?.forceSummaryOnExhaustion ??
            DEFAULT_FORCE_SUMMARY_ON_EXHAUSTION,
        };
      }

    - Apply hardcoded defaults with nullish coalescing
    - Normalize values with Math.max for safety
    - Return a fully-resolved type (no optional fields)

STEP 10: Add budget-exhaustion result builder
--------------------------------------------------------------------------------

  PURPOSE:
    Create a result builder function that produces a consistent
    EmbeddedAgentRunResult for budget exhaustion, modeled after
    handleRetryLimitExhaustion in run/retry-limit.ts.

  TARGET FILE (NEW):
    src/agents/embedded-agent-runner/run/budget-exhaustion.ts

  IMPLEMENTATION:

    import type { IterationBudget } from "../../iteration-budget.js";
    import type {
      EmbeddedAgentRunResult,
      EmbeddedAgentMeta,
      EmbeddedRunLivenessState,
    } from "../types.js";

    export function buildBudgetExhaustionResult(params: {
      budget: IterationBudget;
      durationMs: number;
      agentMeta: EmbeddedAgentMeta;
      livenessState?: EmbeddedRunLivenessState;
      summaryError?: string;
    }): EmbeddedAgentRunResult {
      const errorDetail = params.summaryError
        ? `Budget exhausted (${params.budget.used}/${params.budget.maxTotal}). ${params.summaryError}`
        : `Budget exhausted after ${params.budget.used} of ${params.budget.maxTotal} allowed iterations.`;

      return {
        payloads: [
          {
            text:
              "I reached the maximum number of allowed tool-calling iterations " +
              `(${params.budget.maxTotal}) without producing a final answer. ` +
              "The task may be incomplete. Please try again or increase the " +
              "iteration budget in your configuration.",
            isError: true,
          },
        ],
        meta: {
          durationMs: params.durationMs,
          agentMeta: params.agentMeta,
          ...(params.livenessState
            ? { livenessState: params.livenessState }
            : {}),
          budgetUsed: params.budget.used,
          budgetMax: params.budget.maxTotal,
          error: {
            kind: "budget_exhausted" as const,
            message: errorDetail,
          },
        },
      };
    }

  PATTERN FOLLOWED:
    Same structure as handleRetryLimitExhaustion (run/retry-limit.ts):
    - Returns EmbeddedAgentRunResult with error payload
    - Includes error.kind for downstream classification
    - Human-readable error message in payload.text
    - Meta includes duration, agentMeta, error details

C.1  HIGH RISK
-----------------

  None identified. All V1 critical issues have been resolved in prior
  iterations. V3 addresses all V2 medium issues.


C.2  MEDIUM RISK
-------------------

  1. Harness createLoopConfig path (Step 6D)
     RISK: The CoreAgentHarness.createLoopConfig is a SEPARATE implementation
     from Agent.createLoopConfig. If onBeforeToolCallingRound is mapped in
     only one, the budget silently fails in the other code path.

     MITIGATION:
     - Step 6D explicitly handles both implementations
     - Verification procedure: grep for createLoopConfig, trace actual
       call path from runEmbeddedAttemptWithBackend
     - Defense-in-depth: both implementations get the mapping

  2. Callback lifecycle (Step 7)
     RISK: installAgentToolHooks() overwrites beforeToolCall and afterToolCall
     on the Agent instance. If future code changes overwrite more callbacks,
     onBeforeToolCallingRound could be silently lost.

     MITIGATION:
     - Verified: installAgentToolHooks only touches beforeToolCall and
       afterToolCall (agent-session.ts lines 497-551)
     - The callback is set AFTER session creation, which is AFTER
       installAgentToolHooks runs
     - Integration test (Step 16.7) verifies the callback is invoked

  3. Budget exhaustion at text boundary (Step 8)
     RISK: If the payloadCount check (FIX #1) is missing, valid text
     responses would be incorrectly treated as budget exhaustion errors.

     MITIGATION:
     - payloadCount === 0 check is explicitly included (V2 FIX #1)
     - Integration test (Step 16.6) covers this exact scenario


C.3  LOW RISK
-----------------

  1. Default change for tool loop detection (Step 14)
     RISK: Enabling warnings by default may produce unexpected log output
     for existing deployments.

     MITIGATION: Only warning-level output (no blocking). Easy to disable
     via config: tools.loopDetection.enabled = false.

  2. Schema strictness (Step 3)
     RISK: .strict() on the Zod schema rejects unknown keys. If users have
     custom fields in their config, validation fails.

     MITIGATION: All other OpenClaw schemas use .strict(). This is consistent.

  3. Budget interaction with failover (Steps 8-10)
     RISK: When a FailoverError triggers mid-run, the budget state may be
     inconsistent (partially consumed).

     MITIGATION: FailoverError causes the entire run to restart with a new
     provider. The budget persists across the restart, which is the desired
     behavior -- the agent has already used those iterations regardless of
     which provider served them.
