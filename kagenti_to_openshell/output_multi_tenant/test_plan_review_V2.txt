ISSUE R2-1 (HIGH): Provider handler tests call handle_create_provider which
  does request.into_inner() before principal extraction is possible

  PROBLEM: Section 10.1 tests call handle_create_provider() directly, passing
  a tonic::Request with Principal in extensions. But the port plan modifies
  handle_create_provider to extract the principal BEFORE request.into_inner()
  (line 1154). The test plan's request_with_principal() helper attaches a
  Principal to Request extensions, which is the correct approach.

  HOWEVER: The current handle_create_provider() at line 1154 calls
  request.into_inner() IMMEDIATELY, consuming the Request. The port plan
  must insert principal extraction BEFORE this line. The test plan assumes
  this change is made but does not verify it directly.

  The problem is that the test `create_provider_runtime_guard_blocks_user_
  when_disabled` (Section 10.1) describes a "runtime guard" inside the
  handler, but the PORT PLAN (Step 11E) says: "when ownership is disabled,
  check that the caller has admin role." This guard needs the Principal,
  which means handle_create_provider MUST be modified to extract Principal
  from extensions before into_inner(). The V2 test plan correctly tests this
  behavior, but it should explicitly note that handle_create_provider itself
  is being modified (not just create_provider_record).

  IMPACT: The test descriptions are correct in what they verify. The issue
  is that Section 10 doesn't document the handle_create_provider
  modification as clearly as Section 9 does for sandbox. This is a
  documentation clarity issue, not a test correctness issue.

  FIX: Added explicit note to Section 10 header documenting that
  handle_create_provider is modified to extract Principal before
  into_inner(), matching the sandbox pattern.

  structure concern verified by code review, not by a separate test.

  have no owner label. Then when anonymous lists, since ownership
  enforcement skips for anonymous, all sandboxes are returned.

ISSUE R2-4 (MEDIUM): Section 10.3 shared provider tests assume admin
  creates provider without owner label, but the port plan stamps owner
  on all providers

  PROBLEM: Section 10.2 test list_providers_includes_shared_providers says:
    "Admin creates provider-shared (no owner label, or with allow_unowned)"

  And Section 10.3 test get_shared_provider_allowed_for_any_user says:
    "Provider with no owner label (admin-created shared)"

  But the port plan Step 11A stamps owner labels on ALL providers created
  when ownership is enabled, including admin-created ones. An admin user
  creating a provider would get openshell.ai/owner = admin-uuid stamped.

  For a provider to be "shared" (no owner label), it must be created
  BEFORE ownership was enabled, or the admin must have a way to create
  without owner stamping. The port plan doesn't define a "create shared
  provider" mechanism — it just says that providers without owner labels
  are treated as shared (allow_unowned=true).

  REAL SCENARIOS for shared providers:
    a) Provider created before ownership was enabled (migration)
    b) Provider created by admin with ownership disabled in config

  The tests should use one of these scenarios, not assume admin creates
  a provider without owner label when ownership is enabled.

  FIX: Corrected shared provider test setups to create the shared provider
  via a ServerState with ownership DISABLED (scenario b), then switch to
  an ownership-enabled ServerState for the user's operations. Since both
  states share the same Store, the provider persists across config changes.

  ALTERNATIVE SIMPLER FIX: Use a single ServerState and insert the shared
  provider directly into the store with no owner label, bypassing the
  handler. This is more realistic (simulates a pre-existing provider
  from before ownership was enabled).

  Applied the simpler fix: shared provider tests insert directly into
  the store using store.put_if() with manually constructed protobuf,
  bypassing the handler (which would stamp an owner label).

ISSUE R2-5 (MEDIUM): Section 11 tests create sandboxes via
  ComputeRuntime.create_sandbox() but this is NOT the handler path

  PROBLEM: Section 11.1 says:
    "Create sandbox via ComputeRuntime.create_sandbox() with
    metadata.labels = {"openshell.ai/owner": "user-1"}"

  The compute/mod.rs create_sandbox() function at line 490-501 takes a
  Sandbox proto and a sandbox_token. It does NOT accept labels separately.
  The labels are embedded in the Sandbox proto's metadata.labels field.
  The compute layer then calls store.put_if() with the labels.

  The R4-8 fix changes this put_if call from labels: None to
  labels: labels_json (serialized from metadata.labels). So the test
  should verify that after calling create_sandbox() with a Sandbox that
  has metadata.labels set, the labels end up in the DB labels column.

  But create_sandbox() is a method on ComputeRuntime, which is a struct
  wrapping the store and driver. In tests, this is created via
  new_test_runtime(store). The test would need to:
    1. Create a ComputeRuntime from a store
    2. Construct a Sandbox proto with metadata.labels
    3. Call compute.create_sandbox(sandbox, None)
    4. Query the store directly to verify labels column

  This is actually correct as described, but the test must construct the
  full Sandbox proto correctly. The description "Create sandbox via
  ComputeRuntime.create_sandbox()" is slightly misleading because it's
  not a simple function — it involves the full compute pipeline including
  driver validation.

  With NoopTestDriver, the create_sandbox call may fail because the
  driver's ValidateSandboxCreate returns an error by default (since the
  driver returns not_found/unimplemented for most operations).

  FIX: Changed Section 11 tests to use store.put_if() directly instead
  of going through the compute runtime. This is what the R4-8 fix
  actually changes — the labels parameter in the put_if call. Testing
  put_if directly is more targeted and avoids NoopTestDriver complications.

  For the roundtrip tests (11.2), using store.put_if() + list_with_selector
  directly tests the persistence layer without compute runtime involvement,
  which is the actual path being modified.

ISSUE R2-6 (MEDIUM): Section 16 wiremock test infrastructure uses rcgen
  for JWT key generation, but rcgen generates X.509 certificates, not
  raw RSA key pairs for JWT signing

  PROBLEM: Section 16 says:
    "fn create_test_jwk_pair() -> (EncodingKey, DecodingKey, Jwk) {
        // Generate RSA key pair using rcgen (already a dev-dependency)"

  rcgen is a certificate generation library. It generates X.509
  certificates and RSA/ECDSA private keys. For JWT testing, what's needed
  is:
    1. An RSA private key (for signing JWTs with RS256)
    2. The corresponding public key in JWK format (for the JWKS endpoint)
    3. An EncodingKey (from jsonwebtoken crate) for signing
    4. A DecodingKey (from jsonwebtoken crate) for verification

  rcgen CAN generate RSA keys, but the typical pattern is:
    - Use rcgen to create a key pair
    - Extract the private key as DER/PEM
    - Use jsonwebtoken's EncodingKey::from_rsa_pem() or from_rsa_der()
    - Construct the JWK manually from the public key components

  The test infrastructure description is correct in concept but unclear
  on the specific library interactions. The jsonwebtoken crate (already
  in dependencies) has the actual EncodingKey/DecodingKey types.

  FIX: Clarified that rcgen provides key generation and jsonwebtoken
  provides EncodingKey/DecodingKey. Added more precise pseudocode for
  the key pair creation. Also noted that the OpenShell codebase already
  has rcgen usage in tests (tls_test_utils.rs) which demonstrates the
  key generation pattern.

ISSUE R2-7 (MEDIUM): Section 16 wiremock OIDC tests mock the
  .well-known/openid-configuration endpoint, but JwksCache in
  OpenShell does NOT fetch the OIDC discovery document

  PROBLEM: Section 16 mocks:
    Mock::given(method("GET"))
        .and(path("/.well-known/openid-configuration"))
        .respond_with(...)

  But JwksCache at oidc.rs does NOT fetch the OIDC discovery document.
  It uses the issuer URL directly to construct the JWKS URL. Looking at
  the actual JwksCache implementation:
    - JwksCache::new() takes an OidcConfig
    - refresh_keys() fetches keys from {issuer}/protocol/openid-connect/certs
      (hardcoded Keycloak path, not from discovery)
    - OR it constructs the JWKS URL from the issuer

  The mock for .well-known/openid-configuration is unnecessary. Only
  the JWKS endpoint (/protocol/openid-connect/certs or similar) needs
  to be mocked.

  VERIFICATION: In oidc.rs, the JwksCache constructs JWKS URL from
  config.issuer + a path. The exact path depends on the implementation,
  but the test must match it.

  FIX: Removed the .well-known/openid-configuration mock. Only the JWKS
  endpoint needs to be mocked. Added a note to verify the exact JWKS URL
  construction from JwksCache before implementing.

ISSUE R2-9 (LOW): Section 18.2 concurrent sandbox creation test is
  not actually testing concurrency safety of ownership logic

  PROBLEM: Section 18.2 says:
    "stamp_owner_labels is stateless (pure function), but the handler's
    Principal extraction + into_inner sequence could theoretically race"

  stamp_owner_labels is a pure function that takes inputs and returns
  outputs. It cannot race. The handler's Principal extraction +
  into_inner sequence is per-request and cannot race with other requests
  either (each request has its own tonic::Request object).

  The only real concurrency concern is:
    1. Two users creating sandboxes with the same name (already tested
       by name_collision_across_owners_returns_error in Section 15.2)
    2. Database-level concurrency for label selector queries (handled
       by SQLite/Postgres transaction isolation)

  The concurrent_sandbox_creation_by_different_users test is testing
  something that fundamentally cannot race in Rust's ownership model.
  The concurrent_list_during_creates test is testing SQLite's ACID
  properties, not ownership logic.

  These tests are harmless but provide no actual safety guarantees
  beyond what the type system and database already provide.

  FIX: Reclassified from "Concurrency Safety Tests" to "Stress Tests"
  with updated descriptions. The tests are still valuable for catching
  unexpected panics under load, but they don't test concurrency safety
  specifically.

  fn sign_jwt(
      claims: serde_json::Value,
      key: &jsonwebtoken::EncodingKey,
      kid: &str,
  ) -> String {
      use jsonwebtoken::{Header, Algorithm};
      let mut header = Header::new(Algorithm::RS256);
      header.kid = Some(kid.to_string());
      jsonwebtoken::encode(&header, &claims, key).unwrap()
  }
