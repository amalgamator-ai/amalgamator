1. TEST PLAN EXPLANATION
================================================================================

V3 is a from-scratch rebuild of the test plan for the multi-tenant deployment
support feature. It was written after deep analysis of both the Kagenti source
project and the OpenShell target project's actual test infrastructure, rather
than relying on assumptions about codebase conventions.

1.1 KEY DESIGN DECISIONS
─────────────────────────

  1. CODEBASE-VERIFIED CONVENTIONS

     V3 was built after analyzing 3,582 existing tests in the OpenShell
     codebase (2,872 sync #[test] + 710 async #[tokio::test] across 254
     #[cfg(test)] modules). Every test pattern, helper function, and naming
     convention in V3 matches verified patterns from the actual codebase:

     - Factory helpers: Follows guard.rs (fn user(subject) -> Principal),
       authz.rs (fn identity_with_roles(roles) -> Identity), and
       policy.rs (fn with_user<T>(request) -> Request<T>) patterns
     - Auth injection: Uses request.extensions_mut().insert(principal),
       the same pattern found in guard.rs:163, policy.rs:3920, auth_rpc.rs:214
     - State construction: Uses test_server_state() (grpc/mod.rs:693) and
       test_store() (persistence/mod.rs:629), the established helpers
     - Data seeding: Uses store.put_message() (persistence/mod.rs:605),
       the test-only unconditional write helper
     - No external mocks: Hand-rolled helpers only, matching the project's
       zero-dependency-on-mockall philosophy

  2. NO REDUNDANCY WITH EXISTING TESTS

     V3 explicitly identifies 30+ existing label infrastructure tests and
     44+ existing auth tests that are NOT duplicated. The test plan tests
     only NEW code paths introduced by the 20-step port plan.

  3. CORRECT BY CONSTRUCTION

     All 23 issues found across V1-R1 and V2-R1 reviews are addressed by
     design in V3, not as retroactive patches:

     - Shared providers inserted via store.put_message() (not handler)
       → V2-R1 Issue R2-4
     - Label persistence tested via store.put_if() (not ComputeRuntime)
       → V2-R1 Issue R2-5
     - Wiremock OIDC mocks only JWKS endpoint (not discovery)
       → V2-R1 Issue R2-7
     - Key generation uses rcgen + jsonwebtoken (correct library roles)
       → V2-R1 Issue R2-6
     - Email sanitization preserves dots (only @ replaced)
       → V2-R1 Issue R2-8
     - Stress tests (not "concurrency safety tests")
       → V2-R1 Issue R2-9
     - Config via GatewayFileSection (not CLI args)
       → V2-R1 Issue R2-11
     - No redundant extraction-ordering test
       → V2-R1 Issue R2-2
     - Dual-label stamping on ObjectMeta AND SandboxTemplate
       → V4-R1 Issue R4-1
     - Handler modification documented for both sandbox and provider
       → V2-R1 Issue R2-1
     - OidcConfig uses actual field names (jwks_ttl_secs, not jwks_ttl)
       → V1-R1 Issue R1-1

  4. PRECISE ARITHMETIC

     Every test is individually enumerated. The traceability matrix total
     (158 tests) is verified by per-section addition. No "~approximately"
     counts.

1.3 NEW TEST INFRASTRUCTURE
────────────────────────────

  V3 defines 4 new test helpers (in grpc/mod.rs test_support) and 3 wiremock
  helpers (in oidc.rs integration_tests):

  New helpers:
    request_with_principal<T>() — injects Principal into tonic::Request extensions
    make_user(subject, role) — factory for Principal::User with OIDC identity
    make_admin(subject) — shorthand for make_user with admin role
    test_server_state_with_ownership(enabled, tenant_id) — ServerState with ownership

  Wiremock helpers:
    create_test_rsa_key_pair() — generates RSA keys for JWT signing
    setup_mock_jwks_server() — mock JWKS endpoint for OIDC testing
    sign_jwt(claims, key, kid) — sign a JWT with RS256

  These helpers follow patterns already present in the codebase:
    - guard.rs line 102-122 (fn user, fn sandbox factories)
    - policy.rs line 3920 (fn with_user<T> for request extension injection)
    - authenticator.rs line 102 (MockAuthenticator with canned outcomes)
    - sandbox_jwt.rs line 250-278 (real crypto key generation in tests)

1.4 KAGENTI E2E COVERAGE
──────────────────────────

  All 20 Kagenti E2E test cases from test_T4_2_tenant_isolation.py (14 tests)
  and test_T4_4_per_user_isolation.py (11 tests, minus 5 listed twice) are
  mapped to equivalent Rust tests in Appendix A. The mapping covers:

    - Audience isolation → Wiremock OIDC tests (Section 17)
    - RBAC isolation → Helm template tests (Section 18.2)
    - Credential isolation → Helm template tests (Section 18.1)
    - Owner label stamping → Sandbox handler tests (Section 10.1)
    - Owner list filtering → Sandbox handler tests (Section 10.2)
    - Access denied enforcement → Sandbox handler tests (Section 10.3-4)
    - Admin bypass → Sandbox handler tests (Section 10.2-4)

2.7 WHAT A V3 REVIEW MIGHT STILL FIND
───────────────────────────────────────

  Potential residual issues (LOW severity only):

  1. Exact JWKS URL path in JwksCache::refresh_keys() — the test plan notes
     "/protocol/openid-connect/certs" but says "verify before implementing."
     A reviewer could verify the exact path.

  2. OwnershipConfig field names — the plan uses "allow_unowned_providers"
     but the actual implementation might use a different name. This is a
     naming decision that hasn't been made yet (it's new code).

  3. Helm template test approach — using "helm template | yq" is one
     approach; the project might prefer a different tool chain.

  4. E2E test feature flag — the plan uses #[cfg(feature = "e2e-docker")]
     but the ownership tests might need their own feature flag
     (e.g., "e2e-ownership") to gate on OIDC availability.
