ISSUE R4-1 (MEDIUM): validate_token() takes 1 argument, not 2

  PROBLEM: Section 17 (wiremock OIDC tests) calls:
    cache.validate_token(&jwt, &config).await.unwrap()

  This passes TWO user-supplied arguments: the JWT token AND an OidcConfig
  reference. But the actual validate_token signature is:

    pub async fn validate_token(&self, token: &str) -> Result<Identity, Status>

  Verified at oidc.rs line 288. The method takes only ONE user argument
  (the token string). The OidcConfig is captured internally during
  JwksCache::new(&config) and stored as self.config. The validate_token
  method uses self.config.issuer, self.config.audience,
  self.config.roles_claim, and self.config.scopes_claim internally.
  After Step 2 adds groups, it will also use self.config.groups_claim.

  IMPACT: All 4 tests in Section 17 would fail to compile:
    17.1: cache.validate_token(&jwt, &config) → won't compile
    17.2: same
    17.3: same, AND additionally tries to mutate config.groups_claim
          AFTER JwksCache construction, but the config is already
          captured inside the cache — the mutation has no effect
    17.4: same

  FIX:
    - All validate_token calls: remove &config argument
      BEFORE: cache.validate_token(&jwt, &config).await.unwrap()
      AFTER:  cache.validate_token(&jwt).await.unwrap()

    - Test 17.3 (custom groups_claim): Must construct a NEW
      JwksCache with the modified config, because the groups_claim
      is captured at construction time. The mock server can be
      reused (OIDC discovery and JWKS are independent of groups_claim),
      but the config must be modified BEFORE creating the cache:

      BEFORE:
        config.groups_claim = "custom.team_membership"
        cache.validate_token(&jwt, &config).await.unwrap()
      AFTER:
        let (mock, mut config, key) = setup_mock_jwks_server().await;
        config.groups_claim = "custom.team_membership".to_string();
        let cache = JwksCache::new(&config).await.unwrap();
        // ... sign JWT and validate ...
        cache.validate_token(&jwt).await.unwrap()

ISSUE R4-2 (MEDIUM): E2E test file location is wrong — e2e/rust/ is a
  separate crate that uses black-box CLI testing

  PROBLEM: Section 16 places tests at:
    e2e/rust/tests/ownership_lifecycle.rs (NEW)

  And describes the tests using white-box handler calls:
    test_server_state_with_ownership(true, None).await
    handle_create_sandbox_inner(&state, request_with_principal(...))
    make_user("user-A", "openshell-user")

  But the e2e/rust/ directory is a SEPARATE workspace crate
  (openshell-e2e) with its own Cargo.toml. Verified:

    e2e/rust/Cargo.toml:
      [workspace]              ← prevents being part of root workspace
      name = "openshell-e2e"
      [features]
      e2e = []                 ← feature-gated

    e2e/rust/tests/sandbox_lifecycle.rs:
      #![cfg(feature = "e2e")]
      use openshell_e2e::harness::binary::openshell_cmd;
      → runs CLI binary commands (black-box testing)

  The Section 16 tests CANNOT go here because:
    1. openshell-e2e is a separate crate — it cannot access
       #[cfg(test)] items from openshell-server (test_support,
       make_user, test_server_state_with_ownership, etc.)
    2. E2E tests in this directory use CLI binary execution
       (openshell_cmd), not handler function calls
    3. E2E tests require a running server process, not in-process
       handler invocation

  IMPACT: 8 tests in Section 16 would not compile in the specified location.

  FIX: Move Section 16 tests into the handler test modules where they
  have access to all required helpers:
    - 16.1 (sandbox lifecycle, 4 tests) → crates/openshell-server/src/grpc/sandbox.rs
      in #[cfg(test)] mod tests, alongside the existing sandbox handler tests
    - 16.2 (provider lifecycle, 3 tests) → crates/openshell-server/src/grpc/provider.rs
      in #[cfg(test)] mod tests, alongside the existing provider handler tests
    - 16.3 (cross-resource, 1 test) → crates/openshell-server/src/grpc/sandbox.rs
      in #[cfg(test)] mod tests (since it tests sandbox creation with providers)

  These tests are handler-level integration tests that exercise multi-step
  flows through the handler layer. They belong with the handler tests, not
  in the E2E directory. The "E2E" label is misleading — they don't test
  the full stack (CLI → gRPC → server → compute → driver).

ISSUE R4-3 (LOW): put_if name parameter is &str, not Option<&str>

  PROBLEM: Section 12.1 (sandbox_labels_persisted_on_create) calls:

    store.put_if(
        "sandbox", "sbx-1", Some("my-sandbox"),
        &payload, Some(&labels), WriteCondition::MustCreate
    )

  But the actual put_if signature (persistence/mod.rs line 232-240):

    pub async fn put_if(
        &self,
        object_type: &str,
        id: &str,
        name: &str,           // ← &str, NOT Option<&str>
        payload: &[u8],
        labels: Option<&str>,
        condition: WriteCondition,
    ) -> PersistenceResult<WriteResult>

  The `name` parameter is `&str`, not `Option<&str>`. Passing
  `Some("my-sandbox")` would not compile.

  Verified against existing persistence tests (persistence/tests.rs):
    store.put_if(
        "sandbox", "id-1", "new-sandbox",  // ← plain &str
        b"payload", None, WriteCondition::MustCreate,
    ).await.unwrap();

  IMPACT: Test 12.1 would not compile as written.

  FIX: Change Some("my-sandbox") to "my-sandbox":

    BEFORE: store.put_if("sandbox", "sbx-1", Some("my-sandbox"), ...)
    AFTER:  store.put_if("sandbox", "sbx-1", "my-sandbox", ...)

ISSUE R4-4 (LOW): Test 6.4.7 uses .. struct update syntax on Identity
  which has no Default impl

  PROBLEM: Section 6.4.7 (user_with_no_roles_still_gets_selector) describes:

    principal = Principal::User(UserPrincipal {
        identity: Identity {
            subject: "u1".to_string(),
            roles: vec![],  // no roles
            ..
        }
    })

  The `..` at the end of the Identity struct literal implies Rust's
  struct update syntax (e.g., `..Default::default()`). But Identity
  has `#[derive(Debug, Clone)]` only — no Default impl (verified at
  identity.rs lines 15-31).

  Without Default, `..` struct update syntax requires another Identity
  instance to fill in the remaining fields. Since none is provided,
  this won't compile.

  IMPACT: Test description is misleading. An implementer following this
  literally would get a compile error.

  FIX: Spell out all Identity fields explicitly. After Step 1 adds the
  groups field, Identity has 6 fields that must all be specified:

    principal = Principal::User(UserPrincipal {
        identity: Identity {
            subject: "u1".to_string(),
            display_name: None,
            roles: vec![],
            scopes: vec![],
            groups: vec![],
            provider: IdentityProvider::Oidc,
        },
    })

  Alternatively, this test could use make_user and then check the
  logic differently. But since the test specifically needs a user with
  NO roles (while make_user always adds one role), explicit construction
  is the correct approach.
