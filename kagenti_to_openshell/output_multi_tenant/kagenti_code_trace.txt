1. FEATURE OVERVIEW
================================================================================

Kagenti implements multi-tenancy for OpenShell through a "gateway-per-tenant"
pattern. Each tenant (team) gets:

- A dedicated Kubernetes namespace
- An isolated OpenShell gateway StatefulSet (gateway + compute-driver +
  credentials-driver sidecars)
- Namespace-scoped RBAC (Role, not ClusterRole)
- OIDC audience scoping via Keycloak (JWT aud=<tenant>)
- Per-tenant TLS certificates via cert-manager
- ResourceQuota and LimitRange per namespace
- Per-user sandbox ownership within a tenant (openshell.ai/owner label)
- Tenant-scoped credential/provider isolation
- Platform-specific ingress (Istio TLSRoute for Kind, passthrough Route for OCP)

The architecture separates shared cluster-wide infrastructure (Keycloak realm,
cert-manager CA, sandbox controller, Gateway API CRDs) from per-tenant
resources, enabling independent lifecycle management.

================================================================================
2. ARCHITECTURE SUMMARY
================================================================================

Deployment Model:
```
Cluster
├── keycloak/                      Shared OIDC provider (openshell realm)
├── agent-sandbox-system/          Shared CRD controller (k8s SIG)
├── cert-manager/                  Shared CA chain (openshell-ca)
├── kagenti-system/                Shared TLS passthrough Gateway (Kind only)
│
├── team1/                         Tenant 1 — isolated stack
│   ├── openshell-server (StatefulSet)
│   │   ├── gateway container
│   │   ├── compute-driver sidecar
│   │   └── credentials-driver sidecar
│   ├── Service (ClusterIP)
│   ├── RBAC (Role + RoleBinding)
│   ├── TLSRoute or Route (ingress)
│   ├── ResourceQuota + LimitRange
│   ├── TLS certs (cert-manager Certificate CRs)
│   └── sandbox pods (owned by gateway)
│
└── team2/                         Tenant 2 — same structure, isolated
    └── ...
```

Isolation Layers:
1. Namespace isolation (K8s namespace per tenant)
2. OIDC audience scoping (JWT aud=<tenant> validated per gateway)
3. Namespace-scoped RBAC (gateway SA can only access own namespace)
4. Per-user ownership (openshell.ai/owner label on sandboxes/providers)
5. Separate SQLite DB per gateway (emptyDir or PVC)
6. TLS certificate isolation (per-tenant leaf certs from shared CA)
7. Credential isolation (per-tenant credentials-driver config)

================================================================================
3. ENTRY POINTS & DEPLOYMENT FLOW
================================================================================

The feature is activated through a layered script architecture:

Phase 1: Shared Infrastructure
  scripts/openshell/deploy-shared.sh
  └── Creates: sandbox controller, Gateway API CRDs, cert-manager CA chain,
      Keycloak realm with OIDC clients/roles/users/groups/audience scopes

Phase 2: Per-Tenant Deployment (repeat per tenant)
  scripts/openshell/deploy-tenant.sh <tenant>
  └── Creates: namespace, labels, Helm install (charts/openshell/),
      TLS cert verification, rollout wait, optional agent deployment

Phase 3: CLI Configuration
  scripts/openshell/configure-cli.sh <tenant>
  └── Registers gateway endpoint, extracts mTLS certs, triggers OIDC login

Cleanup (reverse order):
  scripts/openshell/cleanup-tenant.sh <tenant>
  scripts/openshell/cleanup-shared.sh
  scripts/openshell/cleanup-all.sh  (orchestrates both)

CI Orchestration:
  .github/scripts/local-setup/openshell-full-test.sh
  └── 7-phase pipeline: cluster → platform → images → shared → tenants → tests → destroy

4.2 deploy-tenant.sh (Per-Tenant Deployment)
────────────────────────────────────────────────────────────────────────────────
File: scripts/openshell/deploy-tenant.sh (393 lines)
Language: Bash

Purpose: Deploy one tenant's isolated OpenShell gateway stack via Helm.
Idempotent. Supports --dry-run.

Arguments:
  Positional: <tenant>  (e.g., team1, team2)
  --chart-dir <dir>     Helm chart directory (default: charts/openshell/)
  --keycloak-ns <ns>    Keycloak namespace (default: keycloak)

  --set <key=value>     Extra Helm --set values
  --timeout <seconds>   Rollout timeout
  --agents              Also deploy agent manifests
  --dry-run             Print commands without executing

Steps:

Step 0: Early namespace creation
  - Creates namespace before platform-specific setup
  - On OCP: builds combined CA bundle (system + ingress CA)

Step 1: Namespace creation + labeling
  - kubectl create namespace "$TENANT"
  - kubectl label namespace "$TENANT"
      shared-gateway-access=true
      openshell.ai/tenant="$TENANT"
      --overwrite

Step 2: Helm upgrade --install
  Core Helm values passed:
    --namespace "$TENANT"
    --set "tenant=$TENANT"
    --set "oidc.issuer=$OIDC_ISSUER"    (auto-detected from Keycloak)
    --set "oidc.audience=$TENANT"
    --set "driver.namespace=$TENANT"
    --set "ingress.type=$INGRESS_TYPE"   (istio or route)
    --set "ingress.host=$INGRESS_HOST"   (openshell-<tenant>.<domain>)

  Kind-specific:
    --set "keycloakClusterIP=$KEYCLOAK_CLUSTER_IP"

  OCP-specific:
    --set "openshift.enabled=true"
    --set "trustedCABundle=openshell-trusted-ca"

Step 3: TLS Secret Verification
  - Waits for openshell-server-tls and openshell-client-tls secrets
    (created by certgen Helm hook Job)

Step 4: StatefulSet Rollout Wait
  - kubectl rollout status statefulset/openshell-server

Step 5: Optional Agent Deployment (--agents flag)
  - On OCP: grants privileged SCC to openshell-supervisor SA
  - On Kind: patches validating webhook to exclude tenant namespace
  - Creates openshell-supervisor ServiceAccount
  - Creates kagenti-skills ConfigMap
  - Applies agent manifests from deployments/openshell/agents/*/deployment.yaml
  - Creates policy ConfigMaps from policy-data.yaml + sandbox-policy.rego
  - Patches agents for LiteLLM proxy (if available)
  - Waits for agent rollouts

Key Functions:
  is_openshift()        - platform detection
  get_ocp_base_domain() - reads OCP ingress domain
  get_keycloak_issuer() - returns OIDC issuer URL
  get_ingress_host()    - builds per-tenant hostname
  get_ingress_type()    - returns "route" or "istio"

Hostname Patterns:
  OCP:  openshell-${TENANT}.${base_domain}
  Kind: openshell-${TENANT}.${KIND_DOMAIN}  (KIND_DOMAIN=localtest.me)

Release Naming:
  RELEASE_NAME="${HELM_RELEASE_PREFIX}-${TENANT}"  (e.g., openshell-team1)

4.4 Keycloak OIDC & Audience Scoping
────────────────────────────────────────────────────────────────────────────────

Keycloak Configuration (created by deploy-shared.sh Step 4):

Realm: "openshell"
  Client: "openshell-cli" (public, PKCE enabled)
    - Standard flow + direct access grants enabled
    - Valid redirect URIs: http://localhost:*
    - Web origins: *
    - Optional client scopes: team1-audience, team2-audience

Audience Scoping Mechanism:
  1. Per-tenant client scopes created: "<tenant>-audience"
  2. Each scope has a "Hardcoded Audience" protocol mapper:
     - Mapper type: oidc-audience-resolve
     - Included client audience: <tenant>
  3. Scopes are added as OPTIONAL to openshell-cli client
  4. Group-based conditional scoping:
     - Users in /team1 group → audience scope includes team1
     - Users in /team2 group → audience scope includes team2
  5. Gateway validates: JWT.aud MUST contain gateway's configured audience
     (OPENSHELL_OIDC_AUDIENCE env var / oidc.audience Helm value)

Authentication Flow:
  CLI → Keycloak (PKCE Authorization Code) → JWT with aud=<tenant>
  CLI → Gateway (Bearer JWT in gRPC metadata)
  Gateway → validates iss, aud=<configured-tenant>, roles, scopes
  → Reject if aud mismatch (401/403)

Test Users:
  alice: team1 group, openshell-admin role → gets aud=team1
  bob:   team2 group, openshell-admin role → gets aud=team2
  admin: team1+team2 groups, openshell-admin → gets aud=team1,team2

OIDC Roles:
  openshell-admin: Provider CRUD, config mutations, admin bypass
  openshell-user:  Sandbox CRUD, exec, SSH

Related Keycloak Utility Code:
  kagenti/common/keycloak.py
    - read_keycloak_credentials(api, secret_name, namespace, user_key, pass_key)
      → returns (username, password) tuple from K8s secret
  kagenti/auth/shared_utils.py
    - get_session_lifetime_payload() → Keycloak session config
    - register_client(keycloak_admin, client_id, payload) → creates/gets client

4.5 Per-User Ownership (Owner-Label Approach)
────────────────────────────────────────────────────────────────────────────────

Design Doc: docs/research/openshell-per-user-tenancy.md
Implementation: Kagenti OpenShell fork (crates/openshell-server/src/auth/ownership.rs)
Status: Implemented (v0.0.56-rc.2+)

Within a single shared gateway (one namespace/team), per-user isolation is
enforced via the openshell.ai/owner label:

Create Flow:
  1. Gateway reads Principal::User from OIDC-validated request extensions
  2. Stamps openshell.ai/owner = identity.subject (Keycloak UUID sub claim)
  3. Client-supplied openshell.ai/* keys are STRIPPED (anti-spoofing)

List Flow:
  Gateway ANDs openshell.ai/owner=<caller> into label selector before DB query

Get/Delete/Connect/Exec:
  After fetch by name/ID, returns PermissionDenied if owner != caller

Admin Bypass:
  Callers with openshell-admin role skip ownership filter

OIDC Disabled:
  Ownership skipped for Anonymous principal (backward-compatible)

Label-value charset:
  K8s rules: alnum, -, _, ., <=63 chars
  Keycloak sub is UUID (satisfies this)
  Sanitization helper in auth/ownership.rs for non-UUID deployments

Provider Ownership (v0.0.56-rc.3+):
  Same owner-label pattern applied to providers
  Resolution order: user-owned provider > shared (admin-created) provider
  Name uniqueness scoped to (owner, name)

4.6 RBAC Authorization Per Tenant
────────────────────────────────────────────────────────────────────────────────

Kubernetes RBAC (Helm chart: charts/openshell/templates/rbac.yaml):

Gateway ServiceAccount RBAC (namespace-scoped):
  Role "openshell-gateway" in tenant namespace:
    agents.x-k8s.io/sandboxes → get, list, watch, create, update, delete
    core/pods, events, PVCs    → get, list, watch
    core/secrets               → get, list, watch
  RoleBinding: binds to openshell-gateway SA in tenant namespace

  CRITICAL: This is a ROLE (not ClusterRole), so the gateway SA has ZERO
  access to other tenant namespaces. Even if compromised, lateral movement
  is impossible at the K8s RBAC level.

TokenReview RBAC (cluster-scoped, per-tenant named):
  ClusterRole "openshell-gateway-tokenreview-<tenant>":
    authentication.k8s.io/tokenreviews → create
  ClusterRoleBinding: binds to openshell-gateway SA

Sandbox SA RBAC (OpenShift only):
  ClusterRoleBinding for privileged SCC:
    system:openshift:scc:privileged → openshell-sandbox SA in tenant namespace

PoC/Legacy RBAC (deployments/openshell/rbac.yaml):
  ClusterRole: sandboxes CRD + namespaces (read-only)
  Namespace-scoped Role in team1: pods (full CRUD), specific secrets, etc.
  NOTE: This is the older PoC RBAC; the Helm chart version is the current one.

4.8 Tenant-Scoped Provider Isolation
────────────────────────────────────────────────────────────────────────────────

Provider isolation operates at two levels:

Level 1: Namespace isolation
  Each tenant's gateway has its own SQLite database (PVC-backed via
  StatefulSet volumeClaimTemplate). Providers stored in the gateway's DB
  are inherently tenant-scoped.

Level 2: Per-user ownership within tenant
  When OIDC is enabled, providers are stamped with openshell.ai/owner.
  User-owned providers are only visible to their owner + admins.
  Shared (admin-created) providers have no owner label and are visible to all.

  Resolution order when binding a sandbox to a provider by name:
    1. User's own provider (if exists with that name)
    2. Shared provider (fallback)

Credentials Driver Configuration:
  charts/openshell/templates/credentials-configmap.yaml:
    Per-tenant credentials.yaml with tenant-scoped client_id

  charts/openshell/templates/secrets.yaml:
    openshell-credentials-secrets: per-tenant credential secrets

4.10 CLI Configuration
────────────────────────────────────────────────────────────────────────────────

File: scripts/openshell/configure-cli.sh (186 lines)

Purpose: Register a deployed gateway with the local openshell CLI.

Flow:
  1. Auto-detect platform (OCP vs Kind)
  2. Derive gateway endpoint:
     Kind: https://openshell-<tenant>.localtest.me:30443
     OCP:  https://openshell-<tenant>.<apps-domain>
  3. Derive OIDC issuer URL:
     Kind: http://keycloak.localtest.me:30080/realms/openshell
     OCP:  https://keycloak-<keycloak-ns>.<apps-domain>/realms/openshell
  4. Extract mTLS certificates from K8s secrets:
     openshell-server-tls → ca.crt
     openshell-client-tls → tls.crt, tls.key
     Writes to: ~/.config/openshell/gateways/<name>/mtls/
  5. Register: openshell gateway add <name> \
       --url <endpoint> \
       --issuer <oidc-issuer> \
       --client-id openshell-cli \

================================================================================
5. DATA FLOW
================================================================================

Tenant Deployment Data Flow:
  1. deploy-tenant.sh receives <tenant> argument
  2. Detects platform (OCP/Kind) → determines ingress type and OIDC issuer
  3. Creates K8s namespace → labels with tenant identity
  4. Invokes Helm with tenant-specific values:
     tenant → namespace name, audience, driver namespace
     oidc.issuer → Keycloak URL
     oidc.audience → tenant name (scopes JWT validation)
     ingress.host → per-tenant hostname
  5. Helm chart templates render all resources with tenant namespace
  6. certgen Job creates TLS secrets (server + client + JWT signing keys)
  7. StatefulSet creates gateway pod with 3 containers communicating via UDS

Authentication Data Flow:
  1. User invokes openshell login
  2. CLI opens browser → Keycloak PKCE Authorization Code flow
  3. Keycloak issues JWT with:
     iss: https://keycloak.<domain>/realms/openshell
     aud: [<tenant>, "account"]  (based on group membership + audience scope)
     sub: <user-uuid>
     realm_access.roles: ["openshell-admin" | "openshell-user"]
  4. CLI stores tokens locally, sends Bearer JWT in gRPC metadata
  5. Gateway validates: iss matches config, aud contains configured audience
  6. On per-user operations: extracts sub from validated JWT → owner label

Sandbox Creation Data Flow:
  1. CLI → Gateway (gRPC CreateSandbox with Bearer JWT)
  2. Gateway validates JWT (iss, aud, roles)
  3. Gateway stamps openshell.ai/owner = JWT.sub
  4. Gateway → Compute Driver (gRPC over UDS)
  5. Compute Driver creates Sandbox CRD in tenant namespace
  6. agent-sandbox-controller reconciles → creates Pod + PVC
  7. Init container copies supervisor binary into sandbox
  8. Supervisor starts, establishes kernel isolation, runs agent process

6. STATE MANAGEMENT
================================================================================

Per-Tenant Persistent State:
  1. SQLite Database: /data/openshell.db (PVC, 1Gi default)
     - Sandbox metadata, provider configs, credentials
     - One DB per gateway instance (tenant isolation)
  2. Sandbox PVCs: workspace persistence per sandbox pod
  3. TLS Secrets: openshell-server-tls, openshell-client-tls
     - cert-manager managed, auto-renewal
  4. JWT Signing Keys: openshell-gateway-jwt-keys
     - Ed25519 keypair, generated by certgen hook
  5. Gateway Secrets: openshell-gateway-secrets
     - SSH handshake secret (stable across upgrades)

Shared Persistent State:
  1. Keycloak DB: PostgreSQL in keycloak namespace
     - Realm config, users, groups, clients, scopes
  2. cert-manager CA: openshell-ca-secret in cert-manager namespace
     - ECDSA P-256 CA certificate, 10-year validity
  3. agent-sandbox-controller: StatefulSet in agent-sandbox-system
  4. Test user passwords: K8s secrets (openshell-alice-password, etc.)
