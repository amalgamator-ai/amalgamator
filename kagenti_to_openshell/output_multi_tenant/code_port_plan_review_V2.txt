1. EXECUTIVE SUMMARY
================================================================================

  [UNCHANGED FROM V2]

  This plan ports Kagenti's multi-tenant deployment support to OpenShell.
  The feature operates at two complementary layers:

    Layer 1 — Per-User Ownership (Rust gateway code changes):
      Within a single gateway instance, enforce per-user isolation via the
      openshell.ai/owner label. This is the core Rust work.

    Layer 2 — Gateway-Per-Tenant (Helm/infrastructure changes):
      Each tenant gets a dedicated Kubernetes namespace with an isolated
      gateway stack. This is primarily Helm chart and deployment tooling.

  Both layers compose. Backward compatibility is preserved: when OIDC is
  disabled or ownership config is absent, all ownership logic is bypassed.

  REVIEW FIX on deny_unknown_fields:

  The V2 plan stated:
    "NOTE on #[serde(deny_unknown_fields)]: The OidcConfig struct itself
     does NOT have deny_unknown_fields (only GatewayFileSection does)."

  This is INCORRECT. Verified: OidcConfig HAS #[serde(deny_unknown_fields)]
  at line 462 of config.rs.

  CORRECTED NOTE:
    OidcConfig has #[serde(deny_unknown_fields)]. Adding groups_claim with
    #[serde(default)] is SAFE because deny_unknown_fields only rejects
    fields present in the INPUT that are NOT defined in the struct. It does
    NOT reject missing fields — those use their serde defaults. So:
    - Old configs without groups_claim → groups_claim defaults to "" → OK
    - New configs with groups_claim → groups_claim is a known field → OK
    - Configs with a TYPO like "group_claim" → rejected with clear error → OK

  Since GatewayFileSection.oidc is typed as Option<OidcConfig>, the
  deny_unknown_fields on OidcConfig applies when deserializing the
  [openshell.gateway.oidc] TOML section. This means the groups_claim
  field MUST be added to OidcConfig (as proposed) — it cannot be added
  only to GatewayFileSection.

  [MOSTLY UNCHANGED FROM V2, with two fixes:]

  REVIEW FIX 1: Runtime admin guard uses empty admin_role (Step 11A)

  The V2 plan's runtime guard has a functional bug:

    V2 CODE (BUGGY):
      if !ownership_config.enabled {
          if let Principal::User(user) = &principal {
              if !user.identity.roles.iter()
                  .any(|r| r == &ownership_config.admin_role) {
                  return Err(Status::permission_denied(
                      "provider creation requires admin role"
                  ));
              }
          }
      }

  BUG: When ownership is disabled, ownership_config() returns
  OwnershipEnforcement::disabled() which sets admin_role to "". The check
  `r == &ownership_config.admin_role` compares against "", which NEVER
  matches any role. Result: ALL users (including admins) are denied from
  creating providers when ownership is disabled but OIDC is configured.

  This happens because OwnershipEnforcement::disabled() does not carry
  the OIDC admin_role — it's only populated when ownership is enabled.

  CORRECTED CODE:
      if !ownership_config.enabled {
          // When ownership is disabled, preserve the existing admin-only
          // restriction for provider creation. Read admin_role directly
          // from the OIDC config (not from OwnershipEnforcement which
          // has an empty admin_role when disabled).
          if let Some(ref oidc) = state.config.oidc {
              if !oidc.admin_role.is_empty() {
                  if let Principal::User(user) = &principal {
                      if !user.identity.roles.iter()
                          .any(|r| r == &oidc.admin_role) {
                          return Err(Status::permission_denied(
                              "provider creation requires admin role"
                          ));
                      }
                  }
              }
          }
      }

  WHY THIS FIX IS CORRECT:
    - When OIDC is configured with roles, admin_role is "openshell-admin"
    - The guard checks the user's roles against the OIDC admin_role
    - Admin users pass the check; non-admin users are denied
    - When OIDC is not configured (state.config.oidc is None), the guard
      is skipped entirely (no OIDC = no role-based restriction)
    - When OIDC is configured but admin_role is empty (auth-only mode),
      the guard is skipped (matching current behavior where empty roles
      mean auth-only)

  REVIEW FIX 2: Scope requirement note (Step 11D)

  The V2 plan proposes changing CreateProvider's #[rpc_auth] annotation
  from role="admin" to role="user". But the current annotation is:

    #[rpc_auth(auth = "bearer", scope = "provider:write", role = "admin")]

  The `scope = "provider:write"` requirement is preserved. When
  scopes_enabled is true in AuthzPolicy (i.e., the OIDC scopes_claim
  is configured), users will also need the "provider:write" scope
  (or "openshell:all") to create providers. This is enforced by
  AuthzPolicy.check() at authz.rs line 98.

  IMPACT: In deployments using scopes, the OIDC provider must grant
  "provider:write" scope to users who should create their own providers.
  Without this scope, the scope check at the multiplex layer will reject
  the request before the handler is reached.

  RECOMMENDATION: Add a note in the deployment documentation that when
  multi-tenancy is enabled with scope-based authorization, the
  "provider:write" scope must be granted to user-role principals who
  need to create providers. This does NOT require code changes — it's
  a configuration concern.

  When scopes_enabled is false (the common case — scopes_claim defaults
  to empty), the scope check is skipped entirely (authz.rs line 98:
  `if self.scopes_enabled { self.check_scope(...) }`).
