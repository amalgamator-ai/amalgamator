1. ISSUES FOUND AND FIXED
================================================================================

This review identified 6 issues in the V2 porting plan. All issues have
been addressed in the corrected plan.

HIGH ISSUES (1):

  ISSUE R2-1: Provider runtime guard uses empty admin_role
    Affected: Step 11A
    Problem: When ownership is disabled, ownership_config() returns
      OwnershipEnforcement::disabled() which sets admin_role to "".
      The runtime guard in handle_create_provider checks:
        user.identity.roles.iter().any(|r| r == &ownership_config.admin_role)
      Since admin_role is "", this comparison NEVER matches any role.
      Result: ALL users (including admins) are denied from creating
      providers when ownership is disabled but OIDC is configured.
    Why it matters: This is a functional regression — deployments that
      upgrade to the new code with OIDC enabled but ownership disabled
      would find that no user can create providers, breaking existing
      admin workflows.
    Fix: Read admin_role directly from state.config.oidc (the OIDC
      configuration) instead of from OwnershipEnforcement. The corrected
      code checks `state.config.oidc.as_ref().map(|o| &o.admin_role)`
      which always has the correct role name ("openshell-admin") when
      OIDC is configured, regardless of ownership state.
    Validation: Added two test cases —
      admin_can_create_provider_when_ownership_disabled and
      user_cannot_create_provider_when_ownership_disabled.

MEDIUM ISSUES (2):

  ISSUE R2-2: OidcConfig deny_unknown_fields claim incorrect
    Affected: Step 2A (NOTE), Step 3 (Prerequisites)
    Problem: The V2 plan states "The OidcConfig struct itself does NOT
      have deny_unknown_fields (only GatewayFileSection does)." Verified:
      OidcConfig HAS #[serde(deny_unknown_fields)] at line 462 of
      config.rs.
    Why it matters: While the proposed fix (adding groups_claim with
      #[serde(default)]) is still correct and safe, the reasoning is
      wrong. An implementer reading the plan might make incorrect
      assumptions about OidcConfig's serde behavior. More importantly,
      knowing that OidcConfig has deny_unknown_fields confirms that
      groups_claim MUST be added to OidcConfig itself — it cannot be
      added only to GatewayFileSection or an intermediate struct.
    Fix: Corrected the NOTE to accurately describe the
      deny_unknown_fields behavior and its implications. Added
      explanation of why adding #[serde(default)] fields to a
      deny_unknown_fields struct is safe.

  ISSUE R2-3: Scope requirement not mentioned for provider creation
    Affected: Step 11D
    Problem: The current CreateProvider annotation is:
      #[rpc_auth(auth = "bearer", scope = "provider:write", role = "admin")]
      The V2 plan mentions changing role="admin" to role="user" but does
      not mention the existing scope = "provider:write" requirement.
      When scopes_enabled is true in AuthzPolicy, users need BOTH the
      role AND the scope to pass authorization.
    Why it matters: In deployments using OIDC scopes (scopes_claim is
      configured), regular users would be blocked from creating providers
      at the authorization layer if they don't have "provider:write"
      scope — even though the role check passes. The implementer and
      deployer need to know about this dependency.
    Fix: Added documentation note about the scope requirement. When
      scopes_enabled is false (the common case — scopes_claim defaults
      to empty), scope checking is skipped entirely (authz.rs line 98).
      When scopes are used, the OIDC provider must grant "provider:write"
      to user-role principals. Added as Risk #12 in Risk Analysis.

LOW ISSUES (3):

  ISSUE R2-4: labels_from_metadata helper is dead code with wrong bounds
    Affected: Step 4
    Problem: The ownership module includes a labels_from_metadata helper
      function with generic bounds M: AsRef<HashMap<String, String>>.
      Two issues: (1) The protobuf ObjectMeta does not implement
      AsRef<HashMap<String, String>>, so the helper cannot be used with
      protobuf types as intended. (2) The helper is never called anywhere
      in the plan — all ownership enforcement code uses the inline
      pattern `sandbox.metadata.as_ref().map(|m| &m.labels).cloned()
      .unwrap_or_default()`.
    Why it matters: Dead code with incorrect trait bounds would cause a
      compile error if someone tried to use it, creating confusion.
    Fix: Removed the labels_from_metadata function entirely. The inline
      pattern used throughout the plan is clear and idiomatic.

  ISSUE R2-5: Pod template labels in wrong template file
    Affected: Step 15D
    Problem: The V2 plan proposes adding tenant labels to
      statefulset.yaml. However, the pod template is defined in the
      shared partial _gateway-workload.tpl (which defines
      "openshell.gatewayPodTemplate"). Both statefulset.yaml and
      deployment.yaml reference this shared template. Adding labels
      only to statefulset.yaml would miss the Deployment workload shape.
    Why it matters: When using the Deployment workload shape
      (workload.kind=deployment), pods would not get tenant labels.
    Fix: Add tenant labels to _gateway-workload.tpl instead of
      statefulset.yaml. This ensures both workload shapes (StatefulSet
      and Deployment) get tenant labels without duplication.

  ISSUE R2-6: ClusterRole name missing existing suffix
    Affected: Step 16B
    Problem: The V2 plan proposes adding tenant.id to the ClusterRole
      name as: {{ include "openshell.fullname" . }}-{{ .Values.tenant.id }}
      But the existing name includes a "-node-reader" suffix:
      {{ include "openshell.fullname" . }}-node-reader
      The proposed change drops this suffix.
    Why it matters: Dropping the suffix would change the resource name
      for ALL deployments (not just multi-tenant), potentially breaking
      existing ClusterRoleBindings that reference the old name.
    Fix: Preserve the existing suffix when adding tenant uniqueness:
      {{ include "openshell.fullname" . }}-node-reader-{{ .Values.tenant.id }}

4. CONVERGENCE ASSESSMENT
================================================================================

The plan has improved significantly across iterations:

  V1:    11 issues (3 critical, 3 high, 3 medium, 2 low)
  V2:    6 issues (1 high, 2 medium, 3 low)  — 45% reduction

  No critical issues remain. The single HIGH issue (R2-1: empty admin_role
  in runtime guard) is a clear functional bug with a straightforward fix.
  The MEDIUM issues are documentation accuracy (R2-2) and deployment
  guidance (R2-3). The LOW issues are code cleanliness (R2-4, R2-5, R2-6).

  The plan is architecturally sound. The two-layer approach (per-user
  ownership + gateway-per-tenant) is well-designed, leverages existing
  OpenShell infrastructure correctly, and maintains backward compatibility.

  KEY RISK REMAINING: The provider role change (Step 11D) affects ALL
  deployments. The runtime guard (Step 11A, now corrected) mitigates this,
  but it adds application-layer complexity on top of the macro-layer check.
  This is the most nuanced aspect of the plan and should receive extra
  review attention during implementation.
