1. ISSUES FOUND AND FIXED
================================================================================

This review identified 11 issues in the V1 porting plan, categorized by
severity. All issues have been addressed in the corrected plan.

CRITICAL ISSUES (3):

  ISSUE C1: OwnershipConfig naming collision
    Affected: Steps 3 and 12
    Problem: The plan defined two structs named "OwnershipConfig" in different
      modules — one in auth/ownership.rs (runtime enforcement config with
      {enabled, admin_role}) and one in openshell-core/config.rs (serializable
      TOML config with {enabled}). Having two structs with the same name in
      different crates creates confusion, import ambiguity, and maintenance risk.
    Fix: Renamed the runtime struct to OwnershipEnforcement (Step 3) and the
      config struct to OwnershipSettings (Step 12). Clear separation: Settings
      is what you configure, Enforcement is what the runtime uses.

  ISSUE C2: Provider listing dual-query pagination bug
    Affected: Step 9C
    Problem: The original plan listed user-owned providers via one query and
      shared (no-owner) providers via a separate query, each with independent
      limit/offset. This breaks pagination semantics: with limit=50, the
      combined result could contain up to 100 items. Offset-based pagination
      would skip or double-count items.
    Fix: Replaced with a single-query approach: fetch all providers, filter
      in-memory for (owned-by-caller OR no-owner), then apply skip/take for
      correct pagination. Acceptable for provider collections which are
      typically small (tens, not thousands). Matches how SQLite's
      list_with_selector already works (load all, filter in memory).

  ISSUE C3: Provider CreateProvider role change incompatible with macro
    Affected: Step 9
    Problem: The plan proposed changing CreateProvider from Role::Admin to
      Role::User "when ownership is enabled." However, #[rpc_auth(role = "admin")]
      is a compile-time annotation generated by the rpc_authz proc macro. It
      cannot be toggled at runtime based on configuration.
    Fix: Change the annotation to role = "user" permanently, but add a runtime
      guard in handle_create_provider: when ownership is NOT enabled, enforce
      admin-only via an explicit role check in the handler body. This preserves
      backward compatibility — existing non-ownership deployments still require
      admin role for provider creation.

HIGH ISSUES (3):

  ISSUE H1: Missing ownership enforcement for exec/SSH/watch/attach/detach
    Affected: Steps 6-8 (gap)
    Problem: The plan covered ownership enforcement for create, list, get, and
      delete sandbox operations but did NOT address: WatchSandbox (line 575),
      ExecSandbox (line 803), ExecSandboxInteractive (line 1251),
      CreateSshSession (line 1330), AttachSandboxProvider (line 290), and
      DetachSandboxProvider (line 404). These are all sandbox access operations
      that non-owners should not be able to perform.
    Fix: Added new Step 8b covering all sandbox access handlers. Each handler
      must extract Principal before into_inner() and enforce ownership on the
      target sandbox. Added corresponding test cases in Step 18.

  ISSUE H2: Missing WatchSandbox ownership filtering
    Affected: Step 8b (new)
    Problem: WatchSandbox opens a streaming connection for sandbox events. If
      a non-owner could watch a sandbox, they would see all status changes,
      logs, and events — a significant information leak. The original plan's
      architecture section noted "no watch bus filtering needed" for
      gateway-per-tenant, but did not address per-user ownership within a
      single gateway's watch stream.
    Fix: Added ownership check at the START of handle_watch_sandbox, before
      subscribing to any buses. The sandbox is fetched by ID and ownership
      enforced, same pattern as get/delete.

  ISSUE H3: Duplicate label constants across crates
    Affected: Steps 3 and 4
    Problem: The plan defined LABEL_OWNER and LABEL_TENANT constants in both
      auth/ownership.rs (openshell-server) and driver_utils.rs (openshell-core).
      Identical string constants in two different crates create maintenance
      drift risk — if one is changed, the other may not be updated.
    Fix: Define constants ONLY in openshell-core/driver_utils.rs (the shared
      crate). The ownership module in openshell-server imports them via
      `use openshell_core::driver_utils::{LABEL_OWNER, LABEL_TENANT};`.
      This is safe because openshell-server already depends on openshell-core.

MEDIUM ISSUES (3):

  ISSUE M1: validate_label_selector called on server-generated selector
    Affected: Step 7
    Problem: The original plan called validate_label_selector() on the merged
      selector (user-provided + server-generated owner filter). The server-
      generated portion is trusted by construction. Validating it is: (a)
      unnecessary overhead on every list call, and (b) risky if
      sanitize_label_value produces a value that the validator rejects
      (e.g., an empty value after sanitization).
    Fix: Only validate the user-provided label_selector. The merged selector
      is constructed from a validated user part and a trusted server part.

  ISSUE M2: sanitize_label_value doesn't enforce K8s start/end rule
    Affected: Step 3
    Problem: Kubernetes label values must begin and end with an alphanumeric
      character. The original sanitize_label_value only filtered characters
      and truncated to 63 chars, but did not trim leading/trailing non-
      alphanumeric characters. Example: sanitize_label_value("-test-")
      would produce "-test-" which is an invalid K8s label value.
    Fix: Added trim_start_matches/trim_end_matches for non-alphanumeric
      characters after the initial character filtering. Added test case
      for this edge case.

  ISSUE M3: handle_create_provider code not shown for principal extraction
    Affected: Step 9B
    Problem: The plan showed the modified create_provider_record() signature
      with the new owner parameter, and mentioned modifying "the gRPC handler
      that calls create_provider_record" but did not provide the actual code
      for handle_create_provider. This is a critical integration point where
      the principal must be extracted before request.into_inner().
    Fix: Added complete handle_create_provider code showing principal
      extraction, ownership resolution, and the modified call to
      create_provider_record with owner.as_deref().

LOW ISSUES (2):

  ISSUE L1: Redundant parse_object_labels function
    Affected: Step 3
    Problem: The plan defined parse_object_labels(labels_json: Option<&str>)
      which parses a JSON string into a HashMap. However, the enforcement code
      in Steps 7-8 correctly uses sandbox.metadata.labels (the protobuf
      HashMap<String, String>), not a JSON string. The function would never be
      called in the actual integration.
    Fix: Removed parse_object_labels from the ownership module. The protobuf
      ObjectMeta.labels field is already a HashMap<String, String> — no JSON
      parsing needed.

  ISSUE L2: extract_principal helper function missing
    Affected: Steps 6-8b
    Problem: The plan repeatedly showed the same 4-line pattern for extracting
      Principal from request extensions across multiple handler functions.
      This should be a reusable helper to reduce boilerplate and ensure
      consistent fallback behavior.
    Fix: Added extract_principal<T>(request: &tonic::Request<T>) -> Principal
      helper to the ownership module. All handler modifications use this
      helper instead of inline extraction.
