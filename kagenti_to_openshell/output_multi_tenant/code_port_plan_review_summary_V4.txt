1. ISSUES FOUND AND FIXED
================================================================================

This review identified 8 issues in the V4 porting plan. All issues have
been addressed in the corrected plan.

HIGH ISSUES (2):

  ISSUE R4-1: Owner labels do not flow from ObjectMeta.labels to compute
              drivers — two separate label maps exist
    Affected: Steps 7, 12, and Section 11 (Label Flow Diagram)
    Problem: The V4 plan stamps owner labels on request.labels, which
      flows into Sandbox.metadata.labels (ObjectMeta). But the compute
      drivers receive labels through a COMPLETELY SEPARATE path:
        SandboxSpec.template.labels → DriverSandboxTemplate.labels

      These are independent label maps in the protobuf schema:
        - Sandbox.metadata (ObjectMeta) has labels field 4
        - SandboxSpec.template (SandboxTemplate) has labels field 4
      They are NOT the same map and do NOT share data.

      Verified data flow:
        driver_sandbox_template_from_public() at compute/mod.rs line 1598:
          labels: template.labels.clone()
        This copies SandboxTemplate.labels, NOT ObjectMeta.labels.

      The V4 plan's Label Flow Diagram (Section 11) incorrectly claims:
        "labels: template.labels.clone() (direct pass-through)"
      implying that owner labels in ObjectMeta flow through template.
      They do NOT.

      Result: Owner labels stamped on ObjectMeta would appear in the
      persistence layer but NOT on K8s pods or Docker containers. The
      K8s driver's sandbox_labels() (Step 12) reads from
      spec.template.labels and would find NO owner labels.

    Why it matters: This is a functional gap in the K8s and Docker driver
      label propagation. kubectl filtering by openshell.ai/owner would
      not work. The Label Flow Diagram would mislead implementers.

    Fix: Step 7 must stamp owner labels on BOTH ObjectMeta.labels AND
      SandboxTemplate.labels. After stamp_owner_labels generates the
      labels, copy LABEL_OWNER and LABEL_TENANT to spec.template.labels:
        if let Some(owner) = labels.get(LABEL_OWNER) {
            template.labels.insert(LABEL_OWNER.to_string(), owner.clone());
        }
      Corrected Label Flow Diagram in Section 11 shows both paths.

  ISSUE R4-8: Sandbox labels not persisted in DB labels column on creation
    Affected: Steps 7, 8
    Problem: compute/mod.rs create_sandbox() at line 499 calls
      store.put_if() with labels: None:
        self.store.put_if(
            Sandbox::object_type(), &sandbox_id, ...,
            &sandbox.encode_to_vec(),
            None,                    // labels NOT in DB column
            WriteCondition::MustCreate,
        )

      Owner labels ARE in the protobuf payload (sandbox.metadata.labels)
      but are NOT stored in the database's labels column. The labels
      column is used by list_with_selector for filtering.

      The delete path at lines 682-702 DOES serialize labels to the DB
      column. But initial creation does NOT.

    Why it matters: Step 8 (sandbox list handler) adds owner-based
      filtering via list_with_selector. Without labels in the DB column,
      newly created sandboxes won't match the owner label selector.
      A user creates a sandbox and immediately lists → sandbox is missing.

    Fix: In create_sandbox(), serialize metadata.labels to the labels
      parameter before calling put_if, using the same pattern as the
      delete path (lines 682-702). This also fixes a pre-existing issue
      where user-provided labels are not queryable after creation.

MEDIUM ISSUES (3):

  ISSUE R4-2: Provider label persistence path is incomplete
    Affected: Step 11A
    Problem: Provider creation (create_provider_record at provider.rs
      line 119-127) passes labels: None to store.put_if(). Even when
      Step 11A stamps owner labels on provider.metadata.labels, the
      labels are NOT stored in the database's labels column.

      Additionally, provider metadata is conditionally initialized at
      lines 73-82. If the client sends a provider WITHOUT metadata
      (metadata.is_none()), create_provider_record creates new metadata
      with empty labels. The V4 plan's stamping code uses if-let on
      provider.metadata, which would silently skip stamping when metadata
      is None.

    Why it matters: Provider owner labels won't be queryable via
      list_with_selector. The in-memory filtering in Step 11B would
      still work (it decodes protobuf payloads), but DB-level filtering
      fails. The conditional metadata initialization could silently
      skip label stamping.

    Fix: (1) Ensure metadata exists before stamping by creating default
      ObjectMeta if None. (2) Serialize labels to the put_if labels
      parameter in create_provider_record, matching the sandbox fix.

  ISSUE R4-3: Identity construction sites not fully enumerated
    Affected: Step 1, Section 3
    Problem: The V4 plan lists 3 vague categories of Identity
      construction sites. Verification found at least 11 specific sites:

      Production code (6 sites):
        oidc.rs:342, multiplex.rs:520, multiplex.rs:770,
        supervisor_session.rs:878, grpc/auth_rpc.rs:300,
        inference.rs:1005

      Test helpers (5 sites):
        multiplex.rs:1419, auth/authenticator.rs:142,
        auth/guard.rs:104, grpc/policy.rs:3924, grpc/policy.rs:4026

    Why it matters: Every missed site produces a "missing field: groups"
      compile error. While Rust catches these automatically, an implementer
      would need to discover each one through trial-and-error. The plan
      should enumerate them to save time and prevent confusion.

    Fix: Replace the 3-category list with the complete 11-site
      enumeration with exact file:line references.

  ISSUE R4-4: Additional provider admin methods not addressed
    Affected: Step 11D
    Problem: The V4 plan changes #[rpc_auth] roles for create_provider,
      update_provider, delete_provider. But there are 5 additional
      admin-only provider methods:
        - import_provider_profiles (line 400)
        - update_provider_profiles (line 408)
        - rotate_provider_credential (line 440)
        - delete_provider_refresh (line 456)
        - delete_provider_profile (line 472)

      The plan does not address whether these should also get ownership
      enforcement or remain admin-only.

    Why it matters: Without explicit decisions, implementers may
      inconsistently handle these methods. Some (like credential
      rotation) affect provider runtime behavior for all sandboxes.

    Fix: Explicitly document that these methods REMAIN admin-only
      (profile and credential operations are infrastructure concerns).
      However, when ownership is enabled, admin callers should still
      pass the ownership check on the target provider.

LOW ISSUES (3):

  ISSUE R4-5: OidcClaims listing omits existing #[serde(default)] attributes
    Affected: Step 2A
    Problem: The V4 plan shows OidcClaims fields without the
      #[serde(default)] attributes on preferred_username and email that
      exist in the actual code. This is a cosmetic inaccuracy.
    Why it matters: Minor — may confuse an implementer who sees different
      attributes in the actual file vs the plan.
    Fix: Update the OidcClaims listing to include #[serde(default)] on
      preferred_username and email for accuracy.

  ISSUE R4-6: certgen SAN configuration uses different pattern than plan
    Affected: Step 18
    Problem: The V4 plan shows adding SANs via a direct --server-san
      flag, but the actual certgen.yaml uses openshell.defaultServerDnsNames
      helper and iterates over pkiInitJob.serverDnsNames lists.
    Why it matters: Minor — the V4 plan's approach works but is
      inconsistent with existing template patterns.
    Fix: Note that the existing certgen pattern should be extended
      to include ingress.host, following the established iteration.

  ISSUE R4-7: Provider metadata may not exist when stamping labels
    Affected: Step 11A
    Problem: The V4 plan's code uses:
        if let Some(ref mut metadata) = provider.metadata { ...stamp... }
      When metadata is None (client didn't send it), the if-let fails
      and labels are never stamped. Then create_provider_record creates
      metadata with empty labels.
    Why it matters: Provider ownership silently fails for requests
      without metadata. The provider is created without an owner label.
    Fix: Ensure metadata exists before stamping (create default
      ObjectMeta if None). Merged into Issue R4-2 fix.

    R4-1: Add 4 lines to stamp labels on template (mechanical)

           from existing delete path)

  ownership + gateway-per-tenant) is architecturally sound and has
  been stable since V1.

  - Global name uniqueness → documented as known limitation
  - Pre-existing resources on ownership enable → documented migration path
