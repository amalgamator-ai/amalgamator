3. OBSERVATIONS (documented, not actionable)
================================================================================

OBSERVATION A — TOCTOU in delete/update handlers (LOW)
  The ownership check and the actual mutation (delete/update) are not
  atomic — there is a window where the resource could theoretically change
  between the ownership fetch and the operation. However:
  - No API exists to modify sandbox labels after creation
  - Provider update uses CAS (compare-and-swap), providing incidental
    protection against concurrent modifications
  - Exploitability: None today, theoretical in future if label-mutation
    APIs are added

OBSERVATION B — No Sandbox principal tests in ownership.rs (LOW)
  Tests cover User and Anonymous variants but not Sandbox. The code
  handles all non-User variants uniformly via `let Principal::User(user)
  = ... else { return }`, so Sandbox is handled correctly. Tests would
  serve as documentation and regression protection.

OBSERVATION C — ListProvidersRequest lacks label_selector (INFORMATIONAL)
  Unlike ListSandboxesRequest which has label_selector for user-supplied
  filtering, ListProvidersRequest only has limit/offset. Ownership
  filtering works correctly via server-side owner_label_selector, but
  users cannot supply their own label filters for providers. This is a
  proto limitation outside the scope of this patch.

OBSERVATION D — ownership_config() per-call allocation (LOW)
  The method builds a new OwnershipConfig on every handler call,
  allocating 2 strings. Could be cached in ServerState at startup since
  config is immutable at runtime. The allocation is trivially small.

OBSERVATION E — Subject collision via sanitization (KNOWN LIMITATION)
  Two different OIDC subjects can sanitize to the same K8s label value
  (e.g., "user@a.com" → "user_a.com" ← "user_a.com"). Inherent in
  the K8s 63-char alphanumeric constraint. Unlikely with UUID-based
  subjects, possible with email-based subjects. Documented.
