1. EXPLANATION OF THE TEST PLAN
================================================================================

1.1 WHAT WAS GENERATED
───────────────────────

The test plan (test_plan_V1.txt) is a comprehensive testing strategy for the
multi-tenant deployment feature being ported from Kagenti to OpenShell. It
covers all 20 steps of the reviewed code porting plan (code_port_plan_review_V4.txt)
with approximately 143 test cases organized across 14 test files.

1.2 APPROACH
────────────

The test plan was developed through deep analysis of three dimensions:

  A) Source project test patterns (Kagenti):
     Analyzed Kagenti's E2E tests in kagenti/tests/e2e/openshell/:
     - test_T4_2_tenant_isolation.py (637 lines): Tests auth isolation via
       JWT audience scoping, RBAC isolation via kubectl auth can-i, and
       credential isolation via secret/ConfigMap scoping.
     - test_T4_4_per_user_isolation.py (491 lines): Tests owner label
       stamping, per-user list filtering, cross-user access denial, and
       admin bypass.
     These Kagenti tests are Python E2E tests that run against a live
     Kubernetes cluster with Keycloak. The test plan translates their
     semantic coverage into Rust unit and integration tests.

  B) Target project test conventions (OpenShell):
     Analyzed OpenShell's existing test infrastructure (~1000+ tests):
     - Unit tests: #[cfg(test)] mod tests in source files, #[test] for sync,
       #[tokio::test] for async
     - Integration tests: crates/openshell-server/tests/ with common/mod.rs
       providing TestOpenShell, PkiBundle, generate_pki(), start_test_server()
     - E2E tests: e2e/rust/tests/ with feature-gated compilation (e2e,
       e2e-docker, e2e-kubernetes)
     - Helpers: test_server_state() (in-memory SQLite), NoopTestDriver,
       FakeComputeDriver, MockAuthenticator
     - Identity construction: user_principal(subject) pattern with Identity
       struct fields (subject, display_name, roles, scopes, provider)
     - Assertions: assert_eq!, assert!, .expect_err("msg"), err.code()
       comparison

  C) Port plan requirements (code_port_plan_review_V4.txt):
     Analyzed all 20 implementation steps plus review fixes:
     - R4-1: Dual-label stamping (ObjectMeta.labels AND SandboxTemplate.labels)
     - R4-2: Provider label persistence (DB labels column)
     - R4-3: Complete Identity construction site enumeration (11 sites)
     - R4-4: Provider admin-only methods
     - R4-7: Provider metadata existence before stamping
     - R4-8: Sandbox label persistence (DB labels column on creation)

1.3 TEST ORGANIZATION
─────────────────────

The plan uses three tiers matching OpenShell's test infrastructure:

  Tier 1 — Unit Tests (Sections 3-8, 12-14):
    ~77 tests in #[cfg(test)] mod blocks within source files.
    Test pure-logic functions in isolation: sanitize_label_value(),
    stamp_owner_labels(), check_ownership(), owner_label_selector(),
    Identity construction, OidcClaims groups extraction, Config parsing.

  Tier 2 — Integration Tests (Sections 9-11, 15):
    ~54 tests in grpc/ test modules and tests/ directory.
    Exercise handler flows with in-memory SQLite: create→stamp→persist→list→
    get→delete lifecycle with real persistence and mocked compute driver.

  Tier 3 — Helm Chart Tests (Section 16):
    12 tests using `helm template` shell commands.
    Verify YAML rendering for tenant values, RBAC, ResourceQuota,
    LimitRange, certificate SANs.

1.4 KEY DESIGN DECISIONS
─────────────────────────

  1. EVERY enforcement test has a "disabled" variant:
     Each ownership check test includes a companion test with ownership
     DISABLED to verify backward compatibility. This prevents regressions
     in existing single-tenant deployments.

  2. Anti-spoofing is tested at BOTH unit and integration levels:
     stamp_strips_client_spoofed_labels (unit) verifies the function.
     create_sandbox_strips_client_spoofed_owner_label (integration) verifies
     the full handler flow. Defense in depth.

  3. Dual-label stamping has dedicated tests:
     create_sandbox_stamps_labels_on_both_metadata_and_template specifically
     verifies the R4-1 fix (the most critical review finding).

  4. DB label persistence has dedicated tests:
     create_sandbox_persists_labels_in_db_column and
     list_with_selector_finds_labeled_sandbox verify the R4-8 fix, ensuring
     owner labels survive roundtrip through the database.

  5. Test helpers follow existing patterns:
     make_user() follows guard.rs user() pattern.
     test_server_state_with_ownership() extends test_server_state().
     All Identity construction includes groups: vec![] for Step 1 compatibility.

  6. No new Cargo dependencies:
     All tests use existing test infrastructure (tokio, tonic, serde_json,
     in-memory SQLite). No new test crates are needed.

1.5 COVERAGE GAPS & KNOWN LIMITATIONS
──────────────────────────────────────

  1. K8s runtime behavior (RBAC enforcement, namespace isolation) cannot be
     unit-tested. Helm template tests verify the YAML structure, but actual
     RBAC enforcement requires a live K8s cluster (E2E only).

  2. OIDC audience scoping (cross-gateway JWT rejection) is deployment-level.
     The test plan covers groups extraction from JWT claims, but actual
     audience validation against a live IdP is not unit-testable.

  3. CLI display (Step 19) has no dedicated test. It's a cosmetic change
     that can be verified via manual inspection or E2E CLI smoke tests.

  4. SandboxIndex owner tracking (Step 14) tests are conditional on
     implementation of the optional step.

  5. Concurrent provider creation race (risk #11 in port plan) is hard
     to test deterministically. The existing persistence uniqueness tests
     cover the constraint; the test plan includes a basic concurrent
     sandbox creation test.
