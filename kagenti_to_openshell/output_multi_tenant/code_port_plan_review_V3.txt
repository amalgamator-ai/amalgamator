STEP 4: Create Ownership Module (auth/ownership.rs)
==============================================================================

  [MOSTLY UNCHANGED FROM V3, with one critical fix:]

  REVIEW FIX: Sanitized subject mismatch in check_ownership and
  owner_label_selector (Issue R3-3)

  The V3 plan has a functional bug where stamp_owner_labels() sanitizes
  the subject before storing it as a label value, but check_ownership()
  and owner_label_selector() compare/query using the RAW subject.

  V3 stamp_owner_labels (Step 4B) -- CORRECT:
    let owner = sanitize_label_value(&user.identity.subject);
    labels.insert(LABEL_OWNER.to_string(), owner);
    // Stored label value: sanitized subject

  V3 check_ownership (Step 4C) -- BUGGY:
    Some(owner) if owner == &user.identity.subject => Ok(()),
    // Compares sanitized stored value against RAW subject

  V3 owner_label_selector (Step 4D) -- BUGGY:
    Some(format!("{}={}", LABEL_OWNER, user.identity.subject))
    // Queries for RAW subject, but stored value is sanitized

  BUG SCENARIO:
    User subject: "user@example.com"
    stamp_owner_labels sanitizes to: "userexamplecom" (stored)
    check_ownership compares: "userexamplecom" == "user@example.com" -> FALSE
    Result: User is denied access to their OWN sandbox.

    This affects any OIDC provider that uses non-UUID subjects (e.g.,
    email addresses from Google, Azure AD, Okta). Keycloak UUIDs are
    unaffected since they pass through sanitization unchanged.

  CORRECTED check_ownership (Step 4C):

    pub fn check_ownership(
        principal: &Principal,
        config: &OwnershipEnforcement,
        resource_labels: &HashMap<String, String>,
        resource_kind: &str,
        resource_id: &str,
    ) -> Result<(), Status> {
        if !config.enabled {
            return Ok(());
        }
        match principal {
            Principal::User(user) => {
                if config.is_admin(principal) {
                    return Ok(());
                }
                // CRITICAL: Sanitize subject before comparison to match
                // what stamp_owner_labels() stored.
                let sanitized_subject = sanitize_label_value(&user.identity.subject);
                match resource_labels.get(LABEL_OWNER) {
                    Some(owner) if owner == &sanitized_subject => Ok(()),
                    Some(_) => Err(Status::permission_denied(format!(
                        "{resource_kind} '{resource_id}' is owned by another user"
                    ))),
                    None => Err(Status::permission_denied(format!(
                        "{resource_kind} '{resource_id}' has no owner and \
                         requires admin access"
                    ))),
                }
            }
            Principal::Anonymous => Ok(()),
            Principal::Sandbox(_) => Ok(()),
        }
    }

  CORRECTED owner_label_selector (Step 4D):

    pub fn owner_label_selector(
        principal: &Principal,
        config: &OwnershipEnforcement,
    ) -> Option<String> {
        if !config.enabled {
            return None;
        }
        match principal {
            Principal::User(user) => {
                if config.is_admin(principal) {
                    return None;
                }
                // CRITICAL: Sanitize subject to match stored label value
                let sanitized = sanitize_label_value(&user.identity.subject);
                Some(format!("{}={}", LABEL_OWNER, sanitized))
            }
            _ => None,
        }
    }

  WHY THIS FIX IS CORRECT:
    stamp_owner_labels stores: sanitize_label_value(subject)
    check_ownership compares against: sanitize_label_value(subject)
    owner_label_selector queries for: sanitize_label_value(subject)
    All three now use the same sanitized value -> comparisons match.

  --- Step 4E: sanitize_label_value (additional improvement) ---

  REVIEW NOTE: The V3 sanitizer filters characters but does not enforce
  that the result begins and ends with an alphanumeric character (a K8s
  label value requirement). For example, "-hello-" passes sanitization
  but is an invalid K8s label value.

  IMPROVED sanitize_label_value:

    pub fn sanitize_label_value(value: &str) -> String {
        let sanitized: String = value
            .chars()
            .filter(|c| c.is_alphanumeric() || *c == '-' || *c == '_' || *c == '.')
            .take(63)
            .collect();
        // K8s labels must begin and end with alphanumeric characters
        let sanitized = sanitized
            .trim_start_matches(|c: char| !c.is_alphanumeric())
            .trim_end_matches(|c: char| !c.is_alphanumeric());
        if sanitized.is_empty() {
            "unknown".to_string()
        } else {
            sanitized.to_string()
        }
    }

==============================================================================

  [SUBSTANTIALLY CORRECTED -- Issue R3-2:]

  REVIEW FIX: DriverSandbox does not have metadata.labels (Issue R3-2)

  The V3 plan says:
    "NOTE: The Sandbox type here is the protobuf-generated struct. Its
     metadata field is Option<ObjectMeta>, and ObjectMeta.labels is
     HashMap<String, String>."

  This is WRONG. Verified: In the K8s driver, Sandbox is an alias for
  DriverSandbox (driver.rs line 28):

    use openshell_core::proto::compute::v1::{
        DriverSandbox as Sandbox,
        ...
    };

  DriverSandbox (compute_driver.proto, lines 64-76) has:
    - id: String
    - name: String
    - namespace: String
    - spec: Option<DriverSandboxSpec>
    - status: Option<DriverSandboxStatus>

  There is NO metadata field. The V3 plan's code:
    if let Some(ref metadata) = sandbox.metadata {
        if let Some(owner) = metadata.labels.get(LABEL_OWNER) {
  WILL NOT COMPILE.

  HOWEVER, labels ARE available through DriverSandboxTemplate. Verified:
  The gateway populates DriverSandboxTemplate.labels via
  driver_sandbox_from_public() (compute/mod.rs, line 1598). The
  DriverSandboxTemplate is accessible through the spec:

    sandbox.spec -> DriverSandboxSpec -> template -> DriverSandboxTemplate
    DriverSandboxTemplate has labels: HashMap<String, String> (proto line 125)

  CORRECTED sandbox_labels() code:

  File: crates/openshell-driver-kubernetes/src/driver.rs

  fn sandbox_labels(sandbox: &Sandbox) -> BTreeMap<String, String> {
      let mut labels = BTreeMap::new();
      labels.insert(LABEL_SANDBOX_ID.to_string(), sandbox.id.clone());
      labels.insert(
          LABEL_MANAGED_BY.to_string(),
          LABEL_MANAGED_BY_VALUE.to_string(),
      );

      // Propagate owner and tenant labels from the sandbox template.
      // The gateway populates DriverSandboxTemplate.labels via
      // driver_sandbox_from_public() in compute/mod.rs.
      if let Some(ref spec) = sandbox.spec {
          if let Some(ref template) = spec.template {
              if let Some(owner) = template.labels.get(LABEL_OWNER) {
                  labels.insert(LABEL_OWNER.to_string(), owner.clone());
              }
              if let Some(tenant) = template.labels.get(LABEL_TENANT) {
                  labels.insert(LABEL_TENANT.to_string(), tenant.clone());
              }
          }
      }

      labels
  }

  WHY THIS FIX WORKS:
  1. Gateway creates Sandbox (gateway proto type) with metadata.labels
     including openshell.ai/owner
  2. Gateway calls compute.create_sandbox() which invokes
     driver_sandbox_from_public() (compute/mod.rs, line 1550+)
  3. driver_sandbox_from_public maps public sandbox labels to
     DriverSandboxTemplate.labels (line 1598)
  4. Compute driver receives DriverSandbox with spec.template.labels
  5. sandbox_labels() reads from spec.template.labels (CORRECTED)
  6. Labels end up on the Kubernetes Sandbox CRD object

  NOTE: The exact field path (spec.template) depends on DriverSandboxSpec
  having a template field of type DriverSandboxTemplate. This is
  confirmed by the driver's import of DriverSandboxTemplate as
  SandboxTemplate and the gateway's driver_sandbox_from_public() code.

  PREREQUISITE: Verify that the gateway's label stamping in Step 7
  happens BEFORE driver_sandbox_from_public() is called. The flow is:
    1. handle_create_sandbox_inner stamps owner label on request.labels
    2. Labels are set in the Sandbox protobuf metadata.labels
    3. compute.create_sandbox() converts Sandbox to DriverSandbox
    4. driver_sandbox_from_public copies metadata.labels to template.labels
  This ordering is correct.

  [UNCHANGED FROM V3, with one addition:]

  13. Sanitized subject identity collision (LOW)
      Risk: Two different OIDC subjects could sanitize to the same K8s
            label value. For example, "user@a.com" and "user.a.com" both
            sanitize to "useracom" (once trimmed).
      Mitigation: UUIDs (the common case) have no sanitization-related
            collisions. For email-based subjects, collisions are
            theoretically possible but extremely unlikely in practice.
            The sanitizer is a safety net for K8s compatibility, not a
            primary identifier. The OIDC subject claim is the source of
            truth; the label is an enforcement mechanism.
      Validation: Log a warning when sanitization changes the subject.
