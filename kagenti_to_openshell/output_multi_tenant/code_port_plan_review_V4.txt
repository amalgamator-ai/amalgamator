STEP 7: Modify Sandbox Create Handler (Owner Stamping)
==============================================================================

  [SUBSTANTIALLY CORRECTED -- Issues R4-1 and R4-8:]

  REVIEW FIX: Owner labels must be stamped on BOTH ObjectMeta.labels
  AND SandboxTemplate.labels (Issue R4-1)

  PROBLEM: The V4 plan stamps owner labels only on request.labels, which
  flows into Sandbox.metadata.labels (ObjectMeta). However, the K8s and
  Docker drivers receive labels through a SEPARATE path:
    SandboxSpec.template.labels → DriverSandboxTemplate.labels

  These are DIFFERENT label maps:
    - ObjectMeta.labels (Sandbox.metadata.labels) — used for persistence
      and ownership checks in the gateway.
    - SandboxTemplate.labels (Sandbox.spec.template.labels) — flows to
      compute drivers, appears on K8s pods and Docker containers.

  The V4 plan's label flow diagram (Section 11) incorrectly claims that
  owner labels flow from ObjectMeta.labels through to the compute driver.
  They do NOT. driver_sandbox_template_from_public() at line 1598 copies
  SandboxTemplate.labels, not ObjectMeta.labels.

  CORRECTED Step 7 code:

  File: crates/openshell-server/src/grpc/sandbox.rs

  After the existing code at line 123-156 (into_inner, spec extraction,
  template resolution), add owner label stamping to BOTH locations:

    // === OWNERSHIP: Extract principal BEFORE into_inner() ===
    let principal = request.extensions()
        .get::<Principal>()
        .cloned()
        .unwrap_or(Principal::Anonymous);
    let ownership_config = state.ownership_config();

    let request = request.into_inner();
    let spec = request.spec.ok_or_else(|| ...)?;

    // ... existing validation (lines 128-152) ...

    // Resolve template (existing code at line 155-156)
    let mut spec = spec;
    let template = spec.template.get_or_insert_with(SandboxTemplate::default);
    // ... existing template image defaulting (line 157-159) ...

    // === OWNERSHIP: Stamp labels (NEW) ===
    // 1. Stamp on request.labels (goes to ObjectMeta for persistence)
    let labels = crate::auth::ownership::stamp_owner_labels(
        &principal,
        &ownership_config,
        request.labels.clone(),
    );

    // 2. ALSO stamp on template.labels (goes to compute drivers)
    //    This ensures owner labels appear on K8s pods and Docker containers
    //    via the SandboxTemplate → DriverSandboxTemplate → driver path.
    if let Some(owner) = labels.get(LABEL_OWNER) {
        template.labels.insert(LABEL_OWNER.to_string(), owner.clone());
    }
    if let Some(tenant) = labels.get(LABEL_TENANT) {
        template.labels.insert(LABEL_TENANT.to_string(), tenant.clone());
    }

    // ... existing code continues ...
    let mut sandbox = Sandbox {
        metadata: Some(ObjectMeta {
            id: id.clone(),
            name: name.clone(),
            created_at_ms: now_ms,
            labels,  // <-- stamped labels
            resource_version: 0,
        }),
        spec: Some(spec),  // <-- spec.template.labels also stamped
        status: None,
    };

  WHY BOTH LOCATIONS:
    - ObjectMeta.labels: Used by the gateway for persistence, ownership
      checks (check_ownership), and label-selector queries
      (list_with_selector). Stored in the DB labels column.
    - SandboxTemplate.labels: Copied by driver_sandbox_template_from_public()
      (compute/mod.rs line 1598) to DriverSandboxTemplate.labels, which
      flows to K8s pod labels and Docker container labels.

  REVIEW FIX: Sandbox labels must be persisted in DB labels column
  (Issue R4-8)

  PROBLEM: The compute layer's create_sandbox() at compute/mod.rs line 499
  calls store.put_if() with labels: None:

    self.store.put_if(
        Sandbox::object_type(),
        &sandbox_id,
        sandbox.object_name(),
        &sandbox.encode_to_vec(),
        None,                        // <-- labels NOT persisted!
        WriteCondition::MustCreate,
    )

  This means owner labels in ObjectMeta.labels are embedded in the
  protobuf payload but NOT in the database's labels column. The label
  column is used by list_with_selector for filtering. Without it,
  owner_label_selector in Step 8 won't match newly created sandboxes.

  (The delete path at line 682-702 DOES serialize labels. But the
  initial creation does not.)

  CORRECTED: Modify compute/mod.rs create_sandbox() to serialize labels:

  File: crates/openshell-server/src/compute/mod.rs

  In create_sandbox() (line 480), BEFORE the store.put_if call:

    let labels_json = sandbox
        .metadata
        .as_ref()
        .map(|metadata| &metadata.labels)
        .filter(|labels| !labels.is_empty())
        .map(serde_json::to_string)
        .transpose()
        .map_err(|e| {
            crate::persistence::PersistenceError::Encode(format!(
                "failed to serialize labels: {e}"
            ))
        })
        .map_err(|e| Status::internal(format!("serialize labels: {e}")))?;

  Then change the put_if call (line 494-501):
    self.store.put_if(
        Sandbox::object_type(),
        &sandbox_id,
        sandbox.object_name(),
        &sandbox.encode_to_vec(),
        labels_json.as_deref(),    // <-- CHANGED from None
        WriteCondition::MustCreate,
    )

  This follows the exact pattern used in the delete path at lines 682-702.

  NOTE: This change also fixes a pre-existing issue where user-provided
  labels on sandbox creation are not queryable via label selectors.

STEP 11: Modify Provider CRUD for Per-User Ownership
==============================================================================

  [SUBSTANTIALLY CORRECTED -- Issues R4-2 and R4-4 and R4-7:]

  REVIEW FIX: Provider label persistence path is incomplete (Issue R4-2)

  PROBLEM: The V4 plan's Step 11A stamps owner labels on
  provider.metadata.labels before calling create_provider_record. This
  correctly sets the labels on the protobuf metadata. However:

  1. create_provider_record at provider.rs line 73 has:
       if provider.metadata.is_none() {
           provider.metadata = Some(ObjectMeta { ... labels: HashMap::new() ... });
       }
     If the client sends a provider WITHOUT metadata, this block creates
     new metadata with EMPTY labels, AFTER the V4 plan stamps them.
     The stamped labels would be lost.

  2. The persistence call at line 119-127 passes labels: None to
     store.put_if(). Even when labels are in the protobuf metadata, they
     are NOT stored in the database's labels column:
       store.put_if(
           Provider::object_type(),
           &provider_id,
           provider.object_name(),
           &provider.encode_to_vec(),
           None,                      // <-- labels NOT persisted!
           WriteCondition::MustCreate,
       )

  IMPACT:
    - list_with_selector won't find provider owner labels
    - The in-memory filtering approach in Step 11B needs to decode
      protobuf payloads to get metadata.labels (which it does via
      the Provider proto), but the labels still need to be in metadata

  CORRECTED Step 11A — stamp owner labels AND persist them:

  File: crates/openshell-server/src/grpc/provider.rs

  In handle_create_provider, AFTER extracting the provider from the
  request:

    let mut provider = req.provider
        .ok_or_else(|| Status::invalid_argument("provider is required"))?;

    // === OWNERSHIP: Ensure metadata exists before stamping ===
    // create_provider_record only initializes metadata when it's None.
    // We must ensure metadata exists so we can stamp labels on it.
    if provider.metadata.is_none() {
        provider.metadata = Some(
            openshell_core::proto::datamodel::v1::ObjectMeta::default()
        );
    }

    // === OWNERSHIP: Stamp owner labels on provider metadata ===
    if let Some(ref mut metadata) = provider.metadata {
        let labels = crate::auth::ownership::stamp_owner_labels(
            &principal,
            &ownership_config,
            metadata.labels.clone(),
        );
        metadata.labels = labels;
    }

  Then, inside create_provider_record (provider.rs, around line 118),
  change the store.put_if call to include serialized labels:

    // Serialize labels for DB storage (enables label-selector queries)
    let labels_json = provider
        .metadata
        .as_ref()
        .map(|metadata| &metadata.labels)
        .filter(|labels| !labels.is_empty())
        .map(serde_json::to_string)
        .transpose()
        .map_err(|e| {
            Status::internal(format!("failed to serialize labels: {e}"))
        })?;

    let result = store
        .put_if(
            Provider::object_type(),
            &provider_id,
            provider.object_name(),
            &provider.encode_to_vec(),
            labels_json.as_deref(),   // <-- CHANGED from None
            WriteCondition::MustCreate,
        )
        .await...;

  WHY THIS FIX IS NEEDED:
    Without labels in the DB column, list_with_selector won't match
    provider owner labels. The in-memory filtering in Step 11B works
    by decoding protobuf payloads, but having labels in the DB column
    is better for consistency and enables future optimizations.

  REVIEW FIX: Provider metadata must exist before stamping
  (Issue R4-7)

  The V4 plan's code:
    if let Some(ref mut metadata) = provider.metadata {
        ...stamp labels...
    }

  This if-let fails when metadata is None (client didn't send metadata).
  In that case, create_provider_record creates metadata with empty labels,
  losing the owner stamp.

  The corrected code above ensures metadata exists before stamping by
  creating a default ObjectMeta when None.

  REVIEW FIX: Additional provider admin methods not addressed (Issue R4-4)

  The V4 plan only changes #[rpc_auth] roles for:
    - create_provider (line 360)
    - update_provider (line 424)
    - delete_provider (line 464)

  But there are additional admin-only provider methods:
    - import_provider_profiles (line 400): role = "admin"
    - update_provider_profiles (line 408): role = "admin"
    - rotate_provider_credential (line 440): role = "admin"
    - delete_provider_refresh (line 456): role = "admin"
    - delete_provider_profile (line 472): role = "admin"

  DECISION: These methods should REMAIN admin-only:
    - import_provider_profiles: Bulk import is an admin operation
    - update_provider_profiles: Profile management is an admin operation
    - rotate_provider_credential: Credential rotation affects all users
    - delete_provider_refresh: Token management is an admin operation
    - delete_provider_profile: Profile cleanup is an admin operation

  Per-user ownership applies to provider CRUD (create, update, delete
  of the provider itself). Profile and credential management within a
  provider should remain admin-only because these operations affect the
  provider's runtime behavior for all sandboxes using it.

  However, when ownership is enabled, these methods should also verify
  that the admin calling them has access to the target provider (i.e.,
  the provider exists and ownership check passes). Add ownership checks
  to these handlers following the same pattern as Step 11C.

  [Steps 11B through 11E UNCHANGED FROM V4, except that Step 11B's
   in-memory filtering now works because labels ARE in the protobuf
   metadata (stamped correctly with the fixes above)]

7. RISK ANALYSIS
================================================================================

  [UNCHANGED FROM V4, with two additions:]

  12. Dual-label stamping consistency (LOW)
      Risk: Owner labels must be stamped on BOTH ObjectMeta.labels and
            SandboxTemplate.labels. If one is missed, the labels will be
            inconsistent between the persistence layer and the K8s driver.
      Mitigation: Step 7 stamps both in the same code block, using the
            same labels variable. A single stamp_owner_labels call
            generates the labels, then copies owner/tenant to both maps.
      Validation: Integration test verifies labels on both the gateway
            Sandbox proto and the K8s pod/Docker container.

  13. Labels column NULL on initial creation (pre-existing issue) (LOW)
      Risk: Before the fix in Step 7 (Issue R4-8), sandbox labels were
            NOT stored in the database's labels column on initial
            creation (store.put_if with labels: None). This is a
            pre-existing issue that affects ALL labels, not just owner.
      Mitigation: The fix in Step 7 serializes labels on creation,
            matching the pattern used in the delete/update paths.
      Validation: Verify list_with_selector returns newly created
            sandboxes with matching labels.
