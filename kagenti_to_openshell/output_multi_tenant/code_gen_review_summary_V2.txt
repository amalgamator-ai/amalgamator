ISSUE 1 — COMPILATION ERROR (CRITICAL): Missing imports in provider.rs
  Affected code: crates/openshell-server/src/grpc/provider.rs
  What is wrong: The handler functions `handle_create_provider`,
    `handle_get_provider`, `handle_list_providers`, `handle_update_provider`,
    and `handle_delete_provider` all use `Principal`, `stamp_owner_labels`,
    `check_ownership`, and `owner_label_selector` — but none of these are
    imported anywhere in provider.rs. The file would fail to compile.
  Why it matters: This is a hard compilation error that prevents the crate
    from building. It appears the V2 code generation added the imports to
    sandbox.rs but forgot to do the same for provider.rs.
  How it was fixed: Added the following imports to the handler section of
    provider.rs (after the "Handler wrappers" separator):
      use crate::auth::ownership::{check_ownership, owner_label_selector, stamp_owner_labels};
      use crate::auth::principal::Principal;

ISSUE 2 — SECURITY (HIGH): Provider create doesn't persist labels to DB
  Affected code: crates/openshell-server/src/grpc/provider.rs,
    function `create_provider_record` at the `store.put_if()` call
  What is wrong: The `create_provider_record` function passes `None` for
    the `labels` parameter to `store.put_if()`. This means ownership labels
    stamped on the provider's ObjectMeta.labels are never serialized to the
    database's labels column. Consequently, `list_messages_with_selector`
    queries (including ownership-filtered list operations via
    `list_provider_records_with_selector`) cannot find providers by their
    ownership labels.
  Why it matters: Provider ownership-filtered listing is broken. A user who
    creates a provider will not see it in their filtered list view because
    the ownership label selector produces no matches. This is the provider
    equivalent of the sandbox label persistence fix already applied in
    compute/mod.rs — the same bug pattern that was fixed for sandboxes was
    missed for providers.
  How it was fixed: Added label serialization before the `put_if` call in
    `create_provider_record`:
      let labels_json = provider.metadata.as_ref()
          .map(|metadata| &metadata.labels)
          .filter(|labels| !labels.is_empty())
          .map(serde_json::to_string)
          .transpose()
          .map_err(|e| Status::internal(...))?;
    Then changed `None` to `labels_json.as_deref()` in the `put_if` call.

ISSUE 3 — SECURITY (HIGH): Provider delete swallows store errors
  Affected code: crates/openshell-server/src/grpc/provider.rs,
    function `handle_delete_provider`
  What is wrong: Uses `if let Ok(existing) = get_provider_record(...)` to
    fetch the provider for ownership checking. If the store returns an
    error (e.g., database unreachable), the `Err` branch is silently
    ignored and the ownership check is skipped entirely, allowing the
    delete to proceed without authorization.
  Why it matters: This is the same security issue that V1 review identified
    and fixed for sandbox delete (`.ok().flatten()` pattern), but the
    equivalent fix was not applied to provider delete. A transient DB
    failure could allow an unauthorized user to delete any provider.
  How it was fixed: Changed from `if let Ok(existing) = get_provider_record`
    to using `store.get_message_by_name::<Provider>(&name).await.map_err()?`
    which propagates store errors as gRPC Status::internal. Only when the
    provider is found (`Some(existing)`) is the ownership check performed.

ISSUE 4 — STYLE (LOW): rustfmt formatting in ownership.rs
  Affected code: crates/openshell-server/src/auth/ownership.rs
  What is wrong: Several lines exceed the line length limit or have
    unnecessary trailing-argument formatting that doesn't match rustfmt
    conventions (e.g., `Status::permission_denied` call split across 3
    lines when it fits on one; `owner_label_selector` function signature
    split unnecessarily; long assert_eq! lines in tests).
  Why it matters: OpenShell uses rustfmt as part of its CI checks.
    Non-conformant formatting would fail CI even if the code compiles.
  How it was fixed: Ran `rustfmt` on ownership.rs to auto-fix all
    formatting issues.

DOCUMENTED BUT NOT FIXED (deferred to future iterations)
============================================================================

A. No CLI flag for `--oidc-groups-claim`. The `groups_claim` field is
   hardcoded to `"groups"` in the OIDC config construction from CLI args.
   When OIDC comes from the TOML file, the `groups_claim` is properly
   deserialized via serde default. This is a feature gap, not a bug — the
   default value is correct and matches the serde annotation.

B. `ownership_config()` allocates on every call. The `OwnershipConfig`
   struct is built fresh from the gateway config on each handler
   invocation. For a latency-sensitive path this could be cached in
   `ServerState`, but allocation is cheap and the struct is small.

C. Subject collision through lossy sanitization. Two distinct OIDC
   subjects can sanitize to the same label value (e.g., "alice@a.com"
   and "alice+a.com" both become "alice_a.com"). This is a known
   limitation documented in V1 review.

D. `sanitize_label_value` truncates before trimming. A 63-char string
   ending with a non-alphanumeric character will be shorter than
   necessary after trimming. This is cosmetic and documented.

E. Provider profile/credential management methods (import_provider_profiles,
   update_provider_profiles, configure_provider_refresh,
   rotate_provider_credential, delete_provider_refresh,
   delete_provider_profile) remain admin-only as intended by the plan.
