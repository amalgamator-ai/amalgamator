================================================================================
1. EXECUTIVE SUMMARY
================================================================================

This plan ports Kagenti's multi-tenant deployment support to OpenShell.
OpenShell is currently single-tenant by design: all users share the same
sandbox list, provider list, K8s namespace, and persistence store. There
is no per-user ownership, no tenant scoping, and no namespace isolation.

The port introduces two complementary layers:

  Layer 1 — Per-User Ownership (gateway-level, Steps 1-14):
    Within a single shared gateway, enforce that each user's sandboxes
    and providers are isolated from other users. Uses openshell.ai/owner
    labels stored in the persistence layer and on K8s pods/CRDs.

  Layer 2 — Gateway-Per-Tenant Deployment (Helm-level, Steps 15-18):
    For hard multi-tenancy, deploy one gateway per tenant via Helm into
    isolated K8s namespaces. Each gateway has its own database, OIDC
    audience, RBAC, TLS certificates, and resource quotas.

The approach mirrors Kagenti's architecture while translating to
idiomatic Rust and integrating with OpenShell's existing patterns.

Estimated effort: 16-21 developer-days.

================================================================================
2. ARCHITECTURAL DECISION
================================================================================

Kagenti uses a hybrid approach:
  1. Gateway-per-tenant: Hard isolation via separate K8s namespaces
  2. Per-user ownership within tenant: Soft isolation via owner labels

OpenShell will adopt the same hybrid:
  - Layer 1 (per-user ownership) is implemented as Rust code changes
    in the gateway server, requiring no external dependencies.
  - Layer 2 (gateway-per-tenant) is implemented as Helm chart changes,
    deployment scripts, and OIDC audience configuration.

WHY THIS APPROACH:
  - Matches Kagenti's proven architecture (tested in CI with E2E)
  - Layer 1 is useful standalone (soft multi-tenancy for simple deployments)
  - Layer 2 provides hard isolation (K8s namespace + RBAC boundary)
  - Both layers are backward-compatible (disabled by default)

Add method to OidcClaims impl block (after extract_roles at line 133):

  /// Extract group claims from the JWT using the configured claim path.
  /// Groups are extracted from the JSON at `groups_claim` (e.g., "groups",
  /// "cognito:groups", "https://example.com/groups"). If the path is empty
  /// or the claim is missing, self.groups remains empty.
  pub(crate) fn extract_groups(&mut self, groups_claim: &str) {
      if groups_claim.is_empty() {
          return;
      }
      // Navigate the dot-separated path in the extra JSON
      let mut current = &self.extra;
      for segment in groups_claim.split('.') {
          match current.get(segment) {
              Some(v) => current = v,
              None => return,
          }
      }
      // Parse as array of strings
      if let Some(arr) = current.as_array() {
          self.groups = arr
              .iter()
              .filter_map(|v| v.as_str().map(|s| s.to_string()))
              .collect();
      }
  }

PATTERN NOTE: This follows the exact same pattern as the existing
extract_roles() method (oidc.rs, lines 119-133), which navigates a
dot-separated claim path in self.extra and collects string values.

  use std::collections::HashMap;
  use tonic::Status;
  use crate::auth::principal::Principal;
  use openshell_core::driver_utils::{LABEL_OWNER, LABEL_TENANT, LABEL_PREFIX};

  /// Runtime ownership enforcement configuration, derived from
  /// OwnershipConfig and the gateway's OIDC admin_role.
  #[derive(Debug, Clone)]
  pub struct OwnershipEnforcement {
      /// Whether ownership enforcement is enabled.
      pub enabled: bool,
      /// Admin role that bypasses ownership checks.
      /// Sourced from OidcConfig.admin_role (e.g., "openshell-admin").
      pub admin_role: String,
      /// Optional tenant label to stamp on all resources.
      pub tenant_id: Option<String>,
  }

  impl OwnershipEnforcement {
      /// Returns true if the principal has admin privileges and should
      /// bypass ownership checks.
      pub fn is_admin(&self, principal: &Principal) -> bool {
          match principal {
              Principal::User(user) => {
                  user.identity.roles.contains(&self.admin_role)
              }
              _ => false,
          }
      }
  }

--- Step 4C: stamp_owner_labels function ---

  /// Stamp ownership labels on a resource at creation time.
  /// - Strips any client-supplied openshell.ai/* labels (anti-spoofing)
  /// - Adds openshell.ai/owner = sanitized subject
  /// - Adds openshell.ai/tenant = tenant_id (if configured)
  pub fn stamp_owner_labels(
      principal: &Principal,
      config: &OwnershipEnforcement,
      mut labels: HashMap<String, String>,
  ) -> HashMap<String, String> {
      // Anti-spoofing: remove client-supplied openshell.ai/* labels
      labels.retain(|k, _| !k.starts_with(LABEL_PREFIX));

      if !config.enabled {
          // Still strip openshell.ai/* even when ownership is disabled
          return labels;
      }

      // Stamp owner from principal
      if let Principal::User(user) = principal {
          let owner = sanitize_label_value(&user.identity.subject);
          labels.insert(LABEL_OWNER.to_string(), owner);
      }

      // Stamp tenant if configured
      if let Some(ref tenant) = config.tenant_id {
          labels.insert(LABEL_TENANT.to_string(), tenant.clone());
      }

      labels
  }

--- Step 4D: check_ownership function ---

  /// Verify that the caller owns the resource, or is an admin.
  /// Returns Ok(()) if access is allowed, Err(Status) otherwise.
  ///
  /// CRITICAL: Uses sanitize_label_value() on the subject before
  /// comparison, because stamp_owner_labels() stores the SANITIZED
  /// value. Without this, subjects containing non-label characters
  /// (e.g., "user@example.com") would never match their stored labels.
  pub fn check_ownership(
      principal: &Principal,
      config: &OwnershipEnforcement,
      resource_labels: &HashMap<String, String>,
      resource_kind: &str,
      resource_id: &str,
  ) -> Result<(), Status> {
      if !config.enabled {
          return Ok(());
      }

      match principal {
          Principal::User(user) => {
              // Admin bypass: check BEFORE ownership comparison
              if config.is_admin(principal) {
                  return Ok(());
              }

              // CRITICAL: Sanitize subject to match stored label value
              let sanitized_subject = sanitize_label_value(&user.identity.subject);

              match resource_labels.get(LABEL_OWNER) {
                  Some(owner) if owner == &sanitized_subject => Ok(()),
                  Some(_) => Err(Status::permission_denied(format!(
                      "{resource_kind} '{resource_id}' is owned by another user"
                  ))),
                  None => Err(Status::permission_denied(format!(
                      "{resource_kind} '{resource_id}' has no owner label \
                       and requires admin access"
                  ))),
              }
          }
          // Anonymous principals bypass ownership (backward-compatible)
          Principal::Anonymous => Ok(()),
          // Sandbox principals bypass ownership (sandbox-to-sandbox comms)
          Principal::Sandbox(_) => Ok(()),
      }
  }

--- Step 4E: owner_label_selector function ---

  /// Build a label selector string for owner-scoped queries.
  /// Returns None if ownership is disabled or the caller is an admin.
  ///
  /// CRITICAL: Uses sanitize_label_value() on the subject to match
  /// the stored label value set by stamp_owner_labels().
  pub fn owner_label_selector(
      principal: &Principal,
      config: &OwnershipEnforcement,
  ) -> Option<String> {
      if !config.enabled {
          return None;
      }

      match principal {
          Principal::User(user) => {
              if config.is_admin(principal) {
                  return None; // Admins see all resources
              }
              // CRITICAL: Sanitize subject to match stored label value
              let sanitized = sanitize_label_value(&user.identity.subject);
              Some(format!("{}={}", LABEL_OWNER, sanitized))
          }
          _ => None,
      }
  }

--- Step 4F: sanitize_label_value function ---

  /// Sanitize a string for use as a Kubernetes label value.
  /// K8s label values: alphanumeric, -, _, . only; max 63 chars;
  /// MUST begin and end with an alphanumeric character.
  pub fn sanitize_label_value(value: &str) -> String {
      let filtered: String = value
          .chars()
          .filter(|c| c.is_alphanumeric() || *c == '-' || *c == '_' || *c == '.')
          .take(63)
          .collect();

      // K8s labels must begin and end with alphanumeric characters
      let trimmed = filtered
          .trim_start_matches(|c: char| !c.is_alphanumeric())
          .trim_end_matches(|c: char| !c.is_alphanumeric());

      if trimmed.is_empty() {
          "unknown".to_string()
      } else {
          trimmed.to_string()
      }
  }

  use crate::auth::ownership::OwnershipEnforcement;

  impl ServerState {
      /// Build the runtime ownership enforcement configuration.
      ///
      /// The admin_role is sourced from OidcConfig to avoid duplication.
      /// When ownership is disabled OR no OidcConfig exists, returns a
      /// disabled OwnershipEnforcement (ownership checks are no-ops).
      pub fn ownership_config(&self) -> OwnershipEnforcement {
          let enabled = self.config.ownership
              .as_ref()
              .map(|o| o.enabled)
              .unwrap_or(false);

          let admin_role = self.config.oidc
              .as_ref()
              .map(|o| o.admin_role.clone())
              .unwrap_or_default();

          OwnershipEnforcement {
              enabled,
              admin_role,
              tenant_id: self.config.tenant_id.clone(),
          }
      }
  }

WHY THIS DESIGN:
  1. admin_role comes from OidcConfig, not a separate ownership field.
     This prevents the V2-R1 bug where admin_role could be empty when
     ownership was enabled without separate admin_role configuration.
  2. When OIDC is not configured, admin_role defaults to "" which means
     no user can match admin_role, but ownership is typically disabled
     in that case (enabled = false), so all checks short-circuit to Ok().
  3. When ownership is None (not configured at all), enabled defaults to
     false, making all ownership checks no-ops (backward-compatible).

8. RISK ANALYSIS
================================================================================

  1. Provider role change scope (MEDIUM)
     Risk: Changing #[rpc_auth] role from "admin" to "user" for provider
           mutations affects ALL deployments. Non-ownership deployments
           may inadvertently allow user-level provider creation.
     Mitigation: Runtime guard in Step 11E restores admin-only semantics
           when ownership is disabled.
     Validation: Test provider creation with and without ownership enabled.

  2. into_inner() ordering consistency (LOW)
     Risk: Every handler modification must extract Principal BEFORE
           into_inner(). Missing this in one handler produces a
           compile-time error (use-after-move), not a runtime bug.
     Mitigation: Rust borrow checker catches all violations.
     Validation: Compilation verifies correct ordering.

  3. Label selector query limitations (MEDIUM)
     Risk: The persistence layer's list_with_selector may not support
           complex queries (e.g., "label absent" for shared providers).
     Mitigation: Provider listing uses in-memory filtering (Step 11B).
     Validation: Verify list_with_selector handles comma-separated selectors.

  4. Name uniqueness across owners (MEDIUM)
     Risk: Sandbox and provider names are globally unique per object_type
           (objects_name_uq index on (object_type, name)). Two users
           cannot create a sandbox with the same name.
     Mitigation: Document as a known limitation. Users can use unique names
           or UUID-based naming. A future migration could add owner to the
           uniqueness constraint.
     Validation: Test that name collision returns a clear error.

  5. Sanitized subject identity collision (LOW)
     Risk: Two different OIDC subjects could sanitize to the same K8s
           label value (e.g., "user@a.com" and "user.a.com" both become
           "usera.com").
     Mitigation: UUIDs (common case) have no collisions. Email-based
           collisions are theoretically possible but extremely unlikely.
     Validation: Log a warning when sanitization changes the subject.

  6. OIDC audience vs tenant mismatch (LOW)
     Risk: If OIDC audience and tenant_id are configured inconsistently,
           users may authenticate to the wrong gateway or see mismatched
           tenant labels.
     Mitigation: Helm chart defaults audience to tenant name (Step 15B).
           The deploy script validates the mapping.
     Validation: E2E test with two tenants and cross-gateway auth rejection.

  7. Backward compatibility regression (LOW)
     Risk: Existing single-tenant deployments might break if ownership
           config parsing introduces issues.
     Mitigation: All new fields have serde(default). Ownership is disabled
           by default. Anonymous principal bypasses ownership. All tests
           include disabled-ownership scenarios.
     Validation: Verify existing test suite passes without config changes.

  8. SandboxWatchBus tenant isolation (LOW)
     Risk: SandboxWatchBus broadcasts events to all subscribers, regardless
           of ownership. A user watching sandboxes could receive events
           for sandboxes they don't own.
     Mitigation: The watch handler enforces ownership on the INITIAL
           sandbox fetch (Step 10A). The watch stream filters by the
           specific sandbox requested. Cross-sandbox event leakage is
           limited to the specific watched sandbox (which passed the
           ownership check).
     Validation: Test that watch requests for non-owned sandboxes are rejected.

  9. Migration path for existing resources (LOW)
     Risk: Sandboxes and providers created before ownership is enabled
           have no openshell.ai/owner label. When ownership is turned on,
           these resources require admin access (Step 4D: "has no owner
           label and requires admin access").
     Mitigation: Document the migration path: admin must delete or relabel
           existing resources. Alternatively, provide a migration script.
     Validation: Test behavior of pre-ownership resources under ownership.

  10. spec.template.labels path dependency (LOW)
      Risk: The K8s driver label fix (Step 12) depends on the exact proto
            field hierarchy: sandbox.spec.template.labels.
      Mitigation: Path is verified against proto definitions and import
            statements. The same path is used by existing code in the
            driver (e.g., template.labels is used for image, environment).
      Validation: Compile-time verification via Rust type system.

  11. Concurrent provider creation race (LOW)
      Risk: Two users simultaneously creating a provider with the same name
            could produce a uniqueness constraint violation.
      Mitigation: The persistence layer's put_if() with the uniqueness
            constraint returns an error. First writer wins.
      Validation: Existing persistence tests cover uniqueness enforcement.

12. NAME UNIQUENESS & KNOWN LIMITATIONS
================================================================================

  1. SANDBOX NAME UNIQUENESS IS GLOBAL
     The objects table has a unique index: (object_type, name).
     Two users cannot create sandboxes with the same name, even when
     ownership separates visibility. This is a known limitation of
     the persistence schema.

     WORKAROUND: Users can use unique names (e.g., prefix with username)
     or rely on UUID-based auto-naming (petname generator).

     FUTURE: A schema migration could add (object_type, name, owner)
     uniqueness, but this requires careful handling of shared providers
     and is out of scope for V4.

  2. PROVIDER NAME RESOLUTION ORDER
     When a user and an admin both create providers with the same name,
     the current uniqueness constraint prevents this. For user-owned +
     shared provider coexistence, names must be different.

     FUTURE: A resolution order (user > shared) could be implemented with
     a schema migration to allow duplicate names across owner scopes.

  3. SANDBOX WATCH BUS EVENTS
     The SandboxWatchBus does not filter by owner. A watch stream for a
     specific sandbox passes the ownership check at connection time, but
     the event bus itself is not owner-partitioned. This is acceptable
     because the watch is scoped to a specific sandbox ID, not a list.

  4. EXISTING RESOURCES ON OWNERSHIP ENABLE
     Pre-existing sandboxes/providers created before ownership is enabled
     have no openshell.ai/owner label. These resources become admin-only
     when ownership is turned on. An admin must delete or relabel them.
