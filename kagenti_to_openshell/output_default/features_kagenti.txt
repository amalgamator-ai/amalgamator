1. SPIFFE/SPIRE WORKLOAD IDENTITY
--------------------------------------------------------------------------------
Category:         Security / Identity
Type:             Core
Description:      Kagenti integrates SPIFFE/SPIRE to provide cryptographic
                  workload identities for all agents and tools. Each workload
                  receives a SPIFFE Verifiable Identity Document (SVID) in both
                  X.509 (for mTLS) and JWT (for API auth) formats. Identity
                  format: spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>.
                  SPIRE Server issues SVIDs, SPIRE Agent performs node-level
                  attestation, and CSI Driver mounts certificates into pods.
Key Files:
  - kagenti/auth/spiffe-idp-setup/          (SPIFFE IDP configuration)
  - charts/kagenti-deps/                    (SPIRE Helm deployment)
  - docs/identity-guide.md                  (SPIFFE/SPIRE documentation)
  - scripts/kind/setup-kagenti.sh           (--with-spire flag)
Architecture:
  - SPIRE Server (Deployment in spire-system ns) issues SVIDs
  - SPIRE Agent (DaemonSet) attests workloads via Kubernetes SAT
  - SPIRE CSI Driver mounts SVIDs into pods at /opt/
  - Tornjak UI for SPIRE management
  - JWT SVIDs used as client identifiers for Keycloak registration
  - OIDC discovery endpoint exposes JWKS for JWT validation
Dependencies:     Kubernetes, cert-manager
Complexity:       HIGH (SPIRE server/agent infrastructure, attestation policies,
                  CSI driver, OIDC integration with Keycloak)
Languages:        Shell (setup scripts), YAML (Helm charts/CRDs)

3. OAuth2 TOKEN EXCHANGE (RFC 8693)
--------------------------------------------------------------------------------
Category:         Security / Identity
Type:             Core
Description:      Implements OAuth2 Token Exchange per RFC 8693 to enable secure
                  token delegation across the agent-tool call chain. When an agent
                  needs to call a tool, the user's token is exchanged for a
                  narrowly-scoped token with the correct audience for the target
                  service. This ensures least-privilege access and prevents token
                  reuse across services.
Key Files:
  - kagenti/examples/identity/keycloak_token_exchange/ (Examples/tests)
  - kagenti/examples/identity/token_exchange.md        (Deep dive docs)
  - kagenti/tests/e2e/token_exchange/                  (E2E tests)
  - docs/identity-guide.md                             (Flow documentation)
  - docs/diagrams/04-agent-token-exchange-flow.mmd     (Sequence diagram)
Architecture:
  - User authenticates with Keycloak, gets access token (aud: kagenti-ui)
  - Agent receives user token via delegated bearer
  - Agent exchanges token via Keycloak token endpoint with:
    grant_type=urn:ietf:params:oauth:grant-type:token-exchange
    subject_token=<user-token>
    audience=<target-service>
    client_id=<spiffe-id>
  - Result: audience-scoped token with act.sub = agent's SPIFFE ID
  - Token lifetime: short (5-15 minutes), must be refreshed
Dependencies:     Keycloak, SPIFFE/SPIRE, AuthBridge
Complexity:       HIGH (RFC 8693 protocol implementation, Keycloak configuration
                  for exchange policies, audience scoping, delegation chains)
Languages:        Python (examples/tests), Shell (scripts)

4. IDENTITY & AUTH BRIDGE (AUTHBRIDGE/CORTEX SIDECAR)
--------------------------------------------------------------------------------
Category:         Security / Identity
Type:             Core
Description:      AuthBridge (evolved into Cortex) is an Envoy-based sidecar
                  pattern that transparently handles both inbound JWT validation
                  and outbound token exchange for every agent and tool pod. It
                  uses Envoy with an ext-proc (external processor) Go service for
                  token operations. Traffic is intercepted via iptables, making it
                  completely transparent to application code.
Key Files:
  - docs/authbridge/                        (AuthBridge documentation)
  - docs/authbridge/README.md               (Overview)
  - docs/authbridge/security-model.md       (Security model)
  - docs/authbridge/deployment-guide.md     (Deployment guide)
  - docs/authbridge/tls-bridge.md           (TLS bridge pattern)
  - docs/access-control/README.md           (Cortex FGA architecture)
  - docs/access-control/zero-trust.md       (Centralized zero-trust)
  External repo: github.com/kagenti/kagenti-extensions/tree/main/authbridge
Architecture:
  - Envoy sidecar proxy in each agent/tool pod
  - Go ext-proc processor for token operations
  - proxy-init container installs iptables rules for transparent interception
  - INBOUND: Validates JWT signature, expiration, issuer via JWKS
  - OUTBOUND: Exchanges token for target audience via Keycloak (RFC 8693)
  - HTTPS passthrough for non-authenticated traffic
  - Four traffic directions: inbound req/resp, outbound req/resp
  - Webhook-based automatic injection (operator-managed via AgentRuntime CR)
  - Configurable modes: proxy-sidecar, envoy-sidecar, lite, waypoint
Dependencies:     Keycloak, Envoy, Kagenti Operator, SPIFFE/SPIRE (optional)
Complexity:       VERY HIGH (Envoy configuration, ext-proc Go service,
                  iptables interception, token exchange logic, webhook injection,
                  multiple modes, network namespace compatibility)
Languages:        Go (ext-proc), YAML (Envoy config), Shell (proxy-init)

5. FINE-GRAINED ZERO-TRUST ACCESS CONTROL (CORTEX/OPA)
--------------------------------------------------------------------------------
Category:         Security / Policy
Type:             Extension
Description:      Cortex (evolved AuthBridge) implements fine-grained
                  authorization (FGA) at every runtime boundary. Decisions take
                  into account the user, task, agent identities, tools, content,
                  and behaviors. Uses a multi-tiered access control model (Cluster,
                  Namespace, Component, Developer) with AND-gate enforcement.
                  Plugins enrich context; a centralized Access Control Engine
                  (OPA) makes final allow/deny decisions.
Key Files:
  - docs/access-control/README.md           (Architecture overview)
  - docs/access-control/zero-trust.md       (Centralized decision design)
Architecture:
  - Four-tier access control: Cluster, Namespace, Component, Developer
  - Plugin architecture: PIPs (context providers) → PDP (OPA) → PEP (enforce)
  - Cortex sidecar controls 4 traffic directions per agent
  - Authentication (fail-fast): mTLS validation, token presence
  - Authorization (deferred): claims, audiences, content analysis → OPA
  - Structured context contracts between plugins and OPA engine
  - Input/output guardrails, data leak prevention, behavioral anomaly detection
  - XACML-aligned: PIPs (plugins), PDP (OPA engine), PEP (gateway boundary)
Dependencies:     OPA (Open Policy Agent), AuthBridge/Cortex, Keycloak
Complexity:       VERY HIGH (distributed policy enforcement, plugin architecture,
                  multi-tiered rule hierarchy, XACML alignment, context schema)
Languages:        Go (plugins), Rego (OPA policies), YAML (configuration)
